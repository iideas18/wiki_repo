Why This Module Exists

The AI Hedge Fund engine is a powerful collection of autonomous agents capable of performing deep financial analysis — but without a user-facing interface, it remains locked behind command-line invocations, configuration files, and developer-only tooling. The Web Application module exists to democratize access to these capabilities, putting the full power of multi-agent portfolio analysis into the hands of analysts, portfolio managers, and researchers who may never touch a terminal.

At its core, the module solves three critical problems. First, it provides visual pipeline composition through a React Flow node-graph editor, allowing users to drag-and-drop analyst agents, connect them into custom workflows, and configure per-agent model selection — all without writing code. Second, it delivers real-time feedback via Server-Sent Events (SSE), streaming each agent's progress, intermediate results, and errors directly to the browser as they happen, rather than forcing users to wait for a batch process to complete. Third, it maintains a persistent execution history through SQLite-backed storage of flows, run configurations, and per-cycle results, enabling reproducibility and audit trails that are essential in financial applications.

Without this module, the gap between "powerful AI agents" and "actionable investment insight" would remain unbridged. The web application is the bridge — translating programmatic capability into visual, interactive, and observable workflows.

Design Decisions

Every architectural choice in this module reflects a deliberate trade-off. The table below captures the five most consequential decisions and the reasoning behind them.

DecisionChoiceAlternatives ConsideredRationale
Web Framework FastAPI Flask, Django, Express.js Native async support is essential for SSE streaming. Built-in OpenAPI docs accelerate frontend integration. Pydantic models provide request/response validation with zero boilerplate.
Database SQLite + SQLAlchemy ORM PostgreSQL, MongoDB Zero-infrastructure deployment — the database is a single file. SQLAlchemy provides migration support via Alembic and a clean ORM layer. The workload (single-user, low-write) fits SQLite perfectly.
Real-time Communication Server-Sent Events (SSE) WebSockets, Long Polling SSE is simpler than WebSockets for unidirectional server→client streaming. It works over standard HTTP (no upgrade), auto-reconnects, and is natively supported by browsers. The use case (progress updates) is inherently one-way.
Data Access Pattern Repository Pattern Direct ORM queries in routes, Active Record Isolates database logic from business logic. Services call repositories, not the ORM directly. This makes testing easier (mock repositories) and allows swapping storage backends without touching service code.
Frontend Graph Editor React Flow D3.js, Cytoscape.js, custom canvas React Flow provides a production-ready node graph editor with drag-and-drop, zoom/pan, edge routing, and custom node types out of the box. It integrates naturally with React state management and avoids months of custom canvas work.
Service Layer Abstraction Dedicated service classes Inline logic in route handlers AgentService, BacktestService, and GraphService encapsulate complex orchestration logic. Routes remain thin (validate → delegate → respond), and services can be reused across multiple endpoints or tested in isolation.

The system follows a classic layered architecture with a clear separation between the presentation layer (React frontend), the API layer (FastAPI routes), the business logic layer (services), and the data layer (repositories + SQLite). Narrated Walkthrough — From Flow Creation to Results

Follow along as we trace a complete user journey through the web application. Each step corresponds to a real interaction between the user, the frontend, and the backend.

User opens the application. The React frontend loads in the browser, fetches available language models from GET /api/language-models, and initializes the React Flow canvas. The theme is restored from localStorage.
User creates a new flow. Using the node graph editor, the user drags agent nodes (e.g., "Fundamentals Analyst", "Sentiment Analyst", "Risk Manager") onto the canvas and connects them with edges to define the execution order.
User configures per-agent models. Clicking on each agent node opens a config panel where the user selects which LLM to use (e.g., GPT-4, Claude, a local Ollama model). This per-agent model selection is stored in the node's data payload.
User saves the flow. The frontend serializes the React Flow graph (nodes + edges + config) into JSON and sends POST /api/flows. The GraphService validates the graph structure and the FlowRepository persists it as a HedgeFundFlow record in SQLite.
User enters run parameters. The user specifies ticker symbols (e.g., AAPL, GOOGL, MSFT), a date range, and an initial portfolio value. These parameters are independent of the flow definition — the same flow can be run with different tickers.
User clicks "Run Analysis". The frontend sends POST /api/hedge-fund/run with the flow ID and parameters. Simultaneously, it opens an EventSource connection to receive SSE events.
Backend compiles the graph. The GraphService reads the flow's JSON graph, performs topological sorting on the agent nodes, resolves per-agent model configs, and produces a compiled workflow object that the AgentService can execute.
AgentService begins execution. It emits a StartEvent listing all agents in the pipeline and the run ID. The frontend displays a progress panel showing each agent as "pending."
Agents execute sequentially. Each agent (fundamentals, sentiment, technical, risk) runs in order. After each completes, AgentService emits a ProgressUpdateEvent with the agent's name, status, and any intermediate results. The frontend updates the progress bar in real time.
An error occurs (optional path). If an agent fails — e.g., an API key is invalid or an LLM times out — an ErrorEvent is emitted. The frontend highlights the failed agent node in red and shows the error message. The run may continue with remaining agents or abort, depending on configuration.
Run completes. The AgentService aggregates all agent outputs into a final portfolio recommendation and emits a CompleteEvent. The run record (HedgeFundFlowRun) and per-cycle data (HedgeFundFlowRunCycle) are persisted to SQLite.
Results displayed. The React frontend receives the CompleteEvent, closes the SSE connection, and renders the results: portfolio allocations, individual agent analyses, confidence scores, and recommended trades.
User reviews history. Via GET /api/flow-runs, the user can browse past runs, compare results across different configurations, and re-examine individual agent outputs stored in HedgeFundFlowRunCycle records.
User runs a backtest. Using the same flow, the user sends POST /api/hedge-fund/backtest with a historical date range. The BacktestService replays the pipeline over historical data and returns performance metrics, which the frontend renders as charts and comparison tables.

Algorithm Spotlight

1. SSE Event Streaming

The SSE streaming mechanism is the backbone of the real-time UI. When a run starts, the AgentService returns an async generator that yields BaseEvent subclasses. FastAPI's EventSourceResponse wraps this generator, serializing each event to the SSE wire format (data: {json}\n\n). The browser's EventSource API automatically parses these and dispatches them to registered handlers.

Key design choices: events are typed via a type discriminator field, enabling the frontend to route them to different handlers. Each event includes a monotonically increasing sequence number for gap detection. If the SSE connection drops, the browser auto-reconnects and can request replay from the last seen sequence via the Last-Event-ID header.

2. Graph-to-Workflow Compilation

The GraphService transforms a React Flow graph (a JSON object with nodes and edges arrays) into a linear or branching workflow that the AgentService can execute. The algorithm performs three passes:

  1. Validation: Check for cycles (the graph must be a DAG), orphan nodes (nodes with no edges), and missing required configurations.
  2. Topological Sort: Using Kahn's algorithm, produce an execution order that respects all edge dependencies. Nodes at the same topological level can potentially be parallelized.
  3. Config Resolution: For each node, merge the node's local model config with global defaults, producing a fully resolved AgentConfig object with the selected LLM, temperature, and any agent-specific parameters.

3. Flow Persistence & Versioning

Flows are stored as JSON blobs in the HedgeFundFlow table. Each save creates or updates a record, preserving the full graph state (node positions, edge connections, per-node config). The FlowRepository handles serialization/deserialization, converting between SQLAlchemy models and Pydantic schemas. Runs reference flows by ID, so historical runs always link back to the exact flow configuration used — even if the flow is later modified. This provides a complete audit trail for regulatory and review purposes.

What Could Go Wrong

ScenarioImpactMitigation
SSE connection drops mid-run User loses real-time updates; may think the run crashed. Browser's EventSource auto-reconnects. Sequence numbers allow gap detection. The run continues server-side regardless; results are persisted and can be polled via REST.
SQLite write contention Concurrent writes (e.g., saving a flow while a run persists results) can cause SQLITE_BUSY errors. SQLAlchemy is configured with WAL mode and a busy timeout. The single-user deployment model makes heavy contention unlikely. For multi-user scenarios, migration to PostgreSQL is the recommended path.
Invalid graph configuration A graph with cycles, disconnected nodes, or missing model configs would produce undefined behavior if executed. The GraphService validates the graph before compilation. Validation errors are returned as 422 responses with descriptive error messages pointing to the problematic nodes.
LLM provider API failure An agent mid-pipeline fails because the upstream LLM (OpenAI, Anthropic) returns a 5xx or times out. Each agent has configurable retry logic with exponential backoff. Persistent failures emit an ErrorEvent and the run is marked as failed with the error details preserved in the run record.
Stale API keys User's stored API key has been rotated or revoked; all agent calls fail. The /api/api-keys endpoint allows key validation before use. Descriptive error messages on auth failures guide the user to update their keys.

Performance Profile

The web application's performance characteristics are shaped primarily by the underlying LLM calls, not by the web layer itself.

OperationTypical LatencyBottleneck
Flow CRUD< 50msSQLite I/O (negligible)
Graph compilation< 10msCPU (topological sort)
Single agent execution5–30sLLM API latency + token generation
Full pipeline (5 agents)30–120sSequential LLM calls
Backtest (30 days)5–15 minN × agent pipeline per day
SSE event delivery< 5msNetwork (local: sub-ms)

The SSE streaming architecture means users see progress immediately — the perceived latency is the time to the first agent completion (~5–30s), not the total pipeline time. This is a deliberate UX decision: streaming transforms a minutes-long wait into an engaging, incremental reveal.
