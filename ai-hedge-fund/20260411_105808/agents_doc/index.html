Why This Module Exists

The agents module is the intellectual core of the AI Hedge Fund system. Rather than implementing a single monolithic trading strategy, this module embodies a radical design thesis: encode 19 distinct investment philosophies as autonomous agents, each analyzing the same stock independently, then aggregate their signals through risk management and portfolio optimization.

The motivation is diversification of reasoning, not just assets. A Warren Buffett agent focuses on owner earnings and competitive moats. A Michael Burry agent hunts for deep value and contrarian plays. A technical analyst ignores fundamentals entirely and looks at price action. By running all 19 in parallel via LangGraph's fan-out pattern, the system captures a spectrum of market perspectives that no single strategy could achieve.

Each agent follows a hybrid approach: first computing quantitative scores from real financial data (SEC filings, price history, analyst estimates), then invoking an LLM to synthesize those scores into a final bullish/bearish/neutral signal with confidence and reasoning. This combination ensures that the LLM is grounded in data rather than hallucinating, while still benefiting from the LLM's ability to weigh qualitative factors and explain its reasoning in natural language.

The output is a standardized signal format—{signal, confidence, reasoning}—that feeds downstream into the Risk Manager (which applies position-sizing constraints) and the Portfolio Manager (which generates final trade orders). The agents module is deliberately stateless: it receives an AgentState TypedDict, enriches it, and returns. No agent remembers past analyses, ensuring reproducibility.

Narrated Walkthrough — Warren Buffett Agent Analyzing AAPL

Let's follow exactly what happens when the Warren Buffett agent receives a request to analyze Apple Inc. (AAPL).

LangGraph dispatches the agent. The runtime calls warren_buffett_agent(state) where state is an AgentState TypedDict containing tickers=["AAPL"], start_date, end_date, and the current portfolio. All 19 agents are dispatched in parallel.
The agent extracts the ticker list. It iterates over state["tickers"]. For each ticker, it begins an independent analysis. The agent processes one ticker at a time within its function.
Financial data is fetched via tools/api.py. The agent calls get_financial_metrics("AAPL") to retrieve 10 years of income statements, balance sheets, and cash flow statements. Results are cached to avoid redundant API calls across agents.
Price data is retrieved. get_prices("AAPL", start, end) returns daily OHLCV data for the analysis window. This is used for computing returns and volatility.
Owner Earnings are calculated. Buffett's signature metric: owner_earnings = net_income + depreciation - capex. The agent computes this for each year and checks the trend. A rising trend in owner earnings is bullish.
Return on Equity (ROE) is evaluated. The agent checks whether ROE is consistently above 15% — Buffett's threshold for a "wonderful company." It computes a rolling average to smooth out one-time events.
Debt-to-Equity ratio is checked. Buffett prefers companies that can pay off long-term debt within 3-4 years of earnings. The agent computes debt_payoff_years = total_debt / owner_earnings.
Competitive moat indicators are assessed. The agent examines gross margin stability, revenue growth consistency, and return on invested capital (ROIC). Stable or improving metrics suggest a durable moat.
Intrinsic value is estimated via DCF. Using owner earnings as the free cash flow proxy, a discount rate of 10%, and a terminal growth rate of 3%, the agent computes a present value estimate. It then compares this to the current market price to assess margin of safety.
Quantitative scores are assembled. Each criterion (owner earnings trend, ROE, debt, moat, margin of safety) produces a sub-score. These are combined into a summary dictionary passed to the LLM.
The LLM is invoked for synthesis. utils/llm.py sends a carefully crafted prompt: "You are Warren Buffett. Analyze AAPL based on these metrics..." along with the structured data. The LLM is constrained to return {signal, confidence, reasoning} via JSON schema.
The structured signal is validated. The agent checks that signal ∈ {bullish, bearish, neutral} and 0 ≤ confidence ≤ 100. Invalid responses are retried or defaulted to neutral with low confidence.
The signal is merged into AgentState. Using LangGraph's merge-dicts reducer, the agent writes state["analyst_signals"]["warren_buffett"] = {signal, confidence, reasoning}. This does not overwrite other agents' signals.
Control returns to LangGraph. The runtime waits for all 19 agents to complete, then proceeds to the Risk Manager node. The entire Buffett analysis typically completes in 3-8 seconds, dominated by the LLM call.

1. Weighted Signal Combination (Technical Analyst)

The Technical Analyst is unique — it uses no LLM. Instead, it runs 5 sub-strategies and combines them with configurable weights:

# Each strategy returns a signal in [-1, 1] range
strategy_signals = {
    "trend_following": compute_trend_signal(prices),     # EMA crossover
    "mean_reversion": compute_mean_reversion(prices),    # Bollinger Bands
    "momentum": compute_momentum_signal(prices),         # RSI + MACD
    "volatility": compute_volatility_signal(prices),     # ADX + ATR
    "statistical_arb": compute_stat_arb_signal(prices),  # Hurst exponent
}

# Weighted combination — weights sum to 1.0
weights = {
    "trend_following": 0.25,
    "mean_reversion": 0.20,
    "momentum": 0.25,
    "volatility": 0.15,
    "statistical_arb": 0.15,
}

final_score = sum(
    strategy_signals[s] * weights[s] for s in strategy_signals
)
# Map [-1, 1] → {bullish, bearish, neutral} with confidence

2. Hurst Exponent for Mean Reversion Detection

The statistical arbitrage sub-strategy uses the Hurst exponent to determine whether a price series is trending (H > 0.5), mean-reverting (H < 0.5), or random (H ≈ 0.5). This informs whether a mean-reversion or trend-following strategy is more appropriate.

def compute_hurst_exponent(prices, max_lag=20):
    """Rescaled Range (R/S) analysis for Hurst exponent."""
    lags = range(2, max_lag)
    rs_values = []
    for lag in lags:
        subseries = [prices[i:i+lag] for i in range(0, len(prices)-lag, lag)]
        rs = []
        for s in subseries:
            mean = np.mean(s)
            deviations = np.cumsum(s - mean)
            R = max(deviations) - min(deviations)
            S = np.std(s, ddof=1)
            if S > 0:
                rs.append(R / S)
        if rs:
            rs_values.append((lag, np.mean(rs)))

    # Hurst = slope of log(R/S) vs log(lag)
    log_lags = [np.log(r[0]) for r in rs_values]
    log_rs = [np.log(r[1]) for r in rs_values]
    hurst = np.polyfit(log_lags, log_rs, 1)[0]
    return hurst  # < 0.5 = mean-reverting, > 0.5 = trending

3. DCF Intrinsic Valuation

Multiple investor agents (Buffett, Graham, Damodaran, Valuation analyst) compute discounted cash flow valuations with varying parameters. The core formula:

def compute_intrinsic_value(free_cash_flows, discount_rate=0.10,
                             terminal_growth=0.03, projection_years=5):
    """Two-stage DCF: explicit projection + terminal value."""
    # Stage 1: Project FCF forward
    growth_rate = estimate_growth_rate(free_cash_flows)
    projected = []
    for year in range(1, projection_years + 1):
        fcf = free_cash_flows[-1] * (1 + growth_rate) ** year
        pv = fcf / (1 + discount_rate) ** year
        projected.append(pv)

    # Stage 2: Terminal value (Gordon Growth Model)
    terminal_fcf = projected[-1] * (1 + terminal_growth)
    terminal_value = terminal_fcf / (discount_rate - terminal_growth)
    pv_terminal = terminal_value / (1 + discount_rate) ** projection_years

    return sum(projected) + pv_terminal

Performance Profile

The agents module is the most computationally expensive part of the system, but its architecture is optimized for parallelism. In a typical run analyzing 5 tickers, all 19 agents run in parallel via LangGraph's fan-out, reducing wall-clock time from 19 × T to approximately max(T₁, T₂, ..., T₁₉). The bottleneck is almost always the LLM API call, which accounts for 60-80% of each agent's execution time.

Data fetching is amortized across agents: the first agent to request AAPL's financial data triggers an API call, but subsequent agents hit a warm cache. Quantitative computation (ratio analysis, DCF, technical indicators) is typically sub-second per ticker. The Technical Analyst, being pure computation with no LLM call, consistently finishes in under 500ms.

Memory usage is modest — each agent holds only its ticker's data in memory (typically <10 MB). The AgentState TypedDict grows linearly with the number of agents × tickers, but remains under 1 MB for typical workloads. The entire 19-agent analysis for 10 tickers completes in 15-30 seconds depending on LLM provider latency.
