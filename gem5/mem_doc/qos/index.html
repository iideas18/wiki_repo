    Overview

    📚 What is this & why does it exist?

    Analogy — Airport Priority Lanes

    Think of the QoS memory system as an airport with multiple priority lanes. Economy passengers (low-priority requestors) and business class passengers (high-priority requestors) both need to get through security (the memory controller). The Fixed Priority policy always lets business class go first. The Proportional Fair policy gives everyone a fair share based on their needs — if an economy passenger has been waiting a long time, they get bumped up. The Turnaround Policy decides when to switch the security lanes from departures (reads) to arrivals (writes) and back, minimizing the overhead of switching direction at the DRAM bus.

    The qos/ directory provides a QoS framework for gem5 memory controllers. It sits between the Cache Hierarchy | gem5 Wiki" href="../cache/index.html">cache hierarchy and the DRAM/NVM backend, enabling differentiated memory service based on requestor identity, priority, or fairness objectives.

    The framework consists of three key abstractions:

    • QoS Memory System | gem5 Wiki" class="xref">MemCtrl — QoS-aware memory controller base class that integrates policies into the scheduling pipeline
    • QoS Policy — Priority assignment algorithm (Fixed Priority, Proportional Fair)
    • Turnaround Policy — Read/write bus direction switching policy
    • Queue Policy — Per-requestor queue management and admission control

    Narrated Walkthrough: QoS-Aware Memory Access

    Request arrives — A memory request arrives at the QoS-aware memory controller from the crossbar. The packet carries a requestorId identifying the source (CPU 0, CPU 1, GPU, etc.).
    Priority assignment — The controller calls Policy::schedule() to determine the request's priority. With FixedPriority, priority is a static mapping from requestorId. With ProportionalFair, priority is dynamically adjusted based on each requestor's recent bandwidth consumption.
    Queue admission — The QueuePolicy decides if the request can enter the queue. It may reject low-priority requests when the queue is congested, or reorder entries to maintain priority ordering.
    Scheduling — The scheduler selects the next request to issue from the read or write queue. Higher-priority requests are served first. Within the same priority level, FR-FCFS (First-Ready First-Come-First-Serve) is typically used.
    Bus turnaround — The TurnaroundPolicy determines whether to switch the DRAM bus between read and write mode. The IdealTurnaround policy minimizes bus turnaround overhead by batching reads and writes.
    DRAM access — The request is issued to the DRAM interface, which models the detailed timing of activate, read/write, and precharge commands.
    Pipeline — gem5 Wiki" class="xref">Statistics update — The controller updates per-requestor statistics: bandwidth consumed, latency, and priority distribution. This feeds back into Proportional Fair priority adjustment.

    Scheduling Policies Deep Dive

    Fixed Priority Policy

    The simplest QoS policy: each requestor has a statically configured priority level. The memory controller always serves higher-priority requestors first.

    flowchart LR

    PRI["Assigned Priority"]
    Q["Priority Queue"]

    REQ --> MAP
    MAP --> PRI
    PRI --> Q

    MAP -.- CFG["Configuration:\nCPU0 → 3 (high)\nCPU1 → 2\nGPU → 1 (low)"]

    Characteristics:

    • Zero runtime overhead — priority is a table lookup
    • Deterministic behavior — easy to reason about
    • Risk of starvation for low-priority requestors under heavy load
    • Best for: systems with well-defined priority hierarchies (e.g., real-time CPU over background GPU)

    Proportional Fair Policy

    A dynamic policy inspired by wireless networking's proportional fair scheduling. Each requestor's priority is inversely proportional to its recent bandwidth consumption.

    Click to expand 
    flowchart TD

    RANK["Rank by Score"]
    PRI["Priority Assignment"]

    REQ --> HIST
    HIST --> SCORE

    Characteristics:

    • Adapts to changing workload behavior at runtime
    • Prevents starvation — underserved requestors naturally receive higher priority
    • Configurable weight per requestor to bias the "fair share"
    • Tracks bandwidth over a sliding time window
    • Best for: multi-tenant workloads where fairness matters

    Turnaround Policy

    DRAM bus direction switching is expensive (typically 5-15ns turnaround penalty). The turnaround policy batches reads and writes to minimize switches:

    • IdealTurnaround — Switches only when the current direction's queue is empty or a high-priority request in the other direction is waiting. Minimizes turnaround count.
    • Custom policies can implement hysteresis, threshold-based switching, or age-based urgency.

    Queue Management

    The QueuePolicy controls how requests are admitted into and ordered within the memory controller's queues:

    AspectMechanismPurpose
    Per-requestor limitsMaximum queue entries per requestorIdPrevents one requestor from monopolizing the queue
    Priority orderingRequests sorted by assigned QoS priorityEnsures higher-priority requests are served first
    Admission controlReject/stall low-priority requests when queue is fullBack-pressure to prevent buffer overflow
    Separate read/writeIndependent queues for reads and writesEnables read-priority or write-draining modes

    Configuration Examples

    // Python configuration: Fixed Priority QoS
system.mem_ctrl = MemCtrl(
    dram = DDR4_2400_16x4(),
    qos_policy = QoSFixedPriority(
        # CPU cores get high priority, GPU gets low
        qos_priorities = {
            'system.cpu0': 3,
            'system.cpu1': 3,
            'system.gpu':  1,
            'system.dma':  0
        }
    ),
    qos_turnaround_policy = QoSIdealTurnaround()
)
    // Python configuration: Proportional Fair QoS
system.mem_ctrl = MemCtrl(
    dram = DDR4_2400_16x4(),
    qos_policy = QoSPropFairPolicy(
        # Weight each requestor's fair share
        weight = {
            'system.cpu0': 2.0,   # Double share
            'system.cpu1': 1.0,   # Normal share
            'system.gpu':  0.5    # Half share
        },
        # Sliding window for bandwidth tracking
        scoring_interval = '10us'
    ),
    qos_turnaround_policy = QoSIdealTurnaround()
)
    // C++ internals: Policy interface
namespace qos {

class Policy : public SimObject {
  public:
    // Called for each incoming memory request
    // Returns priority level (0 = lowest, N = highest)
    virtual uint8_t schedule(const RequestorID id,
                             const uint64_t data) = 0;
};

class FixedPriorityPolicy : public Policy {
    // priority_map: RequestorID -> priority level
    std::map<RequestorID, uint8_t> priority_map;

  public:
    uint8_t schedule(const RequestorID id,
                     const uint64_t data) override {
        auto it = priority_map.find(id);
        return (it != priority_map.end()) ? it->second : 0;
    }
};

} // namespace qos

    • Upstream: Receives requests from the cache hierarchy via ResponsePort

    Glossary

    TermDefinition
    RequestorA unique source of memory requests, identified by RequestorID. Typically one per CPU core, GPU CU, or DMA engine.
    Priority LevelInteger value (0 = lowest) assigned to requests by the QoS policy. Higher-priority requests are scheduled before lower ones.
    Proportional FairScheduling algorithm that balances fairness and throughput by favoring requestors that have recently received less service.
    Bus TurnaroundThe time penalty incurred when switching the DRAM data bus direction between reads and writes (typically tWTR or tRTW).
    FR-FCFSFirst-Ready First-Come-First-Served — common DRAM scheduling policy that prioritizes row-hit requests, then by arrival order.
    Write DrainMode where the controller exclusively processes writes to free write buffer space, triggered when the write queue exceeds a threshold.
