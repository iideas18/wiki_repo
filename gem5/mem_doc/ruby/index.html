    Overview

    📚 What is this & why does it exist?

    Analogy — Traffic Management

    Think of Ruby as a city-wide traffic management system. Each intersection (Cache Hierarchy | gem5 Wiki" href="../cache/index.html">cache controller) has its own traffic lights (coherence state machine) that follow a rulebook (SLICC protocol). The road network (on-chip network) carries messages between intersections. A central dispatch (directory controller) keeps track of where every vehicle (cache line) is located, ensuring no two intersections claim exclusive rights to the same road. The Sequencer is the on-ramp where CPUs enter the highway, and MessageBuffers are the traffic lanes connecting intersections.

    Ruby is gem5's detailed coherence protocol simulator. Unlike the Classic cache system (which has coherence logic hardcoded in C++), Ruby uses SLICC (Specification Language for Implementing Cache Coherence) to define protocol state machines. This makes it straightforward to implement and test new coherence protocols — from Atomic and Timing Simple CPUs — gem5 Wiki" href="../../cpu_doc/simple/index.html">simple MI to complex MOESI_CMP_directory.

    Key features:

    • SLICC-generated controllers — Coherence logic defined in a high-level DSL, compiled to C++
    • Network models — Simple network (abstract) and Garnet (detailed NoC with routers, VCs, flow control)
    • Directory-based coherence — Scalable multiprocessor coherence via directory controllers
    • GPU coalescer — Specialized memory interface for GPU compute units
    • HTM support — Hardware Transactional Memory via HTMSequencer
    • Profiling — Detailed coherence protocol statistics and event tracking

    SLICC Protocol System

    SLICC (Specification Language for Implementing Cache Coherence) is a domain-specific language that compiles into C++ controller code. Each protocol defines:

    • States — Cache line states (e.g., I, S, M, O, E and transient states)
    • Events — Triggers (e.g., Load, Store, Fwd_GetS, Data_from_Dir)
    • Transitions — State × Event → Actions + New State
    • Actions — Atomic operations (send message, allocate TBE, set permissions)

    SLICC Compilation Pipeline

    Protocol definition — Write .sm files defining states, events, transitions, and actions for each controller type (L1Cache, L2Cache, Directory).
    SLICC compiler — The SLICC compiler (System and Standard Library — the control plane of gem5" href="../../python/index.html">Python-based, in src/mem/slicc/) parses the .sm files and generates C++ controller classes.
    Generated code — Output includes controller classes, message types, and profiling stubs that integrate with the Ruby infrastructure.
    Integration — Generated controllers extend AbstractController and plug into the network via MessageBuffer ports.

    Network Models

    Ruby provides two network implementations with different fidelity/speed trade-offs:

    Simple Network

    An abstract network model that delivers messages with fixed latency. No contention modeling — messages never block each other. Fast simulation for protocol debugging.

    • Fixed per-hop latency
    • Infinite bandwidth links
    • No router microarchitecture
    • Best for: protocol correctness testing, large-scale studies where network detail isn't critical

    Garnet Network

    A detailed on-chip network model with cycle-accurate router pipelines, virtual channels, credit-based flow control, and configurable topologies.

    • 5-stage router pipeline (buffer write → route compute → VC allocate → switch allocate → switch traverse)
    • Wormhole routing with virtual channels (VCs)
    • Credit-based flow control
    • Configurable link bandwidth, latency, and buffer depths
    • Support for mesh, torus, custom topologies
    • Fault injection modeling
    • Best for: NoC research, detailed performance studies

    Request Flow Walkthrough

    Trace a CPU load through the Ruby coherence system:

    CPU issues load — The CPU sends a read request to the Sequencer via RubyPort.
    Sequencer processes — The Sequencer checks its pending table for conflicts, then calls makeRequest() on the L1 cache controller.
    L1 controller event — The SLICC state machine receives a Load event. If the block is in state S or M, it returns data immediately.
    Cache miss → GetS — If the block is in state I, the controller transitions to IS_D and enqueues a GetS message into the network.
    Network transport — The message traverses the on-chip network (Simple: fixed latency; Garnet: full router pipeline) to reach the directory.
    Directory lookup — The Directory controller looks up the address. If no exclusive owner exists, it fetches data from memory and sends Data_from_Dir.
    Data response — The data message travels back through the network to the requesting L1 controller.
    State transition — The L1 controller receives the data, transitions from IS_D to S, allocates the cache block, and notifies the Sequencer.
    Sequencer completes — The Sequencer marks the request as complete and sends the response back to the CPU via RubyPort.

    Sub-module Overview

    system/

    Core Ruby infrastructure: RubySystem, Sequencer, DMASequencer, GPUCoalescer, HTMSequencer, RubyPort, CacheRecorder. The interface between gem5 CPUs and Ruby's protocol world.

    20+ files · CPU/GPU interface

    network/

    On-chip network models. Includes SimpleNetwork (abstract), Garnet (detailed NoC), MessageBuffer, Topology, BasicRouter, BasicLink. Contains garnet/ and simple/ sub-directories.

    15+ files · 2 network models

    structures/

    Storage components: CacheMemory, DirectoryMemory, PerfectCacheMemory, BankedArray, TBE tables, PersistentTable, RubyPrefetcher.

    15+ files · Cache/directory storage

    slicc_interface/

    SLICC runtime: AbstractController, AbstractCacheEntry, RubyRequest, Message, ProtocolInfo. Base classes that SLICC-generated code extends.

    13+ files · Protocol runtime

    protocol/

    SLICC protocol source files (.sm). This directory is populated based on the selected protocol at build time. Contains the state machine definitions.

    Per-protocol · SLICC source

    profiler/

    Ruby-specific profiling and statistics collection. Tracks protocol events, cache hit/miss rates, network utilization, and coherence transition counts.
