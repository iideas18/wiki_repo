pci — PCI Bus and Device Framework

PCI/PCIe Device Simulation Infrastructure

The pci sub-module implements the complete PCI subsystem for gem5: a configurable host bridge with CAM/ECAM configuration space, PCI bus crossbar, Base Address Register (BAR) management for I/O and memory mapping, MSI/MSI-X interrupt support, and the class hierarchy for endpoint and bridge devices.

Config Space BAR Mapping MSI/MSI-X Bus Topology

📚 What is this & why does it exist?

The PCI sub-module simulates the complete PCI bus protocol: host bridges, device enumeration, configuration space, BAR mapping, and MSI/MSI-X interrupts. It lets guest operating systems discover and configure simulated hardware devices exactly as they would on real silicon.

💡 Real-world analogy

Think of the PCI bus like a sophisticated USB hub. The PciHost is the hub controller sitting between the CPU and all peripheral devices. Each device has a unique address (bus:device:function) and a set of mailbox slots (BARs) where it receives commands. The hub translates between the CPU address space and each device local address space.

📚 What is PCI in gem5?

PCI (Peripheral Component Interconnect) is the standard bus for connecting high-speed devices like network cards, GPUs, and storage controllers to the CPU. In gem5, the pci module simulates the entire PCI discovery and configuration protocol so that a guest OS can enumerate devices, assign memory regions, configure interrupts, and communicate with simulated hardware — just like on a real machine.

💡 Analogy: PCI as a USB Hub

Think of the PCI bus like a sophisticated USB hub. The PciHost is the hub itself — it sits between the CPU (your computer) and all the peripheral devices (USB devices). Each device plugged into the hub has a unique address (bus:device:function) and a set of "mailbox slots" (BARs) where it receives commands. The hub translates between the CPU's physical address space and each device's local address space, just as a USB hub routes packets to the right device. When a device needs attention, it sends an "interrupt" — like a USB device signaling it has data ready.

    PCI Configuration Space

    Every PCI device has a 256-byte configuration header. The first 64 bytes are standardized (Type 0 for endpoints, Type 1 for bridges). gem5 implements this via PCIConfig, PCIConfigType0, and PCIConfigType1 unions in pcireg.h.

    Configuration Access Flow

    sequenceDiagram
    participant OS as Guest OS
    participant HOST as GenericPciHost
    participant BUS as PciBus
    participant DEV as PciDevice

    Note over OS,DEV: Config Read — OS enumerates device
    OS->>HOST: MMIO read to ECAM region (confBase + BDF offset)
    HOST->>HOST: Decode bus/device/function from address
    HOST->>BUS: Forward to config address range
    BUS->>DEV: Route to device's config port
    DEV->>DEV: readConfig(pkt) — return from _config
    DEV-->>BUS: Config data response
    BUS-->>HOST: Forward response
    HOST-->>OS: Return vendor ID, device ID, etc.

    Note over OS,DEV: BAR Programming — OS assigns addresses
    OS->>HOST: MMIO write to BAR register offset
    HOST->>BUS: Forward write
    BUS->>DEV: writeConfig(pkt)
    DEV->>DEV: PciBar::write() — update address mapping
    DEV-->>OS: BAR programmed, device responds at new address

    PCI Host Bridge

    GenericPciHost is the configurable root complex that bridges between the system memory bus and the PCI subsystem. It provides three key mappings:

    SpaceParameterDescription
    Configurationconf_base, conf_size, conf_device_bitsECAM (12 bits/device) or CAM (8 bits/device) config space layout
    PIO / Legacy I/Opci_pio_baseBase offset added to PCI I/O addresses to get physical addresses
    Memorypci_mem_baseBase offset added to PCI memory addresses for physical mapping
    DMApci_dma_baseOffset for translating PCI bus addresses to system DMA addresses

    Interrupt Routing

    The host bridge maps PCI interrupt pins (INTA#–INTD#) to platform-level interrupt numbers. The default mapPciInterrupt() uses the device's interrupt line register, but subclasses can override this for platform-specific swizzling (e.g., AArch32, AArch64, TrustZone security extensions, SVE/SVE2 vector processing, PMU, and hardware transactional memory." href="../../arch_doc/arm/index.html">ARM GIC SPI mapping).

    // GenericPciHost interrupt delivery
void GenericPciHost::interfacePostInt(const PciDevAddr &addr, PciIntPin pin)
{
    platform.postPciInt(mapPciInterrupt(addr, pin));
}

void GenericPciHost::interfaceClearInt(const PciDevAddr &addr, PciIntPin pin)
{
    platform.clearPciInt(mapPciInterrupt(addr, pin));
}

    PCI Bus

    PciBus extends NoncoherentXBar to implement PCI bus topology. It adds a special config error port that catches configuration accesses to non-existent devices (returning 0xFFFFFFFF, the standard PCI "no device" response).

    // PciBus — a non-coherent crossbar with config error handling
class PciBus : public NoncoherentXBar
{
  public:
    PARAMS(PciBus);
    PciBus(const Params &p);

    Port &getPort(const std::string &if_name,
                  PortID idx = InvalidPortID) override;

  protected:
    // Override to handle config space routing
    PortID findPort(AddrRange addr_range, PacketPtr pkt = nullptr) override;

    PortID configErrorPortID;
    AddrRange configRange;
};

    Registration and Discovery

    When a PciDevice is constructed, it receives a PciUpstream::DeviceInterface from the PCI host. This interface provides methods for address translation and interrupt delivery:

    // PciUpstream::DeviceInterface methods used by PciDevice
Addr pioAddr(Addr pci_addr);   // translate PCI I/O addr → physical
Addr memAddr(Addr pci_addr);   // translate PCI mem addr → physical
Addr dmaAddr(Addr pci_addr);   // translate PCI bus addr → DMA addr
void postInt();                 // post interrupt via host bridge
void clearInt();                // clear interrupt via host bridge

    Read/Write Dispatch

    PciDevice::read() and write() are final — they dispatch to config space or device space based on the address:

    flowchart TD
    A["Incoming Packet"] --> B{Address in config range?}
    B -->|Yes| C["readConfig() / writeConfig()"]
    B -->|No| D{Address matches a BAR?}
    D -->|Yes| E["readDevice() / writeDevice()"]
    D -->|No| F["Error response"]
    C --> G["Return config register data"]
    E --> H["Device-specific logic"]

    Copy Engine — A PCI Device Example

    The CopyEngine in pci/copy_engine.hh is a concrete example of a PCI endpoint device. It models the Intel I/O Acceleration Technology (I/O AT) DMA copy engine, which the guest OS can use to offload memory copies:

    // Simplified usage in gem5 Python config
from m5.objects import CopyEngine, PciMemBar

copy_engine = CopyEngine(
    pci_bus=0, pci_dev=4, pci_func=0,
    InterruptLine=0x20,
    BAR0=PciMemBar(size='4KiB')  # Control registers
)
system.pci_host.attach(copy_engine)

    Creating a New PCI Device

    To implement a custom PCI endpoint device in gem5, inherit from PciEndpoint and override readDevice() and writeDevice():

    // my_pci_device.hh
#include "dev/pci/device.hh"
#include "params/MyPciDevice.hh"

namespace gem5 {

class MyPciDevice : public PciEndpoint
{
  public:
    PARAMS(MyPciDevice);
    MyPciDevice(const Params &p);

  protected:
    // Handle reads to BAR-mapped addresses
    Tick readDevice(PacketPtr pkt) override
    {
        int bar_num;
        Addr offset;
        getBAR(pkt->getAddr(), bar_num, offset);

        // Decode register at offset within BAR
        switch (offset) {
          case 0x00: // STATUS register
            pkt->setLE<uint32_t>(statusReg);
            break;
          case 0x04: // DATA register
            pkt->setLE<uint32_t>(dataReg);
            break;
          default:
            pkt->setLE<uint32_t>(0);
        }
        pkt->makeAtomicResponse();
        return pioDelay;
    }

    // Handle writes to BAR-mapped addresses
    Tick writeDevice(PacketPtr pkt) override
    {
        int bar_num;
        Addr offset;
        getBAR(pkt->getAddr(), bar_num, offset);

        uint32_t val = pkt->getLE<uint32_t>();
        switch (offset) {
          case 0x08: // COMMAND register
            processCommand(val);
            break;
        }
        pkt->makeAtomicResponse();
        return pioDelay;
    }

  private:
    uint32_t statusReg = 0;
    uint32_t dataReg = 0;
    void processCommand(uint32_t cmd);
};

} // namespace gem5
