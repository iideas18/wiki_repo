arm — ARM/AArch64 ISA Implementation

Comprehensive ARM architecture support including AArch32, AArch64, TrustZone security extensions, SVE/SVE2 vector processing, PMU, and hardware transactional memory.

📚 What is this & why does it exist?

💡 Think of it like…

The ARM ISA implementation is like a Swiss Army knife — compact and versatile. The decoder flips between three blades: 32-bit ARM mode (the full-size knife), 16-bit Thumb mode (the compact tool), and 64-bit AArch64 mode (the modern multi-tool). TrustZone adds a lockbox (Secure World) that even the main blade can't access, while SVE extends the toolkit with adjustable-length vector tools that scale to any width.

Instruction Decoder

The ARM decoder handles three instruction sets within the same architecture: ARM (32-bit fixed-width), Thumb (16/32-bit variable), and AArch64 (32-bit fixed-width but different encoding). The current execution state determines which decoder path is used.

namespace ArmISA {

class Decoder : public InstDecoder
{
  public:
    void moreBytes(const PCStateBase &pc, Addr fetchPC) override;
    bool instReady() const override;
    StaticInstPtr decode(PCStateBase &nextPC) override;

  private:
    // Decode based on current execution state
    StaticInstPtr decodeInst(ExtMachInst mach_inst);

    // AArch32 decode paths
    StaticInstPtr decodeArm(ExtMachInst mach_inst);
    StaticInstPtr decodeThumb(ExtMachInst mach_inst);

    // AArch64 decode path
    StaticInstPtr decodeAArch64(ExtMachInst mach_inst);

    bool bigThumb;    // In second half of 32-bit Thumb
    bool aarch64;     // AArch64 execution state
    ExtMachInst emi;
};

TrustZone Security

TrustZone partitions the system into Secure and Non-Secure worlds. EL3 (Secure Monitor) mediates transitions. gem5 models the full security extension including secure memory regions, secure interrupts, and world switching.

// Security state check
bool isSecure(ThreadContext *tc) {
    SCR scr = tc->readMiscReg(MISCREG_SCR_EL3);
    return !scr.ns;  // NS bit = 0 means Secure
}

// Exception model considers security state for:
// - Memory access permissions (secure vs non-secure)
// - Interrupt routing (FIQ to Secure World)
// - Page table selection (secure/non-secure TTBR)
// - Device access (TrustZone-aware peripherals)

Fault Handling

ARM faults implement the full exception model including precise exception levels, syndrome registers, and fault address reporting.

namespace ArmISA {

class ArmFault : public FaultBase
{
  protected:
    ExceptionLevel toEL;     // Target exception level
    OperatingMode toMode;    // Target mode (AArch32)
    FaultSource faultSource; // Hardware or software fault

  public:
    void invoke(ThreadContext *tc, const StaticInstPtr &inst) override;

    // ARM-specific: update syndrome register
    virtual uint32_t iss() const = 0;      // Instruction Specific Syndrome
    virtual ExceptionClass ec() const = 0; // Exception Class

    // Determine target EL based on routing rules
    ExceptionLevel targetEL(ThreadContext *tc) const;
};

// Specific faults
class UndefinedInstruction : public ArmFault { /* EC=0x00 */ };
class SupervisorCall : public ArmFault { /* EC=0x15 (SVC) */ };
class HypervisorCall : public ArmFault { /* EC=0x16 (HVC) */ };
class SecureMonitorCall : public ArmFault { /* EC=0x17 (SMC) */ };
class DataAbort : public ArmFault {
    Addr faultAddr;     // FAR_ELx
    bool isWrite;
    /* EC=0x24 (lower EL) or 0x25 (same EL) */
};
class PrefetchAbort : public ArmFault { /* EC=0x20/0x21 */ };

} // namespace ArmISA

Performance Monitoring Unit

The ARM PMU models hardware performance counters that count architectural events. It uses the probe framework to attach to CPU events without modifying pipeline code.

// ARM PMU event types
enum PMUEvent {
    SW_INCR        = 0x00,  // Software increment
    L1I_CACHE_REFILL = 0x01, // L1 I-cache refill
    L1D_CACHE_REFILL = 0x03, // L1 D-cache refill
    L1D_CACHE      = 0x04,  // L1 D-cache access
    INST_RETIRED   = 0x08,  // Instruction retired
    EXC_TAKEN      = 0x09,  // Exception taken
    BR_MIS_PRED    = 0x10,  // Branch misprediction
    CPU_CYCLES     = 0x11,  // CPU cycle count
    BR_PRED        = 0x12,  // Branch predicted
    MEM_ACCESS     = 0x13,  // Data memory access
    // ... many more event types
};

🔍 Narrated Walkthrough: AArch64 Exception Entry

  1. Trigger — A DataAbort fault occurs when the CPU accesses an unmapped page at EL0 (user space).
  2. Target EL — The fault routing logic checks HCR_EL2 and SCR_EL3 to determine the target exception level. For a standard OS, data aborts route to EL1.
  3. State Save — The processor saves PSTATE to SPSR_EL1 and the return address to ELR_EL1. The faulting address is written to FAR_EL1.
  4. Syndrome — ESR_EL1 is loaded with the exception syndrome: EC (exception class = DataAbort), ISS (instruction-specific syndrome including DFSC, WnR bit).
  5. Vector Jump — PC is set to VBAR_EL1 + offset (0x000 for synchronous from lower EL using AArch64). Execution continues at the kernel's exception handler.
  6. Handler — The OS reads FAR_EL1 and ESR_EL1 to determine what happened, maps the page, then returns via ERET to resume the faulting instruction.
