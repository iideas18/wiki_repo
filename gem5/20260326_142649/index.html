gem5 is a modular, event-driven computer architecture simulator combining the best features of M5 and GEMS. It models complete systems including CPUs (out-of-order, in-order, Atomic and Timing Simple CPUs — gem5 Wiki" href="cpu_doc/simple/index.html">simple), memory hierarchies (caches, DRAM, Ruby coherence), devices, and ISAs (x86, AArch32, AArch64, TrustZone security extensions, SVE/SVE2 vector processing, PMU, and hardware transactional memory." href="arch_doc/arm/index.html">ARM, RISC-V, MIPS, SPARC, Power) for microarchitectural research, teaching, and hardware/software co-design.

📚 What is this & why does it exist?

gem5 is the de-facto standard open-source simulator for computer architecture research. It allows researchers and engineers to model and evaluate processor designs, memory systems, and interconnects without building physical hardware. gem5 supports both system-call emulation (SE) mode for running individual programs and full-system (FS) mode for booting entire operating systems.

💡 Real-world analogy

Think of gem5 like a high-fidelity flight simulator for chip architects. Just as pilots test maneuvers in a simulator before flying a real aircraft, chip designers use gem5 to test processor designs before spending millions on silicon fabrication. The simulator models every tick of the clock, every Cache Hierarchy | gem5 Wiki" href="mem_doc/cache/index.html">cache miss, and every branch misprediction with enough fidelity to predict real hardware performance.

How CPU & Memory Connect

The CPU and memory modules communicate through gem5's port-based interface. Every CPU core has instruction and data cache ports that connect to the cache hierarchy. On a cache miss, requests flow down through L1, L2, L3 caches to DRAM controllers or Ruby coherence network.

sequenceDiagram
    participant CPU as CPU Core (O3/Minor)
    participant ICACHE as L1-ICache
    participant DCACHE as L1-DCache
    participant L2 as L2 Cache
    participant BUS as Memory Bus
    participant DRAM as DRAM Controller
    CPU->>ICACHE: Fetch request (PC)
    ICACHE-->>CPU: Hit - return instruction
    CPU->>DCACHE: Load/Store (vaddr)
    Note over CPU,DCACHE: TLB translates vaddr to paddr
    DCACHE->>DCACHE: Tag lookup
    DCACHE-->>CPU: Hit - return data (1-3 cycles)
    DCACHE->>L2: Miss - forward request
    L2->>L2: Tag lookup
    L2-->>DCACHE: Hit - fill line (10-20 cycles)
    L2->>BUS: Miss - send to memory bus
    BUS->>DRAM: DRAM read command
    DRAM-->>BUS: Data response (50-200 cycles)
    BUS-->>L2: Fill response
    L2-->>DCACHE: Fill line
    DCACHE-->>CPU: Data ready
Key insight: CPU models own the pipeline (fetch, decode, execute, commit). The memory module owns everything below the CPU's cache ports — caches, buses, DRAM controllers, and coherence. The Port interface in mem/port.hh is the boundary: CPU sends Packet objects through RequestPort, memory responds through ResponsePort.
