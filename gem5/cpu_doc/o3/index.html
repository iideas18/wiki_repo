o3 — Out-of-Order Superscalar Pipeline

The O3 CPU model is gem5’s most detailed processor model, implementing a superscalar out-of-order pipeline with support for Simultaneous Multi-Threading (SMT). It models a 5-stage pipeline — Fetch, Decode, Rename, Issue/Execute/Writeback (IEW), and Commit — connected through TimeBuffer communication channels, with a Reorder Buffer (ROB) maintaining program order for precise exceptions.

⚙ 5-Stage Pipeline 🔨 Register Renaming 🚀 SMT Support 🎯 Speculative Execution

📚 What is this module?

The o3/ directory implements a detailed out-of-order superscalar CPU that models the behavior of modern high-performance processors like AArch32, AArch64, TrustZone security extensions, SVE/SVE2 vector processing, PMU, and hardware transactional memory." href="../../arch_doc/arm/index.html">ARM Cortex-A76 or Intel Skylake. Instructions can be fetched, decoded, and dispatched out of program order, then executed as soon as their operands are ready, and finally retired in strict program order through the ROB.

💡 Real-world analogy: Airport Security

Think of the O3 pipeline like airport security with multiple parallel lanes. Fetch is the check-in counter handing out boarding passes (instructions) in order. Decode is the document checker verifying each passport. Rename assigns each passenger to an available screening lane (physical register), regardless of their ticket number. IEW is the actual security screening — passengers go through whichever lane is free first, so a passenger with just a backpack (Atomic and Timing Simple CPUs — gem5 Wiki" href="../simple/index.html">simple ALU op) finishes before someone with three suitcases (memory load), even if they arrived later. Commit is the departure gate — passengers must board the plane in their original ticket order, no matter when they cleared security. If security finds a problem (branch misprediction), everyone behind that point is sent back to check-in (squash).

Class Architecture

The O3 CPU model is organized around a central o3::CPU class that owns all five pipeline stages and the communication buffers between them. Each stage is a separate C++ class that implements tick() logic called every cycle by the CPU.

Deep-Dive Topics

Register Renaming

How RenameMap and FreeList eliminate WAR/WAW hazards by mapping architectural registers to a larger physical register file. The rename history buffer enables rollback on squash.

Instruction Queue & Issue Logic

The InstructionQueue dependency graph tracks which instructions are waiting on which physical registers. When a writeback arrives, the IQ wakes all dependents, enabling back-to-back scheduling.

Load/Store Queue & Memory Ordering

The LSQ/LSQUnit manages speculative loads, store-to-load forwarding, and memory ordering violations. The MemDepUnit with StoreSet predictor reduces unnecessary serialization.

Squash & Recovery

When a misprediction is detected at Commit, a squash signal propagates backward through all stages. Each stage removes younger instructions, the RenameMap is restored from the history buffer, and Fetch restarts at the correct PC.

SMT Scheduling Policies

O3 supports multiple SMT policies for each pipeline stage: RoundRobin, IQCount (prioritize thread with fewer IQ entries), Oldest (prioritize oldest instruction), and Branch (prioritize thread with fewer unresolved branches).

TimeBuffer Communication

TimeBuffer<T> in cpu/timebuf.hh models pipeline register latency. Each buffer has configurable forward/backward delay slots, allowing stages to communicate with realistic timing.

Code Example: O3 Fetch Stage Tick

// Simplified view of Fetch::tick() from o3/fetch.cc
void Fetch::tick()
{
    // Select thread to fetch from (SMT policy)
    ThreadID tid = getFetchingThread();
    if (tid == InvalidThreadID) return;

    // Consult branch predictor for fetch direction
    const auto &pred = branchPred->predict(fetchPC[tid]);

    // Send ICache request
    icachePort.sendTimingReq(createFetchReq(fetchPC[tid]));

    // On cache response: decode instructions, create DynInsts
    for (int i = 0; i < fetchWidth; ++i) {
        auto inst = buildInst(tid, fetchPC[tid]);
        fetchQueue[tid].push(inst);
        if (inst->isControl()) {
            // Update fetch PC based on prediction
            fetchPC[tid] = pred.target;
            break;
        }
        advancePC(fetchPC[tid]);
    }
}

Code Example: Register Rename

// Simplified view of Rename::rename() from o3/rename.cc
void Rename::rename(DynInstPtr &inst)
{
    // For each source operand: look up current mapping
    for (auto &src : inst->srcRegs()) {
        PhysRegIdPtr phys = renameMap->lookup(src.archReg());
        inst->renameSrcReg(src.index(), phys);
    }

    // For each destination: allocate new physical register
    for (auto &dst : inst->destRegs()) {
        PhysRegIdPtr newReg = freeList->getReg(dst.classValue());
        PhysRegIdPtr oldReg = renameMap->lookup(dst.archReg());
        renameMap->setEntry(dst.archReg(), newReg);
        inst->renameDestReg(dst.index(), newReg, oldReg);
        // Record history for squash recovery
        renameHistory.push({dst.archReg(), newReg, oldReg});
    }
}
