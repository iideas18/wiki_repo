⚙ One-at-a-Time 🔨 Atomic Memory 🚀 Timing Memory 🎯 Fastest Simulation

📚 What is this module?

The simple/ directory provides CPU models that execute instructions one at a time in a simple fetch–execute loop with no pipeline stages. These are not designed to model real processor microarchitecture but instead to provide functional correctness at maximum simulation speed. They are typically used for fast-forwarding to a region of interest (then switching to O3/Minor), for warming up caches, or for studies where only the memory system matters and CPU pipeline detail is irrelevant.

💡 Real-world analogy: Calculator vs Computer

If the O3 CPU is a modern multi-lane superscalar processor and Minor is a simple pipelined processor, then the Simple CPUs are like a basic calculator. You enter one calculation at a time, get the result, then enter the next one. AtomicSimpleCPU is like a calculator with instant memory — press the button and the answer appears immediately (no cache delay). TimingSimpleCPU is like a calculator connected to a filing cabinet — it still does one calculation at a time, but it has to wait for the filing cabinet (cache/memory) to deliver the data before proceeding. This makes Timing useful for studying how memory latency affects program execution.

CPU Variants

AtomicSimpleCPU

AtomicSimpleCPU (simple/atomic.hh) is the fastest CPU model in gem5. It uses atomic memory accesses — each load or store completes instantaneously in a single function call, returning the access latency as a value that the CPU uses to advance the simulation clock. No cache timing ports are used; instead, the CPU calls sendAtomic() which bypasses the normal cache request/response protocol.

This makes AtomicSimpleCPU ideal for:

  • Fast-forwarding billions of instructions to reach a region of interest
  • Functional validation of ISA implementations
  • Boot-up phases in full-system simulation before switching to a detailed model
  • SimPoint checkpoint generation

TimingSimpleCPU

TimingSimpleCPU (simple/timing.hh) uses timing memory accesses through standard cache request/response ports. Each memory operation sends a timing request to the L1 cache and must wait for the response callback before the instruction can complete. This models realistic cache hit/miss latencies while keeping the CPU model itself minimal.

Use TimingSimpleCPU when you need:

  • Memory system studies where pipeline detail is irrelevant
  • A simple CPU to drive cache/DRAM timing simulations
  • Baseline performance numbers with realistic memory timing

NonCachingSimpleCPU

NonCachingSimpleCPU (simple/noncaching.hh) extends AtomicSimpleCPU by connecting directly to the memory bus without any caches. Every memory access goes straight to main memory. This is used for minimal configurations and testing.

Execution Loop

Both Atomic and Timing share the same basic execution loop defined in BaseSimpleCPU:

flowchart TD
    START["tick()"] --> PREFETCH["preExecute()\nFetch instruction at PC"]
    PREFETCH --> DECODE["Decode: create StaticInst"]
    DECODE --> EXEC["Execute: call StaticInst::execute()\nvia SimpleExecContext"]
    EXEC --> MEM{"Memory\ninstruction?"}
    MEM -->|"Yes, Atomic"| AMEM["sendAtomic()\nInstant response + latency"]
    MEM -->|"Yes, Timing"| TMEM["sendTimingReq()\nWait for callback"]
    MEM -->|"No"| POST["postExecute()\nUpdate PC, stats"]
    AMEM --> POST
    TMEM --> WAIT["Suspend until\nrecvTimingResp()"]
    WAIT --> POST
    POST --> ADVANCE["advancePC()\nSchedule next tick()"]
    ADVANCE --> START

Code Example: AtomicSimpleCPU Tick

// Simplified view of AtomicSimpleCPU::tick() from simple/atomic.cc
void AtomicSimpleCPU::tick()
{
    SimpleExecContext &t_info = *threadInfo[curThread];
    SimpleThread *thread = t_info.thread;

    // Fetch: read instruction bytes at current PC
    Tick icache_latency = fetchInstMem();

    // Decode: create StaticInst from fetched bytes
    preExecute();

    // Execute: call StaticInst::execute()
    Fault fault = curStaticInst->execute(&t_info, traceData);

    // Memory ops use sendAtomic() — completes instantly
    // returning access latency for clock advancement

    postExecute();

    // Advance simulation clock by the greater of
    // instruction latency and memory latency
    Tick stall_ticks = 0;
    if (simulate_data_stalls)
        stall_ticks = t_info.dcache_latency;

    advanceInst(stall_ticks + icache_latency);
}

Code Example: TimingSimpleCPU Memory Response

// Simplified view of TimingSimpleCPU::completeDataAccess()
bool TimingSimpleCPU::DcachePort::recvTimingResp(PacketPtr pkt)
{
    // Called by cache when load/store response arrives
    cpu->completeDataAccess(pkt);
    return true;
}

void TimingSimpleCPU::completeDataAccess(PacketPtr pkt)
{
    SimpleExecContext &t_info = *threadInfo[curThread];

    // Complete the memory operation
    t_info.thread->setMem(pkt);

    // Resume execution: finish instruction, advance PC
    postExecute();
    advanceInst(Tick(1));

    // Schedule next tick — CPU was suspended until now
    schedule(tickEvent, curTick() + cyclesToTicks(Cycles(1)));
}

CPU Model Switching

A common gem5 pattern is to use AtomicSimpleCPU for fast-forward, then switch to O3CPU for detailed simulation:

Typical workflow: Boot the OS with AtomicSimpleCPU (fast), take a checkpoint, then restore with O3CPU for detailed analysis. The switchOut() and takeOverFrom() methods in BaseCPU transfer thread state between models seamlessly.
