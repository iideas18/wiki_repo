cpu — CPU Timing Models

The cpu/ module implements gem5's suite of processor timing models, ranging from Atomic and Timing Simple CPUs — gem5 Wiki" href="simple/index.html">simple functional CPUs (AtomicSimpleCPU) to a detailed superscalar out-of-order pipeline (O3CPU). All models inherit from BaseCPU, which provides a unified interface for interrupt handling, thread contexts, memory port connections, and statistics collection.

CPU Class Hierarchy

All CPU models in gem5 derive from BaseCPU (defined in cpu/base.hh), which is itself a ClockedObject. This hierarchy allows the simulation framework to treat all CPU models uniformly for configuration, checkpointing, and statistics, while each model implements its own pipeline timing.

O3 Pipeline Data Flow

The O3CPU implements a classic superscalar out-of-order pipeline with five major stages connected via TimeBuffer structs. Instructions flow front-to-back through the pipeline, while squash signals propagate back-to-front from Commit.

sequenceDiagram
    participant BP as BPredUnit
    participant FE as Fetch
    participant DE as Decode
    participant RN as Rename
    participant IEW as IEW
    participant ROB as ROB
    participant CM as Commit

    FE->>BP: predict(PC)
    BP-->>FE: target + taken/not-taken
    FE->>DE: fetchQueue (DynInst bundle)
    DE->>DE: check branch targets, expand macros
    DE->>RN: decodeQueue (decoded insts)
    RN->>RN: map arch regs → phys regs (RenameMap)
    RN->>IEW: renameQueue (renamed insts)
    RN->>ROB: allocate ROB entry
    IEW->>IEW: dispatch to IQ / LSQ
    IEW->>IEW: issue ready insts to FUs
    IEW->>IEW: execute + writeback
    IEW->>CM: iewQueue (completed insts)
    CM->>ROB: retire head instructions in order
    CM->>RN: free old phys regs (FreeList)
    Note over CM,FE: On misprediction: squash signal propagates back
    CM-->>FE: squash(seqNum, correctPC)

Narrated Walkthrough: ADD Instruction Through O3

Follow a single ADD x1, x2, x3 instruction from fetch to retirement through the O3 pipeline:

  1. Cycle 1 — Fetch request: The Fetch stage (o3/fetch.hh) sends the current PC to the ICache port. The branch predictor (pred/bpred_unit.hh) is consulted; since ADD is not a branch, prediction is “not taken” and next PC = PC+4.
  2. Cycle 2 — ICache response: The Cache Hierarchy | gem5 Wiki" href="../mem_doc/cache/index.html">cache line arrives. The instruction decoder extracts the ADD machine instruction from the cache line and creates a StaticInst object.
  3. Cycle 3 — DynInst creation: Fetch wraps the StaticInst in a DynInst (o3/dyn_inst.hh) which carries dynamic state: sequence number, PC, thread ID, and physical register mappings. The DynInst is placed in the fetch-to-decode TimeBuffer.
  4. Cycle 4 — Decode: The Decode stage (o3/decode.hh) validates the instruction, checks for PC-relative branches, and passes the DynInst to the decode-to-rename buffer.
  5. Cycle 5 — Rename: The Rename stage (o3/rename.hh) reads the RenameMap (o3/rename_map.hh) to translate architectural registers (x1, x2, x3) to physical registers. It allocates a new physical register for the destination (x1) from the FreeList (o3/free_list.hh) and records the old mapping for later freeing. A ROB entry is allocated.
  6. Cycle 6 — Dispatch: The IEW stage (o3/iew.hh) receives the renamed instruction and dispatches it to the InstructionQueue (o3/inst_queue.hh). Since ADD is not a memory operation, it skips the LSQ.
  7. Cycle 7 — Issue: The IQ checks operand readiness via the Scoreboard (o3/scoreboard.hh). Once x2 and x3’s physical registers are marked ready, the ADD is issued to an integer ALU functional unit.
  8. Cycle 8 — Execute: The ALU computes x2 + x3. The result is written to the destination physical register. The Scoreboard marks the destination as ready, waking up any dependent instructions.
  9. Cycle 9 — Writeback: The IEW stage signals completion through the iew-to-commit TimeBuffer. The DynInst is marked as “completed” in the ROB.
  10. Cycle 10 — Commit check: The Commit stage (o3/commit.hh) examines the head of the ROB (o3/rob.hh). If the ADD is at the head and is marked completed, it is ready to retire.
  11. Cycle 11 — Retire: Commit retires the ADD: the old physical register mapping is freed back to the FreeList, the ROB entry is deallocated, and the architectural commit map is updated.
  12. Cycle 12 — Stats update: The committed instruction counter increments. If this was the last instruction, the CPU may signal completion to the simulation framework.

Sub-Module Overview

Pipeline — gem5 Wiki" href="o3/index.html" class="module-card">

o3

Out-of-Order Superscalar Pipeline

Full superscalar OOO CPU: Fetch → Decode → Rename → IEW → Commit with ROB, IQ, LSQ, register renaming, and SMT support. The most detailed and widely-used CPU model in gem5.

48 files20K LOC5 pipeline stagesSMT

minor

In-Order Pipelined CPU

Four-stage in-order pipeline: Fetch1 → Fetch2 → Decode → Execute. Uses a configurable pipeline with buffered inter-stage communication and scoreboard-based hazard detection.

26 files8K LOC4 stagesScoreboard

simple

Atomic and Timing Simple CPUs

One-instruction-at-a-time models. AtomicSimpleCPU uses instant memory access for fast functional simulation. TimingSimpleCPU models cache port timing for basic memory system studies.

18 files4K LOC2 variantsFastest sim

pred

Branch Prediction

Modular branch prediction framework: BTB, conditional predictors (2-bit local, tournament, bi-mode, gshare, TAGE, perceptron), indirect branch predictor, and Return Address Stack.

42 files12K LOC8+ algorithmsTAGE-SC-L

Other Sub-Modules

kvm

KVM-based hardware-accelerated CPU. Delegates instruction execution to the host CPU via Linux KVM for near-native speed during fast-forward simulation phases.

checker

Functional checker CPU that runs alongside OOO models, independently executing each instruction to validate correctness of speculative and reordered execution.

trace

Trace replay CPU that reads pre-recorded elastic dependency traces, generating memory access patterns for memory system research without simulating a full pipeline.

testers

Memory system test generators: memtest for stress testing, rubytest for Ruby coherence protocol verification, traffic_gen for synthetic traffic patterns.

probes

CPU probe points for performance monitoring: instruction tracking, PC-based event counting, and SimPoint/LoopPoint profiling for sampling methodologies.

Example: Configuring an O3 CPU in Python

// gem5 Python configuration (m5 style)
import m5
from m5.objects import *

system = System()
system.cpu = O3CPU()
system.cpu.fetchWidth = 4
system.cpu.decodeWidth = 4
system.cpu.numROBEntries = 192
system.cpu.numIQEntries = 64
system.cpu.branchPred = TournamentBP()
