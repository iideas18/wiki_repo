minor — In-Order Pipelined CPU

MinorCPU is gem5’s in-order pipelined processor model with four fixed pipeline stages: Fetch1, Fetch2, Decode, and Execute. It provides a balance between simulation speed and timing accuracy, making it ideal for studying in-order processor designs such as AArch32, AArch64, TrustZone security extensions, SVE/SVE2 vector processing, PMU, and hardware transactional memory." href="../../arch_doc/arm/index.html">ARM Cortex-A5/A7 class cores, embedded processors, and pipeline hazard behavior.

⚙ 4-Stage Pipeline 🔨 Scoreboard Hazards 🚀 Configurable FUs 🎯 In-Order Execution

📚 What is this module?

The minor/ directory implements an in-order CPU where instructions flow through the pipeline strictly in program order. Unlike the O3 model, Minor does not reorder instructions — if an instruction stalls (e.g., waiting for a Cache Hierarchy | gem5 Wiki" href="../../mem_doc/cache/index.html">cache miss), all subsequent instructions are blocked behind it. This accurately models simpler processor designs where hardware complexity is traded for power efficiency.

💡 Real-world analogy: Assembly Line

Think of MinorCPU like a factory assembly line with four stations. Each product (instruction) moves from station 1 (Fetch1: get raw materials from warehouse) to station 2 (Fetch2: cut materials to size) to station 3 (Decode: read the blueprint) to station 4 (Execute: assemble the product). Products move through strictly in order — if station 4 is slow on one product (e.g., a cache miss takes extra time), all products behind it on the line must wait. The Scoreboard acts like a foreman checking whether the tools (register values) needed at each station are ready before letting work proceed.

Pipeline Architecture

The MinorCPU pipeline is contained in the Pipeline class (minor/pipeline.hh), which owns the four stages and the MinorBuffer FIFO queues between them. The MinorCPU class (minor/cpu.hh) inherits from BaseCPU and owns the Pipeline instance, the activity recorder, and per-thread state.

Pipeline Stages in Detail

Fetch1 — Line Fetch

Fetch1 (minor/fetch1.hh) is responsible for fetching raw cache lines from the instruction cache. It generates fetch requests based on the current PC, handles ITLB misses by initiating page walks, and manages the fetch buffer. When the branch predictor redirects the PC, Fetch1 discards in-flight fetch requests and starts fetching from the new target.

Fetch2 — Line Decomposition

Fetch2 (minor/fetch2.hh) takes the raw cache line bytes from Fetch1 and uses the ISA decoder to decompose them into individual MinorDynInst objects. It handles variable-length instruction sets (like x86) by tracking the decode position within the line. Branch prediction also happens here — Fetch2 consults the branch predictor for each control-flow instruction and updates the fetch PC accordingly.

Decode — Micro-op Expansion

Decode (minor/decode.hh) expands macro-ops into micro-ops for ISAs that require it (e.g., x86 complex instructions). For RISC ISAs like ARM or RISC-V where most instructions are already single micro-ops, this stage is largely a pass-through. The decode stage also classifies instructions by type for the Execute stage.

Execute — Scoreboard & Functional Units

Execute (minor/execute.hh) is the most complex stage. It performs hazard checking using the Scoreboard, dispatches instructions to FuncUnit pipelines, handles memory operations through the LSQ, and manages instruction completion. The Execute stage stalls the pipeline when a data hazard is detected (read-after-write on a register not yet produced) or when a structural hazard occurs (no available functional unit).

Pipeline Hazards

MinorCPU handles three types of hazards through stalling and forwarding:

Hazard TypeDetectionResolution
RAW (Read After Write)Scoreboard check in Execute: source register not yet marked readyStall pipeline until producing instruction completes and marks the register ready
StructuralNo available FuncUnit for the instruction’s opclassStall until a functional unit becomes free
ControlBranch misprediction detected at ExecuteFlush younger instructions from all stages, redirect Fetch1 to correct target
Memory stallDCache miss or DTLB missBlock Execute stage (and all upstream stages) until memory response arrives
Key difference from O3: MinorCPU does not rename registers or reorder instructions. WAR and WAW hazards cannot occur because instructions execute strictly in program order. Only RAW, structural, and control hazards need handling.

Code Example: Execute Stage Evaluate

// Simplified view of Execute::evaluate() from minor/execute.cc
void Execute::evaluate()
{
    // Try to commit completed instructions at head of pipeline
    for (int i = 0; i < commitLimit; ++i) {
        MinorDynInstPtr inst = getInput();
        if (!inst) break;

        // Check scoreboard for RAW hazards
        if (!scoreboard.canInstIssue(inst)) {
            // Stall: source operand not ready
            break;
        }

        // Find available functional unit
        FuncUnit *fu = findFuncUnit(inst->staticInst->opClass());
        if (!fu || fu->isBusy()) {
            // Structural hazard: no FU available
            break;
        }

        // Dispatch to functional unit
        fu->issue(inst);

        // For memory ops, send to LSQ
        if (inst->isMemRef()) {
            lsq.pushRequest(inst);
        }
    }

    // Process FU completions and mark registers ready
    for (auto &fu : funcUnits) {
        if (auto inst = fu->getCompletedInst()) {
            scoreboard.markRegReady(inst->destReg());
        }
    }
}
