sim — Simulation Engine

The discrete-event simulation core that drives gem5's timing model, managing object lifecycles, event scheduling, and system-level coordination.

💡 Think of it like…

The sim module is like the engine of a car. While other modules (CPU, memory, caches) are the wheels, seats, and body, the sim module provides the crankshaft (EventQueue), the chassis (SimObject hierarchy), and the control computer (System) that makes everything run together in lockstep.

Architecture Overview

The sim module forms the foundation of gem5's discrete-event simulation framework. It provides three pillars: SimObject — the universal base class for all simulated components, EventQueue — the priority-driven scheduling engine, and System — the top-level container binding CPUs, memory, and workloads together.

SimObject Hierarchy

Every component in gem5 — CPUs, caches, buses, memories — inherits from SimObject. This base class provides a uniform interface for construction (via Python-generated Params), initialization, serialization (checkpointing), and statistics registration.

SimObject Lifecycle

SimObjects follow a strict initialization protocol:

  1. Construction — Python creates Params structs, C++ constructors receive them
  2. init() — Post-construction setup, resolve cross-object references
  3. regStats() — Register statistics counters
  4. regProbePoints() — Register probe points for instrumentation
  5. startup() — Schedule initial events, final setup
class SimObject : public EventManager, public Serializable, public Drainable, public statistics::Group
{
  public:
    typedef SimObjectParams Params;
    const Params &params() const;

    SimObject(const Params &p);
    virtual ~SimObject();

    virtual void init();
    virtual void startup();
    virtual void regStats();
    virtual void regProbePoints();
    virtual void regProbeListeners();

    // Serialization for checkpointing
    void serializeSection(CheckpointOut &cp, const char *name) const;
    void unserializeSection(CheckpointIn &cp, const char *name);

    // Find SimObject by name
    static SimObject *find(const char *name);
};

ClockedObject

ClockedObject extends SimObject with clock domain awareness. It associates each object with a ClockDomain, enabling cycle-accurate timing. Components use clockEdge() to align operations to clock boundaries and cyclesToTicks() for time conversion.

class ClockedObject : public SimObject
{
    ClockDomain &clockDomain;
    Tick tick;
    Cycles cycle;

  public:
    Tick clockEdge(Cycles cycles = Cycles(0)) const;
    Tick cyclesToTicks(Cycles c) const;
    Tick clockPeriod() const;
    double voltage() const;
    Cycles ticksToCycles(Tick t) const;
    PowerState *powerState;
};

Event System

gem5 uses a discrete-event simulation model where the EventQueue maintains a time-ordered queue of Event objects. The simulation loop repeatedly dequeues the earliest event, advances simulation time, and invokes the event's process() method.

sequenceDiagram
    participant Main as simulate()
    participant EQ as EventQueue
    participant Ev as Event
    participant Obj as SimObject

    Main->>EQ: serviceOne()
    EQ->>EQ: dequeue head event
    EQ->>Ev: process()
    Ev->>Obj: execute action
    Obj->>EQ: schedule(newEvent, when)
    EQ->>EQ: insert sorted by time+priority
    Main->>EQ: serviceOne() [next iteration]

System and Workloads

The System class is the top-level container that binds all components together. It manages the physical memory address map, tracks all CPUs, provides access to the workload, and coordinates full-system vs. syscall-emulation modes.

Workload Hierarchy

The workload abstraction decouples the simulated system from the software being run:

  • Workload — Abstract base managing object files, symbol tables, entry points
  • KernelWorkload — Loads kernel images for full-system simulation, handles kernel symbols and command lines
  • SEWorkload — Manages syscall-emulation processes, maps system calls to host OS

Process & Syscall Emulation

The Process class models a user-space process in syscall emulation (SE) mode. It provides virtual memory (MemState), file descriptor tracking (FDArray), and system call dispatching without requiring a full OS kernel.

class Process : public SimObject
{
  public:
    System *system;
    std::shared_ptr<MemState> memState;
    std::shared_ptr<FDArray> fds;

    Addr brk_point;      // Current brk() address
    Addr stack_base;     // Stack base address
    Addr mmap_end;       // mmap region boundary

    ObjectFile *objFile; // Loaded binary
    SymbolTable *symtab; // Symbol table

    virtual void initState();
    virtual void syscall(ThreadContext *tc);

    // VMA management
    void allocateMem(Addr vaddr, int64_t size, bool clobber = false);
    bool mmapGrowsDown() const;
};

Simulation Control

The simulate() function is the main simulation loop entry point. It processes events from the EventQueue until a simulation exit event fires or the maximum tick count is reached.

// Core simulation entry — returns when exit event is triggered
GlobalSimLoopExitEvent *simulate(Tick num_cycles = MaxTick);

// Exit events for terminating simulation
class GlobalSimLoopExitEvent : public GlobalEvent
{
    std::string cause;
    int code;
  public:
    const std::string getCause() const { return cause; }
    int getCode() const { return code; }
};

🔍 Narrated Walkthrough: Simulation Startup & Event Cycle

  1. Python Configuration — User writes a Python script instantiating SimObjects (CPU, Cache Hierarchy | gem5 Wiki" href="../mem_doc/cache/index.html">cache, memory, bus). The Python layer generates Params structs for each.
  2. C++ Construction — m5.instantiate() creates all C++ SimObjects from their Params. Each constructor registers with the global SimObject list.
  3. Initialization Phase — init() called on all objects (resolve ports, connect wires). Then regStats() registers statistics counters.
  4. Startup Phase — startup() called on all objects. CPUs schedule their first tick events. Memory controllers initialize their state machines.
  5. Event Loop — simulate() enters the main loop. Each iteration calls eventq->serviceOne(), which dequeues the earliest event and calls process().
  6. Event Cascade — A CPU tick event might generate a cache access event, which generates a memory request event, creating a chain of events across the simulated timeline.
  7. Exit — When a SimLoopExitEvent fires (e.g., max instructions reached), control returns to Python with the exit cause string.
