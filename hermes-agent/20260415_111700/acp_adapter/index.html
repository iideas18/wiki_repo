acp_adapter — Agent Communication Protocol

Agent Communication Protocol

Exposes Hermes Agent as an ACP-compliant server for interoperability. Provides HTTP/SSE endpoints, permission-based tool access, session management, and event streaming. Enables editors and external tools to communicate with Hermes via the standard Agent Communication Protocol.

🎯 Why This Module Exists

Without the ACP adapter, Hermes Agent would be limited to CLI interactions and its own gateway protocol. Every editor or IDE wanting to integrate Hermes would need to implement a bespoke communication protocol, handle session management, and bridge approval workflows. The ACP (Agent Communication Protocol) is an emerging standard that editors like Cursor and VSCode already support — by implementing it, Hermes becomes instantly compatible with any ACP-aware client. The adapter bridges the gap between Hermes' synchronous, thread-based AIAgent and the async, event-driven world of ACP. It handles session persistence (conversations survive server restarts), permission callbacks (editor UI for approving sensitive operations), tool kind classification (semantic grouping for editor display), and MCP server registration (dynamic tool addition). Without this module, users would lose their conversation history on every restart, and editors would have no way to request approval for dangerous operations like terminal commands.

💡 Real-world analogy

Think of the ACP adapter as a diplomatic embassy. Hermes Agent is a citizen of one country (its own protocol), and editors like Cursor are citizens of another (ACP). The embassy (acp_adapter) translates between the two languages, issues visas (sessions), handles security clearances (permissions), and maintains a record office (SessionDB) so conversations are never lost even if the embassy temporarily closes. The ambassador (HermesACPAgent) knows both protocols fluently and ensures nothing is lost in translation.

🚶 Step-by-Step Narrated Walkthrough

Follow a single editor session from connection through tool execution and permission approval as it flows through the entire acp_adapter pipeline:

  1. Connection — An editor (e.g., Cursor) spawns the Hermes ACP server process. Communication happens over stdio: stdout carries ACP JSON-RPC frames, stderr is reserved for logging to prevent frame corruption.
  2. Protocol Negotiation — The editor sends initialize(). HermesACPAgent detects the active runtime provider (e.g., OpenAI, Anthropic) and returns auth methods, supported capabilities (session load, fork, model switch), and protocol version.
  3. Session Creation — create_session() generates a UUID, creates a fresh AIAgent instance, wraps it in a SessionState dataclass, and persists it to SessionDB (~/.hermes/state.db).
  4. User Message — The editor sends a message() with the user's prompt. The text is extracted from ACP content blocks (TextContentBlock, ImageContentBlock, etc.) via _extract_text().
  5. Agent Execution — AIAgent.run() executes in a ThreadPoolExecutor (4 workers) so the ACP event loop stays responsive. Callback factories (make_message_cb, make_step_cb, make_thinking_cb, make_tool_progress_cb) bridge agent events to ACP notifications.
  6. Tool Execution — When the agent calls a tool, get_tool_kind() classifies it (read, edit, execute, fetch, think, other). The editor receives a ToolCallStart notification with the kind and arguments.
  7. Permission Request — For sensitive operations (terminal commands, file writes), make_approval_callback() sends a request_permission to the editor with three options: Allow Once, Allow Always, or Deny. The editor shows a UI prompt to the user.
  8. Permission Resolution — The callback uses asyncio.run_coroutine_threadsafe() to coordinate between the agent's worker thread and the ACP event loop. A 60-second timeout auto-denies if the editor doesn't respond.
  9. Streaming Updates — As the agent produces output, make_message_cb() streams text chunks to the editor as ACP message notifications. The editor can display them progressively.
  10. Completion — finish_message() signals the end of the agent's response. The full conversation history is persisted to SessionDB. If the editor reconnects later, load_session() restores from DB.

Key Components

HermesACPAgent

The main ACP Agent subclass that implements the full ACP protocol surface: initialize(), create_session(), message(), fork_session(), load_session(), and set_session_model(). Also exposes slash commands (/help, /model, /tools) as pseudo-tools parsed by the agent loop.

class HermesACPAgent(acp.Agent):
    _SLASH_COMMANDS = {
        "help": "Show available commands",
        "model": "Show or change current model",
        "tools": "List available tools",
    }

    async def initialize(self, protocol_version, client_capabilities, client_info, **kwargs):
        provider = detect_provider()
        return InitializeResponse(
            protocol_version=acp.PROTOCOL_VERSION,
            agent_info=Implementation(name="hermes-agent", version=HERMES_VERSION),
            agent_capabilities=AgentCapabilities(load_session=True, ...),
            auth_methods=[AuthMethodAgent(id=provider, ...)] if provider else None,
        )

SessionManager

Thread-safe manager for ACP sessions backed by Hermes AIAgent instances. Sessions are held in-memory for fast access AND persisted to the shared SessionDB so they survive process restarts. Supports session creation, retrieval, restoration from DB, and forking (creating a new session with copied history).

Permission System

Bridges ACP permission requests to Hermes approval callbacks. When the agent needs to execute a sensitive operation, the callback sends three options to the editor: allow_once, allow_always, or deny. Uses asyncio.run_coroutine_threadsafe() to coordinate between the agent's synchronous worker thread and the async ACP event loop.

Event Callbacks

Four callback factories bridge AIAgent events to ACP notifications:

  • make_message_cb() — Streams text chunks as ACP message notifications
  • make_step_cb() — Reports agent step progress (e.g., "Running tool 3 of 5")
  • make_thinking_cb() — Forwards chain-of-thought reasoning to the editor
  • make_tool_progress_cb() — Emits ToolCallStart and ToolCallProgress updates

🔬 Algorithm Spotlight

Thread-to-Async Bridge Pattern

The Problem: AIAgent is synchronous (blocking file I/O, subprocess calls, network requests). ACP is async (event-driven, non-blocking). Callbacks need to cross the thread/async boundary in both directions: agent thread pushing updates to ACP loop, and ACP loop sending permission responses to agent thread.

The Approach: Agent runs in a ThreadPoolExecutor. Outbound callbacks (agent to editor) use asyncio.run_coroutine_threadsafe(coro, loop) to schedule ACP notifications on the main event loop. Inbound responses (editor to agent) use the same mechanism with future.result(timeout=60) to block the agent thread until the editor responds.

Why This Algorithm: The alternative — rewriting AIAgent as async — would require overhauling the entire tool execution pipeline. The bridge pattern keeps both sides in their natural execution model and adds minimal overhead (one coroutine per callback invocation).

Trace through an example

Given: Editor sends message("Delete all log files"). Agent wants to run rm -rf /var/log/*.log.

Step 1: ACP loop receives the message, submits AIAgent.run("Delete all log files") to the thread pool.

Step 2: AIAgent decides to call the terminal tool with rm -rf /var/log/*.log. This triggers the approval callback.

Step 3: The approval callback calls asyncio.run_coroutine_threadsafe(request_permission(...), loop). The agent thread blocks on future.result(timeout=60).

Step 4: The ACP loop sends the permission request to the editor. The editor shows a dialog: "Allow terminal: rm -rf /var/log/*.log?"

Step 5: User clicks "Allow once". The editor sends AllowedOutcome(option_id="allow_once"). The future resolves, returning "once" to the agent thread.

Result: The command executes once. If the agent tries another dangerous command, a new permission request is sent. The 60-second timeout ensures the agent never hangs indefinitely.

⚡ Performance Profile

Hot Paths

The most performance-sensitive code paths in this module:

  • Callback bridge (thread to async): asyncio.run_coroutine_threadsafe() adds ~0.1ms overhead per call. For streaming responses with many chunks, this is the dominant overhead.
  • Session persistence: SQLite write after each message. For long conversations, the serialized history can be 100+ KB. Writes are synchronous but fast (SQLite WAL mode).
  • Permission round-trip: Blocking wait on future.result(). Latency depends entirely on user response time (0-60 seconds). Not optimizable.

Resource Usage

  • Memory: Each session holds an AIAgent instance with full conversation history. Long conversations can consume 10-50 MB per session. Sessions are evicted from memory on server restart (restored lazily from DB).
  • Threads: 4-thread pool for agent execution. 1 main thread for ACP event loop. Total: 5 threads per server process.
  • Disk: SessionDB grows with conversation history. Each message adds ~1-5 KB. No automatic cleanup; users manage via session deletion.

How acp_adapter Connects to Core Agent

The ACP adapter wraps the core AIAgent without modifying it. All tool execution flows through the same model_tools.handle_function_call() pipeline used by the CLI. The adapter adds session persistence, permission bridging, and event streaming on top.

sequenceDiagram
    participant E as Editor
    participant ACP as ACP Adapter
    participant AI as AIAgent
    participant MT as model_tools
    E->>ACP: message(prompt)
    ACP->>AI: run(prompt, approval_callback)
    AI->>MT: handle_function_call(tool, args)
    MT-->>AI: tool result
    AI-->>ACP: response + callbacks
    ACP-->>E: ACP notifications
Key insight: acp_adapter owns the session lifecycle and protocol translation. AIAgent owns tool execution and conversation logic. The boundary is clean: ACP never calls tools directly, and AIAgent never knows about ACP protocol details.
