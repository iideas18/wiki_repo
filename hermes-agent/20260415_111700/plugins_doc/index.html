Plugin System & Memory Backends

Dynamic plugin discovery and loading infrastructure for context engines and memory providers. YAML-manifest-driven architecture with 8 hot-swappable memory backends, from local vector stores to cloud APIs.

🎯 Why This Module Exists

Without the plugins module, every memory backend would need to be hard-coded into the agent’s core initialization path. Adding a new memory provider—say, a knowledge-graph backend or a cloud-hosted vector store—would require modifying the agent entry point, importing heavyweight SDKs unconditionally, and redeploying the entire system. The plugins module decouples what backends exist from which backend is active. It provides a filesystem-based discovery mechanism that scans for plugin.yaml manifests at startup, presents available options to the CLI without importing anything, and only loads the one backend selected in config.yaml. This lazy-loading architecture means the agent starts quickly even when 8 backends are installed, and users can swap memory strategies—from Holographic’s local embeddings to Honcho’s dialectic modeling to Mem0’s external service—with a single config change and zero code modifications. The plugin system also isolates dependency failures: if Honcho’s SDK is missing, that provider shows as “unavailable” but every other backend continues to work. This is essential for a tool that runs across vastly different environments, from GPU-equipped research servers to lightweight CI containers.

💡 Real-world analogy

Think of the plugins module as a universal power strip with interchangeable adapters. The agent is the appliance that needs power (memory), and each backend is a different country’s plug format. The plugin system is the adapter mechanism: it inspects each adapter’s label (the plugin.yaml manifest) to know what’s available, but only clicks in the one adapter you’ve selected. You can swap adapters without rewiring the appliance, and a broken adapter doesn’t prevent the others from working.

Architecture

The plugin system follows a registry + lazy loading pattern. At startup, the discovery layer scans the filesystem for plugin.yaml manifests in each backend directory. Only the backend selected in config.yaml is actually imported via Python’s importlib machinery. This keeps startup fast and avoids pulling in heavyweight SDK dependencies for unused backends.

🚶 Step-by-Step Narrated Walkthrough

Follow a single memory save-and-recall operation as it flows through the entire plugins pipeline:

  1. Agent Startup — AIAgent.__init__() reads config.yaml and finds memory.provider: holographic. It calls load_memory_provider("holographic").
  2. Discovery Scan — discover_memory_providers() walks plugins/memory/, finding 8 subdirectories. For each, it reads plugin.yaml to extract the name, description, and availability flag—without importing any Python code.
  3. Availability Check — The holographic backend’s plugin.yaml declares no external dependencies, so it passes the availability check. Backends like honcho or mem0 would check for API keys in environment variables.
  4. Dynamic Import — importlib.util.spec_from_file_location() creates a module spec for plugins/memory/holographic/__init__.py. The loader registers parent packages in sys.modules first, enabling relative imports within the plugin.
  5. Submodule Registration — Before executing the main module, the loader pre-registers all .py files in the holographic directory (store.py, retrieval.py, holographic.py) so that from .store import MemoryStore works correctly.
  6. Provider Extraction — The loader first tries mod.register(collector)—if the module uses the register pattern, the _ProviderCollector captures the instance. If that fails, it falls back to scanning the module for a MemoryProvider subclass and instantiating it directly.
  7. Instance Ready — The HolographicMemory instance is returned to the agent. It holds a local vector store, an embedding model reference, and retrieval configuration.
  8. Memory Save — During a conversation, the agent calls provider.store("user prefers dark mode", embedding). The holographic backend computes an embedding vector, adds it to the local FAISS-like index, and persists the mapping to disk.
  9. Memory Recall — Later, the agent calls provider.recall("what theme does the user like?"). The holographic backend embeds the query, performs cosine similarity search against the stored vectors, and returns the top-k matches ranked by relevance.
  10. CLI Discovery — Meanwhile, discover_plugin_cli_commands() checks only the active provider’s cli.py. If holographic has CLI commands (e.g., hermes memory list), they’re registered into the main argparse tree. Unused providers’ CLI modules are never imported.

Old plugins use register(ctx) matching the general plugin system; new plugins use direct subclassing. Neither breaks the other.
Single-active pattern Only ONE memory provider active at runtime Multiple concurrent providers, chained providers, priority cascade Agent initialization needs deterministic behavior. Mixing strategies would complicate the API surface and create ambiguity about which backend handles a given query. Config clarity beats flexibility here.
Holographic as local-first default Zero-dependency local vector store as the default backend Cloud-first default (Supermemory), no default Local-first ensures the agent works out of the box without API keys or network access. Users can opt into cloud backends when they need cross-device sync or larger scale.
CLI command scoping Only the active provider’s CLI commands are registered Register all providers’ CLI commands, namespace by provider name Avoids conflicting commands (e.g., two providers both defining memory list). Keeps CLI clean and avoids importing SDKs for unused providers.

Pre-registration prevents ImportError loops when submodules reference each other.

🔬 Algorithm Spotlight

Holographic Vector Similarity Retrieval

The Problem: When the agent needs to recall past interactions, it must find the most semantically relevant memories from potentially thousands of stored entries. Simple keyword matching fails because natural language queries rarely use the same words as stored memories (“what theme does the user like?” vs. “user prefers dark mode”).

The Approach: Holographic converts both stored memories and recall queries into dense embedding vectors using a local embedding model. At recall time, it computes the cosine similarity between the query vector and every stored vector, then returns the top-k results above a configurable similarity threshold. The local vector index is organized for batch retrieval, allowing the agent to fetch related memories in a single pass.

Why This Algorithm: Cosine similarity on dense embeddings captures semantic meaning that keyword search misses. Alternatives like BM25 (term frequency) would fail on paraphrased content. Full-text search with stemming would miss conceptual similarity. The trade-off is memory: each embedding vector requires storage proportional to the model’s hidden dimension (typically 384–768 floats). For a local-first backend, this is acceptable—even 100K memories at 768 dimensions is only ~300 MB.

Trace through an example

Given: 3 stored memories: “user prefers dark mode” (vec A), “last session discussed Python” (vec B), “user’s timezone is PST” (vec C). Query: “what theme does the user like?”

Step 1: Embed the query into vector q. The embedding model maps “theme” and “dark mode” into nearby regions of the vector space.

Step 2: Compute cosine similarity: sim(q, A) = 0.87, sim(q, B) = 0.23, sim(q, C) = 0.31. Memory A scores highest because “theme” and “dark mode” are semantically linked.

Step 3: With min_threshold = 0.5 and top_k = 3, only memory A (0.87) passes. Memories B and C are filtered out.

Result: Returns “user prefers dark mode” with similarity 0.87. A naive keyword search for “theme” would return nothing because no stored memory contains the word “theme.”

⚡ Performance Profile

Hot Paths

The most performance-sensitive code paths in this module:

  • Plugin Discovery: Filesystem walk + YAML parse — O(n) in number of backend directories. Typically < 10ms for 8 backends. This runs once at startup and is intentionally cheap.
  • Dynamic Import: importlib.util.spec_from_file_location() + exec_module() — 50–200ms depending on backend complexity and SDK import time. Only runs for the active provider.
  • Holographic Recall: Embedding computation + vector similarity search — O(d×n) for brute-force where d = embedding dimension, n = stored memories. Dominant cost for large memory stores.
  • CLI Command Discovery: Imports only cli.py (not the full backend SDK) — keeps CLI startup under 100ms even for backends with heavy dependencies.

Resource Usage

  • Memory: Only the active backend’s modules are loaded into memory. Holographic additionally allocates a vector index proportional to stored memories (~300 bytes per memory entry at 768 dimensions). Cloud backends (supermemory, mem0) have minimal local memory footprint.
  • I/O: Discovery reads plugin.yaml files from disk (one per backend, ~100 bytes each). Holographic reads/writes its vector index file on store/recall. Cloud backends make HTTP requests per operation. config.yaml is read once at startup to determine the active provider.

Sub-Modules

🔌 Core Plugin System

Discovery and loading infrastructure shared by all plugin types. Handles filesystem scanning, YAML manifest parsing, importlib-based dynamic loading, and the dual register()/subclass detection pattern.

  • plugins/__init__.py — Top-level orchestrator
  • plugins/context_engine/__init__.py — Context engine interface
  • plugins/memory/__init__.py — Memory provider interface
  • _EngineCollector / _ProviderCollector helpers

💎 holographic/

Local-first vector store memory backend. Embeds memories as dense vectors and retrieves them via cosine similarity. Zero external dependencies—works offline, making it the default backend.

  • holographic.py — Main provider implementation
  • store.py — Vector index persistence
  • retrieval.py — Similarity search engine
  • plugin.yaml — Metadata manifest

🗣 honcho/

Dialectic user modeling via Plastic Labs’ Honcho platform. Builds a dynamic model of user preferences and personality through multi-turn conversation analysis. Requires HONCHO_API_KEY.

  • client.py — Honcho API client
  • session.py — Session lifecycle management
  • cli.py — CLI subcommands (hermes memory honcho ...)
  • plugin.yaml — Availability flags

☁️ Other Backends

Six additional memory backends covering cloud APIs, knowledge graphs, byte-level retrieval, and database storage. Each follows the same plugin.yaml + __init__.py pattern.

  • supermemory/ — Cloud-hosted memory API
  • hindsight/ — Knowledge graph relationships
  • byterover/ — Byte-level retrieval engine
  • openviking/ — Open-source memory backend
  • mem0/ — External memory service
  • retaindb/ — Database-backed persistence

How plugins Connects to the Agent Core

The plugins module sits between the agent’s configuration system and its runtime memory operations. The config system determines which provider to load; the agent core consumes the loaded provider as a tool for store/recall operations.

    Agent->>Backend: store(key, value)
    Backend-->>Agent: OK
    Agent->>Backend: recall(query)
    Backend-->>Agent: top-k memories
Key insight: The plugins module owns discovery and loading. The agent core owns when and what to memorize. The active backend owns how memories are stored and retrieved. These three concerns are cleanly separated by the MemoryProvider interface.
