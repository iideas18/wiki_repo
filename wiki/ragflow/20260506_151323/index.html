🎯 Project Philosophy

When you first look at this codebase, the most striking thing is how much RAGFlow refuses to outsource. Most "RAG products" are 800 lines of Python that calls an embedding API and a chat API. RAGFlow ships its own Chinese-aware tokenizer (in C++ with a DART double-array trie), its own layout-detection and table-structure neural networks (PaddlePaddle/ONNX, in deepdoc/vision/), its own Graph-RAG construction stack with Leiden community detection, and its own agent-canvas DSL with iteration, loops, switches, and a code sandbox. Reading the source feels less like reading a "wrapper" and more like reading a small operating system for retrieval.

Several design principles emerge from the code patterns:

  • Pluggable everywhere it matters. Doc-stores (ES, Infinity, OpenSearch, OceanBase), object-stores (MinIO, S3, Azure, GCS, OSS, OpenDAL, encrypted), LLM providers, parsers, chunkers, agent components — every layer is a registry/factory. RAGFlow is built for the enterprise that already has half a stack.
  • Workers, not threads. The Flask API never blocks on parsing. Heavy work is enqueued in Redis and consumed by rag/svr/task_executor.py. The API stays thin and stateless; ingest scales by adding workers.
  • Domain-first naming. ParserType.PAPER, ParserType.MANUAL, Pipeline, Canvas. Source code reads like documentation — terms map directly to UI concepts, not CS abstractions.
  • Agents and pipelines unified. Pipeline(Graph) in rag/flow/pipeline.py extends agent.canvas.Graph. The same DAG engine runs both user-built agents and system ingest pipelines — a significant bet on a single execution model.
  • Self-contained doc understanding. The biggest differentiator is also the steepest dependency cost. RAGFlow is willing to ship its own ML pipeline because layout-aware chunking is what makes retrieval useful on real-world enterprise PDFs.
  • Python first, Go where it matters. The Python stack owns ML, orchestration, and prompts. The parallel Go service in internal/ exists for high-throughput HTTP and to cgo-bind the C++ tokenizer. Both stacks share the schema; neither is canonical.

The implicit value system you can read in commits and naming: correctness of retrieval > raw latency, deployment optionality > opinionated stack, end-to-end ownership > vendor dependency. The team has clearly chosen to take on more code in exchange for fewer integration risks at runtime.

How the Python and Go Tiers Connect

RAGFlow keeps a parallel Go service. Reading the directory layout, both stacks share the same MySQL schema and the same doc-store; neither is canonical. The Go side handles high-throughput HTTP paths and binds the C++ tokenizer through cgo for performance.

sequenceDiagram
    participant Web as web/ SPA
    participant Py as Python api/ (Flask)
    participant Go as Go internal/ (Gin)
    participant DB as MySQL (shared)
    participant CPP as C++ rag_analyzer
    participant DS as Doc-store (shared)
    Web->>Py: heavy ops (upload, agent run, chat, GraphRAG build)
    Web->>Go: thin reads (search, list, fetch)
    Py->>DB: write tasks, docs, chats
    Go->>DB: read same schema
    Go->>CPP: cgo tokenize_query
    CPP-->>Go: terms + weights
    Go->>DS: search hybrid
    Py->>DS: index + search
    Note over Py,Go: They never call each other directly — coupling is via DB + doc-store
Key insight: The Python tier owns state-changing work (ingest, agent runs, chat sessions). The Go tier specialises in read-heavy paths (search, list). The boundary is shared MySQL + doc-store, not RPC. This means schema migrations must be coordinated, but neither tier becomes a bottleneck for the other.
