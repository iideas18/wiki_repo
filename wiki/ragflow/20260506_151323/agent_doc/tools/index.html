Tool Failure Modes & Recovery Strategies

Tools fail in predictable ways. RAGFlow implements tiered recovery strategies for each failure mode.

Failure Mode Classification

ModeExampleIs Retriable?Recovery Strategy
Transient NetworkConnection timeout, DNS lookup failed, socket reset✓ YesExponential backoff retry; max 5 attempts
Transient ServiceHTTP 503 Service Unavailable, API rate limit (429)✓ YesExponential backoff; may include jitter to avoid thundering herd
Permanent ServiceHTTP 404 Not Found, HTTP 401 Unauthorized, invalid API key✗ NoUse exception_default_value (fallback output) or exception_goto (jump to error handler)
Invalid InputParameter validation failed, malformed request body✗ NoLog error; use exception_default_value or abort
Resource LimitMemory exhausted in code_exec sandbox, query result too large✗ NoUse exception_default_value; increase limits if possible
TimeoutTool execution exceeded timeout duration✓ Yes (maybe)Retry with longer timeout; if still fails, use fallback

Tool Monitoring & Observability

  • Execution time: Each tool execution step in history includes duration_ms. Use to identify bottlenecks (e.g., if tavily searches are taking >5s, investigate network or service latency).
  • Retry counts: If a tool is retrying frequently, log and alert. Could indicate flaky service or misconfigured timeout.
  • Exception patterns: If same tool always fails with same error (e.g., "API key invalid"), fix configuration before next run.
  • Fallback activation: If exception_default_value is used, workflow continues but with degraded data. Monitor for this and adjust strategy if too frequent.

Advanced Tool Patterns & Integration

Beyond basic tool invocation, RAGFlow supports sophisticated patterns for composition, fallbacks, and context passing.

Tool Composition Patterns

  • Sequential Chaining: Output of one tool flows as input to next. Example: retrieval → llm_answer (context-aware). Via variable references (tool_a@result → tool_b@context).
  • Conditional Execution: Tools run only if preconditions met (Switch nodes). Example: run code_exec if code snippet detected, else skip.
  • Fallback Chains: Multiple tools with fallback semantics. web_crawler fails → try api_request; both fail → return error message. Via exception_default_value or exception_goto.
  • Iteration Parallelism: No built-in multi-threading, but Iteration node runs tool N times across list. Each iteration gets isolated sub-DAG; results aggregated.
  • Dynamic Tool Selection: Tool name determined at runtime. Agent component inspects LLM output to pick next tool (ReAct pattern, tool_choice semantics).

Error Handling & Resilience Tiers

TierStrategyWhen to Use
Tier 1: InstantReturn exception_default_value immediately on first failureNon-critical tools; failure is acceptable
Tier 2: Retry with BackoffRetry 3-5 times with exponential backoff (100ms, 200ms, 400ms, 800ms...)Transient failures expected (network glitch, rate limit). Default.
Tier 3: Fallback + PropagateRetry, then try fallback tool, then propagate error to exception handlerCritical path; multiple fallback options (web search → cache → error).
Tier 4: Manual InterventionPause workflow; log for human review; wait for manual tool result injectionHigh-stakes decisions; no good fallback (approve/reject document).

Tool Context & State Management

  • Tool Isolation: Each tool invocation is isolated; no persistent state between calls (unless explicitly managed). Useful for determinism and testability.
  • Context Injection: Tools can receive workflow context via params. Example: retrieval tool gets search_keywords param from LLM reasoning step.
  • Output Caching: Component outputs cached in _outputs[component_id]. Tools that are deterministic (same input → same output) can skip re-execution if node already run.
  • User Context: Some tools (email, api_request) may need user credentials or request ID. Passed via workflow params or global variables (user_id, auth_token, etc.).
