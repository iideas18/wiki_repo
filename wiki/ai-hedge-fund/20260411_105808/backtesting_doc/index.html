Why This Module Exists

Building an AI-driven hedge fund is meaningless if you cannot measure whether its decisions actually make money. The backtesting engine exists to provide a deterministic, reproducible simulation environment that replays every trading day over a historical window, feeding real market data through the exact same agent ensemble used in live mode. This is not a simplified model — the backtester calls run_hedge_fund() directly, ensuring that every analyst signal, every risk check, and every portfolio manager verdict executes identically to production.

Why does this matter? In quantitative finance, simulation drift is one of the deadliest silent failures. If your backtester uses a different code path from your live system — even subtly, like a different order of analyst evaluations or a slightly different rounding rule — your historical P&L numbers become meaningless. You could convince yourself a strategy returns 40% annually when in reality it loses money, simply because the backtest diverged from what live trading actually does. By reusing the live pipeline verbatim, this module makes simulation drift structurally impossible.

The module also validates the interaction between agents under realistic conditions. A fundamental analyst might love a stock while the risk manager vetoes it — the backtester captures these dynamics across hundreds of trading days, building a statistical picture of how well the ensemble cooperates. It tracks long and short positions independently, computes risk-adjusted metrics (Sharpe, Sortino, max drawdown), and benchmarks everything against SPY so that you can distinguish genuine alpha from market beta.

Design Decisions

DecisionChoiceRationale
Reuse run_hedge_fund() Call the live pipeline directly Eliminates simulation drift — backtest and live share identical logic, so any bug found in backtesting is a bug fixed in production too
Daily iteration granularity Loop over pd.bdate_range() business days Matches the investment horizon of the agent ensemble; intraday noise would add complexity without value for multi-day strategies
Component decomposition Separate Engine, Controller, Trader, Portfolio, Metrics, Output Each concern is independently testable; the Trader can be unit-tested without the Engine; Metrics can run on any portfolio snapshot
Data prefetching (1 year) Load all prices, financials, news, insider trades before the loop Avoids redundant API calls during iteration; the lookback window (up to 1 year) is always available without additional fetching
SPY benchmark Fetch SPY alongside ticker data Enables alpha vs. beta decomposition; raw returns are meaningless without a benchmark — a 20% return in a 25% bull market is actually underperformance
Separate long/short tracking Portfolio maintains distinct position maps Short positions have fundamentally different risk characteristics (unlimited loss potential); mixing them with longs would produce misleading metrics
Colorama + tabulate output Formatted terminal tables with color Immediate visual feedback during long backtest runs; operators can spot problems (e.g., sudden drawdowns) without waiting for final results

The architecture follows a pipeline pattern: the BacktestEngine sits at the top, orchestrating data prefetching, daily iteration, and result aggregation. Each day, it delegates to the AgentController which invokes the full agent ensemble via run_hedge_fund(). Trade decisions flow down through TradeExecutor for validation, then into the Portfolio for position tracking. At the end of each day, Valuation marks positions to market, MetricsCalculator computes cumulative risk metrics, and OutputFormatter renders the day's results to the terminal.

Narrated Walkthrough — Running a 3-Month Backtest of AAPL and MSFT

Follow along as we trace the complete lifecycle of a backtest from CLI invocation to final performance report.
User invokes the backtest CLI. The command specifies tickers (AAPL, MSFT), a date range (2026-01-02 to 2026-03-31), and initial capital of $100,000. The CLI parses arguments and instantiates BacktestEngine with these parameters.
Engine initializes the Portfolio. A fresh Portfolio object is created with $100K cash, empty long positions, and empty short positions. The portfolio will track every position change throughout the simulation.
Data prefetching begins. The engine calls _prefetch_data(), which loads one full year of historical data (2025-01-02 to 2026-03-31) for AAPL, MSFT, and SPY. This includes daily prices, financial metrics, relevant news articles, and insider trading records. All data is cached in memory.
Business day range is generated. Using pd.bdate_range(), the engine creates a list of ~62 trading days between January 2 and March 31. Weekends and market holidays are automatically excluded.
The daily loop begins — Day 1 (Jan 2, 2026). The engine slices the prefetched data up to the current date and passes it to AgentController.run_day(). The controller invokes run_hedge_fund() with the current portfolio state and available data.
Agent ensemble deliberates. Each analyst agent (fundamental, technical, sentiment, etc.) evaluates AAPL and MSFT using the historical data visible up to Jan 2. The portfolio manager synthesizes their signals. The risk manager applies position limits. A final list of trade decisions emerges — perhaps "BUY 50 shares AAPL" and "HOLD MSFT."
TradeExecutor validates and executes. For each decision, the executor checks: Does the portfolio have enough cash? Is the order size within limits? Is the price data available for this date? If validation passes, the trade is applied to the Portfolio — 50 shares of AAPL are added to long positions, and cash is reduced by 50 × closing_price.
Valuation marks positions to market. At the end of Day 1, the Valuation module calculates the total portfolio value: remaining cash + sum of (shares × closing price) for all long positions − sum of (shares × closing price) for all short positions. Unrealized P&L is computed against entry prices.
Metrics are updated. The PerformanceMetricsCalculator records the day's portfolio value, computes the daily return, and updates running calculations for Sharpe ratio, Sortino ratio, and maximum drawdown. SPY's daily return is also recorded for benchmark comparison.
Output is rendered. The OutputFormatter prints a colorized table row showing the date, actions taken, portfolio value, daily return, and cumulative metrics. Green for gains, red for losses — operators can watch the backtest progress in real time.
Days 2–62 repeat the cycle. Each subsequent trading day follows the same pattern. The agent ensemble sees one more day of data each iteration, potentially changing its view on AAPL and MSFT. Positions accumulate, short sales may be initiated, and the portfolio evolves.
A drawdown event occurs (mid-February). AAPL drops 8% over three days. The risk manager triggers a position reduction. The TradeExecutor sells 20 shares. The max drawdown metric updates from −2.1% to −5.3%. The output row turns red.
The loop completes — final day (Mar 31, 2026). After processing the last trading day, the engine exits the loop and moves to the summary phase.
Final performance report is generated. The engine calls OutputFormatter.render_summary(), which produces a comprehensive table: total return vs. SPY, annualized Sharpe and Sortino ratios, maximum drawdown, win rate (% of profitable days), and a per-ticker breakdown of realized and unrealized P&L.

Algorithm Spotlight

1. Sharpe Ratio Calculation

The Sharpe ratio measures risk-adjusted return — how much excess return you earn per unit of volatility. The backtester computes it using daily returns:

def compute_sharpe(daily_returns: list[float], risk_free_rate: float = 0.04) -> float:
    """Annualized Sharpe ratio from daily returns."""
    daily_rf = (1 + risk_free_rate) ** (1/252) - 1
    excess = [r - daily_rf for r in daily_returns]
    if len(excess) < 2:
        return 0.0
    mean_excess = sum(excess) / len(excess)
    std_excess = (sum((x - mean_excess)**2 for x in excess) / (len(excess) - 1)) ** 0.5
    if std_excess == 0:
        return 0.0
    return (mean_excess / std_excess) * (252 ** 0.5)  # annualize

Key detail: the 252 ** 0.5 annualization factor assumes 252 trading days per year. The risk-free rate is converted to a daily rate for proper excess return computation. A Sharpe above 1.0 is generally considered good; above 2.0 is excellent.

2. Max Drawdown Tracking

Maximum drawdown measures the worst peak-to-trough decline in portfolio value — the "how bad can it get?" metric. It is tracked incrementally:

def track_max_drawdown(portfolio_values: list[float]) -> float:
    """Compute maximum drawdown from a series of portfolio values."""
    peak = portfolio_values[0]
    max_dd = 0.0
    for value in portfolio_values:
        if value > peak:
            peak = value
        drawdown = (peak - value) / peak
        if drawdown > max_dd:
            max_dd = drawdown
    return max_dd  # e.g., 0.15 means 15% max drawdown

The algorithm maintains a running peak. Every time the portfolio value exceeds the previous peak, it resets. When the value drops below the peak, the percentage decline is calculated. The worst such decline across the entire backtest is the max drawdown. This is critical for risk assessment — a strategy with high returns but 50% max drawdown may not survive real deployment because of margin calls or investor panic.

3. Portfolio Valuation with Short Positions

Valuing a portfolio with short positions is subtly different from a long-only portfolio. Short positions subtract from portfolio value as their price increases:

def compute_portfolio_value(cash: float,
                             long_positions: dict[str, Position],
                             short_positions: dict[str, Position],
                             current_prices: dict[str, float]) -> float:
    """Total portfolio value including short position mark-to-market."""
    long_value = sum(
        pos.shares * current_prices[ticker]
        for ticker, pos in long_positions.items()
    )
    # Short P&L: profit when price drops below entry
    short_mtm = sum(
        pos.shares * (pos.entry_price - current_prices[ticker])
        for ticker, pos in short_positions.items()
    )
    return cash + long_value + short_mtm

Notice that short_mtm uses entry_price - current_price: if the stock dropped since entry, this is positive (profit). If it rose, it is negative (loss). The cash balance also reflects the proceeds received when the short was initiated, so the overall accounting stays balanced.

What Could Go Wrong

ScenarioImpactMitigation
Missing price data for a ticker on a given date Trade cannot be valued; portfolio MTM is incorrect TradeExecutor skips trades with no price; Valuation uses last-known price with a warning
Lookback window extends before available data Agents receive truncated history, potentially making poor decisions 1-year prefetch ensures at least 1 year of history is always available for any date in the backtest range
Cash goes negative (over-leveraged trades) Unrealistic simulation — real accounts would get margin called TradeExecutor.validate() rejects any trade that would push cash below zero
Short squeeze (price spikes on shorted stock) Unlimited theoretical loss on short positions Risk manager limits short position size; Portfolio tracks unrealized short losses and can trigger forced covers
Agent ensemble returns no decisions for a day Portfolio remains unchanged — not necessarily an error, but could mask bugs OutputFormatter logs "NO TRADES" for empty days; summary shows total days with/without activity

Performance Profile

Backtest execution time is dominated by agent inference, not by the backtesting framework itself. Typical benchmarks:

MetricValueNotes
Prefetch (2 tickers, 1 year)~3–5 secondsNetwork-bound; cached after first run
Per-day iteration (overhead only)<1 msPortfolio update + metrics are O(n_tickers)
Per-day agent ensemble~2–8 secondsDepends on LLM provider latency and number of analysts
3-month backtest (2 tickers)~5–10 minutes~62 trading days × ~5s/day average
Memory usage~50–100 MBDominated by prefetched DataFrames and news text

The framework itself adds negligible overhead. Optimization efforts should focus on agent execution speed (batching LLM calls, caching repeated analyses) rather than the backtest loop.
