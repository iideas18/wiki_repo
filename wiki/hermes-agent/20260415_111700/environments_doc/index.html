RL Training Environments

Integrates Hermes Agent's tool-calling capabilities with the Atropos RL training framework. Provides a layered abstraction bridging OpenAI-spec tool calling with Atropos dataset rollouts, reward scoring, and training loops. Includes 5 benchmark environments and 11 tool call parsers for different LLM formats.

🎯 Why This Module Exists

Without the environments module, every RL training pipeline would need to implement its own agent loop, tool dispatch, reward verification, and sandbox isolation from scratch. The core Hermes agent (run_agent.py) is designed for interactive CLI use — single query, single session. RL training requires batch rollouts across hundreds of parallel tasks, each with isolated sandboxes, configurable tool distributions, and reward scoring. This module bridges that gap by wrapping the agent's tool-calling engine in Atropos-compatible BaseEnv subclasses. It provides ToolContext for reward verifiers to inspect rollout state (e.g., "did the model actually create that file?"), manages thread pool executors for concurrent tool calls, and abstracts away Phase 1 (OpenAI server) vs Phase 2 (VLLM ManagedServer) differences. The benchmark environments (TerminalBench, TBLite, YCBench, SWE, WebResearch) provide standardized evaluation harnesses, while the 11 tool call parsers handle the diverse output formats of models like Hermes, DeepSeek, Qwen, LLaMA, Mistral, GLM, and Kimi.

💡 Real-world analogy

Think of the environments module as a standardized flight simulator for training pilots. The core agent is the pilot; the environments module provides the simulator cockpit (agent loop), flight scenarios (benchmark environments), scoring rubrics (reward functions), and translator headsets (parsers) so pilots who speak different languages (LLM formats) can all train in the same simulator. Without it, you'd need a separate simulator for each pilot language and each training scenario.

🚶 Step-by-Step Narrated Walkthrough

Follow a single RL training rollout for a TerminalBench task as it flows through the entire environments pipeline:

  1. Rollout Request — Atropos framework calls get_next_item() on the TerminalBench environment, requesting a new task from the dataset.
  2. Dataset Item — The environment returns a dataset item containing a terminal challenge prompt (e.g., "Find all Python files larger than 1MB in /data").
  3. Prompt Formatting — format_prompt() converts the dataset item into an OpenAI-format user message with system prompt and enabled toolsets.
  4. Toolset Sampling — HermesAgentEnvConfig samples the tool distribution for this rollout group. All rollouts in the same group share the same tool configuration for fair comparison.
  5. Agent Loop Start — HermesAgentLoop begins the multi-turn loop, calling the LLM with the tools= parameter listing available tool schemas.
  6. Tool Call Parsing — The appropriate parser (e.g., HermesParser for Hermes models) extracts structured tool calls from the LLM response. Phase 2 mode uses client-side parsing for lower latency.
  7. Tool Execution — Each tool call is dispatched to handle_function_call() in a ThreadPoolExecutor (128 workers). The tool runs in a sandbox scoped to the rollout's task_id.
  8. Loop Continuation — Tool results are appended to the conversation history. The loop continues until max_agent_turns is reached or the model stops calling tools.
  9. AgentResult Capture — The full conversation history, turns used, tool errors, and reasoning per turn are captured atomically in an AgentResult dataclass.
  10. ToolContext Creation — A ToolContext is created for the reward verifier, giving it unrestricted access to all Hermes tools scoped to this rollout's task_id.
  11. Reward Computation — compute_reward() uses the ToolContext to verify the model's work (e.g., run the same command and check output), returning a score from 0.0 to 1.0.
  12. Cleanup and Scoring — Sandbox resources (terminal session, browser profile) are cleaned up in a try-finally block. The ScoredDataGroup is built from ManagedServer state and returned to Atropos for training.

Key Components

HermesAgentLoop

The reusable multi-turn agent engine at the heart of every environment. Runs the tool-calling loop using standard OpenAI-spec tools= parameter, dispatches calls via handle_function_call(), and captures results in AgentResult. Supports both Phase 1 (OpenAI API server) and Phase 2 (VLLM ManagedServer with client-side parsing).

AgentResult

Immutable dataclass capturing the full outcome of an agent loop run:

@dataclass
class AgentResult:
    messages: List[Dict[str, Any]]       # Full conversation history
    managed_state: Optional[Dict] = None # ManagedServer state (Phase 2)
    turns_used: int = 0                  # LLM call count
    finished_naturally: bool = False     # Model stopped vs max_turns
    reasoning_per_turn: List[Optional[str]] = field(default_factory=list)
    tool_errors: List[ToolError] = field(default_factory=list)

ToolContext

Per-rollout handle giving reward functions unrestricted access to ALL Hermes tools (terminal, file, web, browser) scoped to the rollout's task_id. Unlike agent-facing tools which may be restricted by permissions, reward verifiers need full access to inspect the agent's work.

HermesAgentBaseEnv

Abstract BaseEnv subclass for Atropos integration. Orchestrates the agent loop, ToolContext creation, and ScoredDataGroup construction. Concrete environments (TerminalBench, SWE, etc.) extend this base with task-specific reward functions and dataset loading.

🔬 Algorithm Spotlight

Tool Call Parsing Strategy

The Problem: Different LLMs produce tool calls in radically different formats — XML tags, JSON blocks, structured outputs, custom delimiters. The agent loop needs a unified interface.

The Approach: A parser registry maps model identifiers to parser classes. Each parser implements extract_tool_calls(text) -> List[ToolCall]. Phase 2 mode selects the parser at environment init based on model config; Phase 1 relies on the OpenAI API's native parsing.

Why This Algorithm: A single regex-based parser would break on edge cases across 11 formats. Dedicated parsers per model family isolate format-specific logic. The registry pattern keeps the agent loop agnostic to model details.

Trace through an example

Given: A DeepSeek model returns: ```json\n{"name": "terminal", "arguments": {"command": "ls -la"}}\n```

Step 1: Phase 2 mode is active. Parser registry looks up "deepseek" and selects DeepSeekParser.

Step 2: Parser scans for JSON code blocks, extracts the object, validates name and arguments fields.

Step 3: Returns [ToolCall(name="terminal", arguments={"command": "ls -la"})] in the normalized format.

Result: The agent loop dispatches this identically to a Hermes-format tool call, despite the completely different wire format.

⚡ Performance Profile

Hot Paths

The most performance-sensitive code paths in this module:

  • Tool dispatch via ThreadPoolExecutor: O(1) submission, but tool execution time varies from milliseconds (file read) to minutes (terminal commands). The 128-worker pool is sized for high-concurrency benchmarks.
  • Tool call parsing: O(n) per response where n is response length. Dedicated parsers avoid regex backtracking on complex outputs.
  • Reward verification: Variable cost — may involve running test suites, compiling code, or browsing. Scoped by ToolContext to prevent accidental global state access.

Resource Usage

  • Memory: Each rollout holds its AgentResult (full conversation history). For 30-turn rollouts with tool outputs, this can be 1-5 MB per rollout. Freed after scoring.
  • I/O: Heavy terminal and file I/O during tool execution. Sandboxed per task_id. Network I/O for LLM calls (Phase 1) or shared memory for VLLM (Phase 2).
  • Threads: 128-thread pool shared across all environments. resize_tool_pool() allows per-environment tuning.
