gateway — Multi-Platform Messaging Gateway

Multi-Platform Messaging Gateway

The gateway module serves as a unified messaging bridge, enabling autonomous communication across Telegram, Discord, Slack, WhatsApp, Signal, Matrix, Email, SMS, and 10+ other platforms through a single adapter abstraction. It manages persistent session contexts, implements session lifecycle policies, and intelligently routes outputs from scheduled jobs.

🔵 18+ Platforms 🟢 Session Management 🟡 Stream Rendering 🔴 Cron Delivery

🎯 Why This Module Exists

Without the gateway module, every scheduled job, every agent response, and every notification would need its own bespoke integration with each messaging platform. Teams running Hermes across Telegram, Discord, and Slack would maintain three separate codebases with three separate authentication flows, three separate message-formatting pipelines, and three separate session stores. Bug fixes would be multiplied by the number of platforms, and adding a new platform like Signal or Matrix would require changes in every component that ever sends a message.

The gateway solves this by placing a single adapter abstraction between the Hermes agent core and the outside world. Platform adapters translate platform-specific events (Telegram updates, Discord interactions, Slack slash commands) into a normalized InboundMessage envelope and translate outbound AgentResponse objects back into platform-native formats. The session store ensures conversational context persists across messages without leaking between users or platforms. The delivery router decides which adapter receives the output of cron jobs without the scheduler needing to know anything about messaging protocols. This separation means a new platform can be added by implementing a single Python class — roughly 150–300 lines — with zero changes to the agent, scheduler, or plugin system.

💡 Real-world analogy

Think of the gateway as a multilingual hotel concierge desk. Guests arrive speaking different languages (Telegram, Discord, Slack, etc.), but behind the desk every request is logged in the same ledger (session store), routed to the same staff (agent core), and answered in the guest's own language. The concierge doesn't need to understand how the kitchen (plugins) works — they just relay orders and deliver plates. Adding a new language is hiring one new translator, not retraining the entire hotel staff.

🚶 Step-by-Step Narrated Walkthrough

Follow a single Telegram message from a user as it flows through the entire gateway pipeline:

  1. Webhook Arrival — Telegram sends an HTTPS POST to the bot's webhook endpoint. The TelegramAdapter receives the raw JSON payload containing the chat ID, user ID, message text, and any attachments. Latency: ~5 ms to parse.
  2. Envelope Construction — The adapter calls parse_update() to transform the Telegram-specific JSON into a normalized InboundMessage dataclass with fields like platform, user_id, channel_id, text, and attachments. Platform quirks (e.g., Telegram's chat.type field) are abstracted away here.
  3. Dispatch to GatewayRunner — The adapter calls GatewayRunner.dispatch(msg). The runner is the central event loop — it doesn't know or care that this message came from Telegram. The HookRegistry fires on_message_received hooks (logging, rate-limit checks, analytics).
  4. Authorization Check — The runner queries PairingStore.check_authorization(user_id, channel_id). In DM mode, the user must have previously entered a valid pairing code. In group mode, the channel itself is the authorization scope. Unauthorized messages receive a polite rejection and the pipeline short-circuits.
  5. Session Key Construction — The runner builds a composite session key: f"{platform}:{channel_id}:{user_id}" for DMs or f"{platform}:{channel_id}" for group chats. This key determines which conversation history is loaded. The algorithm is deliberately simple to make debugging straightforward.
  6. Session Retrieval & Lifecycle — SessionStore.get_or_create(key) loads the session from disk (JSON files) or creates a fresh one. Before returning it, the store checks lifecycle policies: if the session has been idle longer than idle_timeout_minutes (default: 120) or a new calendar day has started since the last message, the session is auto-reset to prevent context drift. The old session is archived, not deleted.
  7. Agent Invocation — The runner passes the user's message plus the loaded SessionContext (conversation history, system prompt overrides, tool permissions) to the agent engine via agent.invoke(). The agent runs in a subprocess for crash isolation — if the agent segfaults or hangs, only that subprocess dies.
  8. Stream Processing — As the agent produces output tokens, GatewayStreamConsumer receives them in real time. It batches tokens into display-friendly chunks (typically 50–100 tokens) to avoid flooding the platform's API with single-character messages. For platforms that support message editing (Telegram, Discord), it sends an initial message and then edits it in place — giving the user a "typing" effect.
  9. Platform-Native Formatting — The stream consumer calls adapter.send_message(chunk). Each adapter translates the generic Markdown output into platform-native formatting: Telegram uses HTML tags, Discord uses its own Markdown dialect, Slack uses Block Kit JSON, Email uses MIME multipart. Code blocks, images, and links are all platform-adapted.
  10. Session Persistence — After the agent finishes, the runner calls SessionStore.persist(key, updated_context). The updated context includes the new user message, the agent's full response, token counts, and a timestamp. The session file is written atomically (write to temp, then rename) to prevent corruption on crash.
  11. Hook Finalization — The runner fires on_message_complete hooks. These typically handle analytics (response latency, token usage), quota tracking, and optional logging to an external observability service.
  12. Cleanup & Readiness — The adapter's event loop returns to listening for the next Telegram update. Total end-to-end latency for a simple query: 200–800 ms (dominated by LLM inference time). The gateway is immediately ready for the next message on any platform.

🔬 Algorithm Spotlight

Session Key Construction & Message Batching

Session Key Construction

The Problem: The gateway must route incoming messages to the correct conversation context. A user can talk to the bot in a Telegram DM, a Discord server channel, and a Slack thread simultaneously — each must have its own session. But in group chats, all users share a single context.

The Approach: Build a deterministic composite key from three fields: platform, channel_id, and optionally user_id. For DMs, the key is {platform}:{channel_id}:{user_id}. For group chats, the key is {platform}:{channel_id}. The platform prefix prevents collisions when the same numeric channel ID appears on different platforms (Telegram and Discord both use snowflake-like IDs).

Why This Algorithm: It's O(1) to construct, O(1) to look up in a dict, and — critically — human-readable. An operator debugging a session issue can ls sessions/telegram:* to find all Telegram sessions instantly. Hash-based keys (SHA-256 of the inputs) would be collision-free but opaque, requiring a secondary index for debugging.

Message Batching

The Problem: LLM streaming produces tokens one-at-a-time (5–50 ms apart). Sending each token as a separate platform message would trigger rate limits (Telegram: 30 msgs/sec, Discord: 5 msgs/sec) and create a terrible user experience.

The Approach: The GatewayStreamConsumer accumulates tokens in a buffer. It flushes when: (a) the buffer reaches a threshold (50–100 tokens), (b) a natural break point is detected (double newline, code fence boundary), or (c) a time deadline passes (500 ms since last flush). On platforms supporting edit-in-place (Telegram, Discord), it sends one initial message and edits it repeatedly. On send-only platforms (SMS, Email), it waits for the full response.

Why This Algorithm: The multi-trigger flush strategy balances responsiveness against API rate limits. A pure token-count threshold would delay short responses. A pure timer would flush mid-word. The natural-break-point detection ensures chunks end at readable boundaries.

Trace through an example

Given: A Telegram user asks "Explain quicksort." The LLM streams 200 tokens over 3 seconds.

Step 1: Tokens 1–12 arrive in 180 ms: "Quicksort is a". Buffer has 12 tokens, no break point, timer not expired → keep buffering.

Step 2: Token 13 arrives at 200 ms, it's a newline after the first sentence. Natural break detected → flush. adapter.send_message("Quicksort is a divide-and-conquer...") creates message ID 42.

Step 3: Tokens 14–80 arrive over 1.2 seconds. At token 65, a double-newline is detected → flush via adapter.edit_message(42, accumulated_text). The user sees the message grow in real time.

Step 4: Tokens 81–200 continue with periodic flushes at natural breaks and timer deadlines. Final flush on stream-end sends the complete response.

Result: The user sees 4–5 progressive edits to a single message over 3 seconds, instead of either (a) 200 individual messages or (b) a 3-second delay followed by a wall of text.

⚠️ What Could Go Wrong

Platform rate limit exceeded Rapid message edits during streaming; multiple concurrent users on the same adapter HTTP 429 response from platform API; RetryAfter header Exponential backoff with jitter built into each adapter's send_message(). Stream consumer increases batch size dynamically when rate limits are detected. Worst case: user sees a slight delay in streaming updates.
Adapter crash / unhandled exception Platform API breaking change; malformed webhook payload; network partition Subprocess exit with non-zero code; exception caught by GatewayRunner's try/except wrapper Each adapter runs in its own async task. A crash in the Telegram adapter does not affect Discord or Slack. The runner logs the error, fires on_adapter_error hooks, and the adapter automatically restarts on the next incoming event. Sessions are persisted before agent invocation, so no context is lost.
Session file corruption Process kill during session write; disk full; filesystem error JSON parse error on session load; checksum mismatch Sessions are written atomically (write to .tmp, then os.rename()). If the temp file is incomplete, the original session file remains intact. On parse error, the session is reset to empty with a warning logged. Archived sessions provide manual recovery.
SSRF via user-supplied URLs User sends a message containing a URL that the agent attempts to fetch (e.g., via a web-browsing tool) URL validation in the tool layer (not the gateway itself) The gateway does not fetch user-supplied URLs — that responsibility belongs to individual tools, which implement allowlist/denylist filtering. The gateway's role is to pass the message to the agent verbatim. However, the HookRegistry supports on_message_sanitize hooks that can strip or flag suspicious URLs before agent invocation.

Additionally, SessionStore enforces a max_turns limit (default: 200) — older turns are evicted FIFO. The session metadata tracks total token count for monitoring.

⚡ Performance Profile

Hot Paths

The most performance-sensitive code paths in the gateway module:

  • Message Dispatch (GatewayRunner.dispatch): O(1) adapter lookup by platform name, O(1) session key construction, O(1) session dict lookup. Total overhead before agent invocation: <5 ms. This path is hot because every single inbound message traverses it.
  • Stream Consumer Flush (GatewayStreamConsumer.flush): O(n) where n = buffered tokens (typically 50–100). Formatting is string concatenation, no regex. Called 3–10 times per agent response. The real bottleneck is the platform API call latency (50–200 ms), not the flush logic itself.
  • Session Serialization (SessionStore.persist): O(m) where m = session turns. JSON serialization of 100+ turns can take 5–15 ms. Mitigated by writing asynchronously in a background task — the user-facing response is sent before persistence completes.

Resource Usage

  • Memory: Each active session consumes 10–500 KB depending on conversation length. With 1,000 concurrent sessions, baseline memory is ~50–500 MB. Sessions are loaded on-demand and evicted from the in-memory cache after cache_ttl_minutes (default: 30). Agent subprocesses are forked per request and cleaned up after completion.
  • I/O: Session reads/writes hit local disk (SSD). Each message triggers 1 read + 1 write. Platform API calls are the dominant I/O: 2–8 HTTPS requests per message (initial send + edits during streaming). Webhook ingestion is passive — platforms push to us, no polling.
  • CPU: Minimal — the gateway is I/O-bound. Token batching and message formatting use basic string operations. The LLM inference (the actual CPU/GPU workload) happens in the agent subprocess or on a remote API server, not in the gateway process.

Sub-Modules

Core

Central gateway orchestration, configuration, and session management.

  • run.py — GatewayRunner event loop
  • config.py — GatewayConfig loader and validator
  • session.py — SessionStore with lifecycle policies
  • pairing.py — PairingStore for DM authorization

Platforms

18+ platform adapters implementing BasePlatformAdapter.

  • base.py — Abstract adapter contract
  • telegram.py — Telegram Bot API (webhooks, edit-in-place)
  • discord.py — Discord bot (interactions, embeds)
  • slack.py — Slack Bolt (Block Kit, slash commands)
  • whatsapp.py, signal.py, matrix.py — Encrypted platforms
  • email.py, sms.py — Async/offline platforms
  • 10+ additional adapters (IRC, Mattermost, Teams, etc.)

Delivery & Streaming

Output pipeline for cron delivery and progressive LLM rendering.

  • delivery.py — DeliveryRouter for scheduled job output
  • stream_consumer.py — Token batching and edit-in-place rendering
  • Adaptive flush strategies per platform capability
  • Rate-limit-aware backoff and retry logic
