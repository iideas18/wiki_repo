📚 What is this & why does it exist?

src/ is the library half of rag-from-scratch. It is the code a downstream consumer would npm install and import from. It exists as a separate unit (rather than just publishing the examples/) so the project can train two muscles at once: (1) explain a concept end-to-end in a single self-contained example.js, then (2) extract the stable abstractions into a layered library that mirrors LangChain.js. Without src/, every example would re-implement Document, the splitter base, and the embedding cache — making the educational arc collapse into a flat pile of scripts.

💡 Real-world analogy

Imagine a cookbook author who teaches by giving you complete recipes (examples/) and, in a separate section at the back, the formal techniques those recipes rely on (src/). Each recipe is self-contained — you don't need the techniques chapter to make the dish — but if you want to build new recipes, the techniques chapter has the named primitives ("a roux", "a beurre blanc") with proper definitions. The techniques chapter is honest about what it covers: some sections are full chapters, others are placeholder pages because the author hasn't yet found the exemplary recipe to derive the technique from.

🎯 Why This Module Exists

The src/ tree is a deliberate exercise in API archaeology — copying LangChain.js's class shape (Document, BaseLoader.load(), BaseTextSplitter.splitText(), Embeddings.embedQuery(), BaseLLM.invoke/stream) but stripping every abstraction the educational arc doesn't yet need. A reader who graduates from this codebase can open LangChain's docs and recognise every primitive.

The current src/ is deliberately partial: only the layers the first six lessons depend on are filled in (embeddings/, text-splitters/, loaders/, llms/, utils/). The empty chains/, retrievers/, vector-stores/, and prompts/ are scaffolded with named-export index.js files — they hold a place in the import graph for future lessons. Without this module, every example would duplicate ~50 lines of Document, splitter base, and cache plumbing; the curriculum would lose its sense of progression.

🚶 Step-by-Step Narrated Walkthrough

Follow a single PDF page from disk to a vector ready for retrieval:

  1. User constructs new PDFLoader(url, {splitPages:true}) — constructor stores source and splitPages; no async work yet (constructors can't await).
  2. User calls await loader.load() — this is where work begins. The loader instantiates PDFParse({url}) from the pdf-parse package.
  3. Loader fetches PDF info via parser.getInfo() — gives us pages count, info.version, metadata. Cheap call (~10ms remote, <1ms local).
  4. Per-page extraction loop calls parser.getText({partial:[i+1]}). Each page text passes through cleanText() — collapse whitespace, cap consecutive newlines at 2.
  5. constructDocument builds the metadata bag: {source, pdf:{version,info,metadata,totalPages}, page:N, loc:{pageNumber:N}}. Returns a Document.
  6. User passes Documents to splitter: await new RecursiveCharacterTextSplitter({chunkSize:1000, chunkOverlap:200}).splitDocuments(docs). Splitter calls createDocuments(texts, metadatas) internally.
  7. Splitter picks the most coarse separator that exists in the text from ['\n\n','\n','. ',' ','']. For a typical PDF page, double-newline appears, so paragraphs are the primary split unit.
  8. Each split is sized via lengthFunction (default t => t.length). Pieces ≤ chunkSize stack into temp[]; oversize pieces recurse into the next finer separator.
  9. mergeSplits handles overlap: as it accumulates pieces into a chunk, when the chunk hits chunkSize it flushes, then shifts pieces off the front until length ≤ chunkOverlap. The remaining pieces become the prefix of the next chunk.
  10. Chunked Documents inherit metadata plus chunk:j and totalChunks:N. The PDF's page number is preserved — you can later cite the source.
  11. User constructs new EmbeddingModel({modelPath:'./models/bge-small.gguf'}) — sets defaults (dim=384, batchSize=32, cache=true). Model is NOT loaded yet.
  12. await embeddings.initialize() — idempotent. Calls getLlama() → loadModel() → createEmbeddingContext(). ~1.5s cold start, dominates the pipeline.
  13. await embeddings.embedDocuments(texts) — batches into chunks of 32, runs each batch as Promise.all(batch.map(per-text)). Per text: cache lookup (SHA-256 hash) — if hit, return immediately; if miss, call ctx.getEmbeddingFor(text) and write the result back.
  14. Vectors return as number[][]. The user is now responsible for storing them — src/vector-stores/ is empty, so this lesson explicitly delegates to embedded-vector-db in the calling example.

📊 Performance Profile

Fast paths. Cache hits in EmbeddingModel.embedQuery are O(1) Map lookup plus a SHA-256 (~5µs for short text). Batch embedding parallelises within a batch via Promise.all — wall-clock is bound by the slowest item, not the sum. Splitter mergeSplits is a single O(N) pass over the input.

Slow paths. Cold model load (LlamaCpp.initialize) is ~1–3 s for a 1B-parameter quantised model on a CPU laptop. Embedding fresh text routes through llama.cpp's getEmbeddingFor() — ~10–50 ms per call depending on model size and CPU. Chunked PDFs of typical academic-paper length (10–30 pages) take ~5–15 s end-to-end on the first run, sub-second on subsequent runs (cache).

Memory. EmbeddingCache is bounded by maxSize (default 10,000). At 384 dims × 4 bytes = ~1.5 KB per entry → ~15 MB at full capacity. Disk dumps write JSON (verbose but trivially loadable). Tradeoff: no Protobuf / no MessagePack — sticking to JSON keeps the cache human-inspectable, which is what an educational repo wants.

Code Examples

Embed a query and a document

import { EmbeddingModel } from './src/embeddings/EmbeddingModel.js';

const embeddings = new EmbeddingModel({
    modelPath: './models/bge-small-en-v1.5.Q8_0.gguf',
    cache: true,
    batchSize: 32
});
await embeddings.initialize();

const queryVec = await embeddings.embedQuery('What is RAG?');
const docVecs  = await embeddings.embedDocuments([
    'Retrieval-Augmented Generation combines retrieval with LLMs.',
    'The capital of France is Paris.'
]);

const sim = await embeddings.similarity('RAG explained', 'Retrieval-Augmented Generation');
console.log('similarity:', sim);  // ~0.85

Split a PDF into overlapping chunks

import { PDFLoader, RecursiveCharacterTextSplitter } from './src/index.js';

const loader = new PDFLoader('https://arxiv.org/pdf/2005.11401', { splitPages: true });
const pages = await loader.load();   // Document[]; one per page

const splitter = new RecursiveCharacterTextSplitter({
    chunkSize: 1000,
    chunkOverlap: 200,
    separators: ['\n\n', '\n', '. ', ' ', '']
});
const chunks = await splitter.splitDocuments(pages);
console.log(`${pages.length} pages -> ${chunks.length} chunks`);

Local LLM completion with grammar-constrained output

import { LlamaCpp } from './src/llms/LlamaCpp.js';

const llm = await LlamaCpp.initialize({
    modelPath: './models/Qwen3-1.7B.Q8_0.gguf',
    contextSize: 2048,
    temperature: 0.2,
    maxTokens: 256,
    // Optional: constrain output to JSON via GBNF
    gbnf: 'root ::= "{" ws "\"answer\":" ws string ws "}"'
});

const response = await llm.invoke('What is RAG?');
console.log(response);
await llm.dispose();

Sub-Module Cards

embeddings/

Text → vectors with caching. Why it exists: dense retrieval needs semantic vectors; the cache makes repeat queries free.

text-splitters/

Chunk long text. Why it exists: embeddings have a max input length; chunks are the indexable unit.

loaders/

Read sources into Document[]. Why it exists: every retrieval pipeline starts with parsing raw bytes.

llms/

Local LLM completion. Why it exists: RAG generates with retrieved context; this is the generation layer.
