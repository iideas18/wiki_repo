📚 What is this & why does it exist?

loaders/ is the entry point of any RAG pipeline: the bridge from "a file on disk or a URL on the web" to "a JavaScript Document object with metadata". Without this layer, every lesson would re-implement PDF parsing inline. With it, swapping a PDF for an HTML page or a JSON dump is a one-line change at the top of a script.

💡 Real-world analogy

A loader is the airport baggage handler. You hand over your bag in whatever format (hard case, soft duffel, briefcase); it comes out the other side as a uniform tagged item with a barcode and a destination written on it. The BaseLoader contract is the standard tag format; PDFLoader is the handler trained for hard cases.

🎯 Why This Component

The interesting design move here is the uniform output. Every loader returns Document[] regardless of source. That single decision lets every downstream component (splitters, vector stores, retrievers) work without knowing or caring whether the data started as a PDF, a URL, or a JSON file. It's a small interface, but it's the keystone that makes the rest of the pipeline composable.

The PDFLoader is the only mature implementation. The others (HTML, JSON, MD, CSV, Web) are stubs — the lessons import them where useful but the implementations are deferred. This is honest: the project teaches RAG using PDFs (papers, books) which is the most common real-world source.

📝 Annotated Code Walkthrough — PDFLoader.load

Resolve source to a buffer

async load() {
    const data = typeof this.source === 'string'
        ? await this._fetchOrRead(this.source)
        : this.source;

Three input types: URL string, filesystem path string, or already-loaded Buffer. The Buffer case lets users plug in custom transport (e.g., S3, sftp) without forking the loader.

Parse with pdfjs

    const pdfDoc = await getDocument({ data, useSystemFonts: true }).promise;
    const numPages = pdfDoc.numPages;

useSystemFonts:true avoids the missing-font warnings that pdfjs would otherwise spam to stderr. Cosmetic but important for clean lesson output.

Walk pages serially

    const pages = [];
    for (let i = 1; i <= numPages; i++) {
        const page = await pdfDoc.getPage(i);
        const content = await page.getTextContent();
        const text = content.items.map(it => it.str).join(' ');
        pages.push({ num: i, text });
    }

Serial, not parallel. pdfjs-dist isn't internally thread-safe across pages of a single document, and the per-page work is small. Parallelising here would be a bug, not a speedup.

Pull metadata

    const meta = await pdfDoc.getMetadata();
    const info = meta?.info || {};

Optional chaining because some PDFs lack the metadata stream entirely. Failing that, you'd get a Cannot read property 'info' of null.

Emit Documents

    if (this.splitPages) {
        return pages.map(p => new Document(p.text, {
            source: this.source, page: p.num, totalPages: numPages,
            title: info.Title, author: info.Author, ...info
        }));
    }
    const text = pages.map(p => p.text).join(this.pageJoiner);
    return [new Document(text, {
        source: this.source, totalPages: numPages, ...info
    })];
}

Per-page mode is the default because it preserves the most provenance. The whole-document mode is for use cases where chunk-level retrieval would be too granular — e.g., very short documents or when you want page-aware splitters to do the chunking themselves.

Deep-Dive Highlights

The URL/FS auto-detect Convenience

source.startsWith('http') is dumb-simple but correct for 99% of cases. Users who want HTTPS-only auth or custom headers can pre-fetch into a Buffer and pass that.

Page mode vs whole mode Tradeoff

Per-page wins when you want to cite (page N). Whole-document wins for very short PDFs where page boundaries are arbitrary.

Why the other formats are stubs Honesty

The README is upfront: this project teaches RAG, not data engineering. PDF + occasional URL covers the realistic exercises. The stubs document the intended API surface for future work.

⚠ Edge Cases & Boundaries

ScenarioWhat Actually Happens
PDF is image-only (scanned)getTextContent returns empty items[]; pages have empty text. The lesson sees zero content — OCR is out of scope.
Network fetch failsfetch throws; bubbles up to caller. No retry/backoff — lessons are interactive, user reruns.
PDF is encryptedgetDocument throws PasswordException. No password handling implemented.
Very large PDF (1000+ pages)Serial page walk takes time but never spikes memory dangerously — pdfjs streams. The bottleneck moves to embedding.
Metadata field has weird UnicodeSpread ...info propagates as-is into Document metadata. Downstream code receiving the metadata gets exactly what was in the PDF.

Code Examples

Load a PDF from URL

import { PDFLoader } from './src/loaders/PDFLoader.js';

const docs = await new PDFLoader(
    'https://arxiv.org/pdf/2005.11401.pdf',
    { splitPages: true }
).load();

console.log(`${docs.length} pages from "${docs[0].metadata.title}"`);
console.log(docs[0].pageContent.slice(0, 200));

Local PDF + immediate splitting

import { PDFLoader, RecursiveCharacterTextSplitter } from './src/index.js';

const chunks = await new PDFLoader('./papers/rag.pdf').loadAndSplit(
    new RecursiveCharacterTextSplitter({ chunkSize: 1000, chunkOverlap: 200 })
);
// chunks carry both PDF metadata (page, source) and chunk metadata (chunk, totalChunks)

Pre-loaded Buffer (for custom transport)

import { readFile } from 'node:fs/promises';
import { PDFLoader } from './src/loaders/PDFLoader.js';

const buffer = await readFile('./encrypted-after-decrypt.pdf');
const docs = await new PDFLoader(buffer, { splitPages: false }).load();
