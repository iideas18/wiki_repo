The Vim module implements a complete vim-mode keybinding layer for the Claude Code CLI input. It provides a full state machine with motions, operators, text objects, and mode transitions — giving power users the muscle-memory efficiency of vim-style editing directly inside the terminal prompt.

💡 Think of it like… a Combination Lock

The Vim module works like a combination lock — each keypress advances the state machine through stages (idle → operator → motion → execute). The types.ts file is the blueprint of all possible dial positions, transitions.ts is the mechanism that clicks each tumbler into place, and the remaining files (motions.ts, operators.ts, textObjects.ts) are the individual dial faces that resolve where to move and what to do when the lock opens.

State Machine

The CommandState union in types.ts defines 12 possible states. The transition() function in transitions.ts dispatches each keypress to the appropriate next state, eventually reaching an execute callback that mutates text or moves the cursor. Every path through the diagram below terminates by returning to idle with an optional side-effect.

Data Flow

Every keypress in normal mode enters through transition(), which consults the current CommandState, delegates to the appropriate resolver, and returns a TransitionResult containing the next state and an optional execute callback. The architecture keeps side-effect-free resolution (motions, text objects) separated from mutation (operators), making each layer independently testable.

Narrated Walkthrough

🚶 Executing d2w — Delete 2 Words

Follow the keypresses d 2 w as they flow through the state machine:

  1. Initial State — VimState is NORMAL with CommandState = idle. The cursor sits at position n in the input text.
  2. d pressed — transition() sees d in OPERATORS. State advances to operator { op: "delete", count: 1 }. No execute callback yet.
  3. 2 pressed — transition() detects a digit in operator state. State advances to operatorCount { op: "delete", count: 2 }. The count accumulates (respecting MAX_VIM_COUNT).
  4. w pressed — transition() recognizes w as a motion in SIMPLE_MOTIONS. It calls resolveMotion("w", 2, cursor, text) which advances past 2 word boundaries. isInclusiveMotion("w") returns false (exclusive).
  5. Operator Execution — executeOperatorMotion() is invoked with the OperatorContext, the resolved range [cursor, target), and operator "delete". It slices the text, calls setText(), updates the cursor via setOffset(), and stores the deleted text in the register via register.write().
  6. Change Recording — A RecordedChange is saved via recordChange() so the dot command (.) can replay the deletion.
  7. Return to Idle — TransitionResult.next is idle. The state machine resets, ready for the next command sequence.

Design Principles

Pure Functions Everywhere

Motion resolution and text object detection are pure functions — they take text and a position, and return a new position or range. This makes them trivially unit-testable without mocking any UI state.

Single Dispatch Entry Point

All keypress handling flows through one function: transition(). This makes it easy to trace, debug, and extend the state machine without hunting through scattered event handlers.

Grapheme Safety

Text object iteration in textObjects.ts is grapheme-aware, correctly handling multi-byte Unicode characters and combining marks so that cursor positioning never lands in the middle of a visual character.

Scannable Transition Table

The transitions.ts file acts as a single source of truth for all state transitions. Each CommandState variant has a clearly delineated branch, making the full behavior of the state machine readable in one pass without jumping between files.
