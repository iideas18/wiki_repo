💡 What is this?

The tools module is the execution layer of the Claude Code agent. Think of it like specialized departments in a company: the File department (FileRead, FileWrite, FileEdit) handles all document work, the Operations department (BashTool, PowerShellTool) runs shell commands, the Research department (GrepTool, GlobTool, WebSearchTool) gathers information, and the Management department (AgentTool, TaskCreateTool) delegates work to sub-agents. Each department has a clear job description (JSON schema), security clearance (permissions), and a standard reporting format (ToolResult). The tools.ts registry acts as the company directory — it decides which departments are available for each session based on feature flags and permission rules.

🚶 Step-by-Step Narrated Walkthrough

Follow a single FileEditTool operation as it flows through the entire tools pipeline:

  1. Model Emits tool_use — The AI model decides a file needs editing and emits a tool_use block with name: "FileEditTool", file_path, old_string, and new_string parameters.
  2. Tool Lookup — The QueryEngine calls findToolByName(tools, "FileEditTool") on the registry assembled by getTools(). The tool is found and returned.
  3. Input Validation — validateInput() runs synchronously: checks that file_path is non-empty, old_string differs from new_string, and the path doesn’t escape the working directory.
  4. Permission Check — checkPermissions() evaluates write permission rules. The path is matched against allow/deny patterns using matchWildcardPattern(). If the result is ask, a permission dialog appears.
  5. File Read — The tool reads the target file from disk. If the file exceeds the size limit (1 GB), it returns an error. If the file is not found, findSimilarFile() suggests alternatives.
  6. Search & Replace — The old_string is located in the file content. If an exact match fails, fuzzy matching kicks in. The replacement is applied, producing the new file content.
  7. Diff Generation — utils/gitDiff.ts computes a structured patch with context lines. Both a git-style diff and a structured patch object are generated for the result.
  8. File Write — The modified content is written to disk atomically. The file state cache is updated so subsequent edits have the correct baseline.
  9. Skill Activation — If the edited file matches a skill trigger pattern (via skills/loadSkillsDir.js), the associated skill is activated for follow-up actions.
  10. LSP Notification — If LSP is enabled, getLspServerManager() is notified of the file change so diagnostics update in real time.
  11. Result Assembly — A ToolResult is returned containing the diff output, line-change counts, and any new context messages. The result is sized-checked against maxResultSizeChars.
  12. UI Rendering — renderToolResultMessage() converts the result into a React component showing the diff with syntax highlighting. The model receives the serialized tool_result block.

Reads file contents with permission checks, size limits, and path suggestions on error.

  • Smart path resolution
  • Large file preview + disk path
  • Similar file suggestions

Ripgrep-powered text search with regex support and multiple output modes.

  • Context lines (-A, -B, -C)
  • Glob filtering
  • Count & file-list modes

MCPTool/

Model Context Protocol bridge integrating external tool servers into the agent runtime.

  • Dynamic tool discovery
  • Server authentication
  • Resource listing & fetching

WebFetchTool/

HTTP URL fetching with preapproved domain lists and content extraction.

  • Domain allowlisting
  • Content-type handling
  • Response size limits

SkillTool/

Custom plugin/extension execution with directory-based skill loading.

  • Trigger pattern matching
  • Skill activation on file edits
  • Extension point for custom logic

shared/

Cross-tool utilities for git operation tracking and multi-agent spawning.

  • Git commit/PR detection
  • OTLP counter increments
  • Analytics event firing

Core Types

// Tool.ts — Core interface (simplified)
export type Tool<Input, Output, P> = {
  readonly name: string
  readonly inputSchema: Input
  readonly inputJSONSchema?: ToolInputJSONSchema
  aliases?: string[]
  searchHint?: string
  maxResultSizeChars: number

  call(
    args: z.infer<Input>,
    context: ToolUseContext,
    canUseTool: CanUseToolFn,
    parentMessage: AssistantMessage,
    onProgress?: ToolCallProgress<P>,
  ): Promise<ToolResult<Output>>

  description(input: z.infer<Input>, options: DescOpts): Promise<string>
  validateInput(input: unknown, ctx: ToolUseContext): ValidationResult
  checkPermissions(input: z.infer<Input>, ctx: ToolPermCtx): Promise<PermResult>
  isEnabled(): boolean
  isReadOnly(input: z.infer<Input>): boolean
  isConcurrencySafe(input: z.infer<Input>): boolean
}

// Factory function
export function buildTool<D extends AnyToolDef>(def: D): BuiltTool<D> {
  return { ...TOOL_DEFAULTS, userFacingName: () => def.name, ...def }
}
