🎯 Project Philosophy

When you first open this repository, the most striking design choice is the absence of a shared runtime. There is no "core library" that all SDKs thunk into; no shared C++ module, no WebAssembly shim, no RPC proxy written in Rust. Instead, four SDKs reimplement the same behaviour from scratch — in TypeScript, Python, Go, and C# — and guarantee parity through three enforcement layers: a shared JSON Schema for the wire contract, a code generator that emits the RPC boilerplate, and a YAML-driven conformance test suite that diffs behaviour across all four.

This is a deliberate trade. A shared core would have been faster to build initially. But anyone who has used polyglot SDKs derived from a single code base knows the feeling — the Node SDK is a joy; the Python one is a thin wrapper over unmarshalled JSON; the Go one has a quirky camelCase API. By committing to per-language idiomaticity, every user of every SDK gets a first-class experience: Python users get async with CopilotClient(), .NET users get await using + CancellationToken, Go users get DefineTool[T,U] generics, TS users get discriminated-union SessionEvents. The cost — four parallel implementations — is managed by the contract-enforcement triad.

The second architectural commitment is treating the Copilot CLI binary as the server. Not an HTTP service, not a library. A sub-process. This feels old-school until you recognise how many problems it eliminates: process death is an OS-level signal (not a TCP timeout), clean-up is SIGKILL, authentication is inherited from the shell session, updates are a single binary swap, and no language's SDK has to reimplement the agent loop. The JSON-RPC framing (LSP-style Content-Length headers) is boring and well-understood; every SDK's "hardest file" is still under 400 lines.

The SDK prioritises correctness over performance and explicit over implicit. Every async entry point takes a cancellation token (or language equivalent). Capabilities are negotiated at session start — no try-call-catch-MethodNotFound patterns. Permission handlers get full tool call context (not just a boolean gate). The tool-use loop is observable via 40+ typed events, not a callback into a black box.

How SDK & CLI Connect

Every SDK speaks to the CLI through the same two-way JSON-RPC channel. Understanding the boundary is the single most important concept:

sequenceDiagram
    participant App as User App
    participant SDK as SDK client-side handlers
    participant RPC as JSON-RPC connection
Content-Length framed
    participant CLI as CLI server-side handlers

    App->>SDK: client.createSession()
    SDK->>RPC: request: session.create {config}
    RPC->>CLI: bytes
    CLI->>CLI: spawn internal session
    CLI-->>RPC: response {sessionId, capabilities}
    Note over RPC: SDK -> CLI: user-intent calls

    App->>SDK: session.send("hello")
    SDK->>RPC: request: session.send
    RPC->>CLI: bytes

    CLI->>RPC: notification: assistant.message
    RPC->>SDK: dispatched to SessionEvent listeners
    SDK-->>App: event callback fires

    CLI->>RPC: request: session/toolInvoke {tool,args}
    Note over RPC: CLI -> SDK: tool/permission/FS calls (bidirectional!)
    RPC->>SDK: dispatched to registered tool handler
    SDK->>App: user's tool code runs
    App-->>SDK: tool result
    SDK->>RPC: response {result}
    RPC->>CLI: bytes

    CLI->>RPC: notification: session.idle
    RPC->>SDK: resolves sendAndWait promise
Key insight. The JSON-RPC channel is bidirectional. The SDK makes calls like session.create and session.send; the CLI calls back for tool execution, permissions, FS operations, and elicitation. Every SDK must register both client-to-server call shims AND server-to-client handler maps on connect. This is why every SDK has a registerClientSessionApiHandlers-equivalent function.
