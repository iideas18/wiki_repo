nodejs — TypeScript / Node.js SDK

The reference SDK. @github/copilot-sdk on npm.

The Node.js SDK is the reference implementation of the Copilot SDK contract. It's the first SDK to receive new features, the source from which behaviour is ported to the other three languages, and the largest single surface in the repo. Uses vscode-jsonrpc for transport, supports both plain JSON Schema and Zod for tool parameters, and bundles the Copilot CLI as a transitive npm dependency so users never install it separately.

📚 What is this & why does it exist?

A TypeScript SDK that wraps JSON-RPC calls into idiomatic async methods on a CopilotClient class. When you call await client.createSession({ model: "gpt-4" }), under the hood the SDK spawns the copilot CLI as a sub-process, wires stdin/stdout into a vscode-jsonrpc message connection, negotiates the protocol version, and hands you back a typed CopilotSession object.

💡 Real-world analogy

Think of the SDK as a remote-control headset for a powerful but complicated robot (the Copilot CLI). The headset doesn't contain the robot; it just speaks its language. You press a button in your app — "tell me about Seattle weather" — and the headset translates that to the correct robot protocol, streams the robot's visual feed (events) back to you, and when the robot asks "should I open the door?" (permission request), it hands the question to you before the robot moves. If your app quits mid-sentence, the headset sends a polite shutdown command before unplugging; if you kill your app abruptly, the OS cuts the pipe and the robot powers down cleanly.

🎯 Why This Module Exists

The Node.js SDK exists because the Copilot CLI itself is a Node.js binary. That means (a) @github/copilot is already the dependency graph of any TypeScript project using the SDK, so bundling adds zero new runtime; (b) the maintainers of the SDK and the CLI work in the same language daily, so fixes roundtrip fast; (c) VS Code extensions and the massive Node ecosystem get first-class support immediately. Without this SDK, every TypeScript agent developer would shell out to copilot and parse stdout — losing the event stream, tool callbacks, permission flow, and streaming responses.

Because it's the reference, it tends to pioneer features. Commands and UI elicitation shipped in Node first (v0.2.0), then landed in Python/Go/.NET in v0.2.1. The enableConfigDiscovery flag, system-message transforms, and traceContextProvider all debuted here. A consequence: occasionally the Node SDK has capabilities no other SDK does yet — check CHANGELOG.md before relying on parity.

🚶 Step-by-Step Narrated Walkthrough

Follow a single session.sendAndWait({prompt: "weather?"}) call with one tool invocation:

  1. Client instantiation — new CopilotClient(options) validates inputs but does no I/O. No process yet.
  2. Session creation (lazy start) — createSession triggers start() if not already started. Spawn path: createRequire resolves @github/copilot → spawn(cliPath, ['serve','--stdio']). Wire StreamMessageReader/Writer into createMessageConnection.
  3. Protocol handshake — getStatus RPC. Compare protocolVersion against MIN_PROTOCOL_VERSION = 2; reject if lower. Cache negotiated version for capability gates.
  4. Register server→client handlers — registerClientSessionApiHandlers installs shims for tool dispatch, permission, elicitation, and SessionFs ops. These handlers dispatch by session ID to the right Session instance.
  5. session.create RPC — sends serialisable config. System-message callbacks are stripped and stored in a side-map; wire sends {action:"transform"} stubs.
  6. Listener pre-registration (race fix) — sendAndWait attaches its session.idle listener before calling send. Comment in session.ts L231-243 explains this.
  7. session.send RPC — returns a messageId. The agent turn is now running in the CLI.
  8. Event stream — assistant.message (partial) — CLI emits streaming chunks; your on() handlers fire for each. The sendAndWait listener captures the last one.
  9. Tool invocation (server→client RPC) — CLI's LLM decided to call get_weather. session/toolInvoke RPC arrives. SDK looks up the session, then toolHandlers.get("get_weather").
  10. Hook chain — if hooks.preToolUse is set, invoke it first. If it denies, RPC replies with error. If it modifies args, the modified set goes to the next stage.
  11. Permission gate — if the tool is permission-gated (or the policy requires it), permissionHandler runs. Can return approved, denied, or (on v2+) modified.
  12. User handler — awaits the user's (args) => result. Exceptions are caught and become {isError:true, content:...} results.
  13. Post-hook + reply — hooks.postToolUse can rewrite the result. RPC responds.
  14. session.idle event — agent loop complete. sendAndWait's idlePromise resolves with the captured last assistant message. Listener unsubscribes in finally.

⚡ Algorithm Spotlight

sendAndWait race-free idle detection

Problem. A fast-returning LLM can emit session.idle before the caller attaches a listener. Pre-registering the listener before sending the RPC closes the gap.

Chosen over: polling isIdle (misses transient states); synchronous subscribe inside the send RPC (vscode-jsonrpc doesn't cleanly support this). Complexity: O(1) per event.

// Register event handler BEFORE calling send to avoid race condition
// where session.idle fires before we start listening
const unsubscribe = this.on((event) => {
    if (event.type === "assistant.message") {
        lastAssistantMessage = event;
    } else if (event.type === "session.idle") {
        resolveIdle();
    } else if (event.type === "session.error") {
        const error = new Error(event.data.message);
        error.stack = event.data.stack;
        rejectWithError(error);
    }
});
// ... now safe to send
await this.send(options);

System-message transform wire trick

User-supplied functions can't cross JSON-RPC. So extractTransformCallbacks replaces each function with {action:"transform"}, stores the originals in a Map, and when the server round-trips a sections.transform RPC, the stored callback runs and the result is returned.

Protocol version negotiation

On connect, getStatus returns {protocolVersion, capabilities}. Client checks protocolVersion >= MIN_PROTOCOL_VERSION (2); lower rejects with an error. Cached negotiatedProtocolVersion drives capability gates like NO_RESULT_PERMISSION_V2_ERROR (the no-result permission return value is only legal on v2+).

📊 Performance Profile

The hot path is the event pump: a single Set.forEach(h => h(event)) per event, O(handlers) per dispatch. No allocation beyond the event object itself. Session creation is one RPC round-trip (~10ms localhost) plus subprocess spawn on first call (~50-100ms, amortised across later sessions on the same client). The bottleneck for large workloads is JSON serialisation of tool results — no streaming-tool-results protocol exists (would require a protocol extension). Memory per idle session is ~1 MB (event handler sets + tools map + capability cache); 10 sessions with 20 tools each = 200 handler closures but still well under 10 MB total.

What was optimised for: correctness and type safety. What was sacrificed: throughput for tool-heavy workloads (each tool invocation is a JSON-RPC round trip, so ~100 tool calls/sec is the practical ceiling per session).

Code Examples

Minimal client & session

import { CopilotClient, approveAll } from "@github/copilot-sdk";

const client = new CopilotClient({ model: "gpt-4" });

const session = await client.createSession({
    onPermissionRequest: approveAll,
});

session.on((event) => {
    if (event.type === "assistant.message") {
        console.log(event.data.content);
    }
});

const final = await session.sendAndWait({ prompt: "Hello, world!" });
console.log("final:", final?.data.content);

await client.stop();

Custom tool with Zod

import { defineTool } from "@github/copilot-sdk";
import { z } from "zod";

const getWeather = defineTool({
    name: "get_weather",
    description: "Get current weather for a city",
    parameters: z.object({
        city: z.string(),
        unit: z.enum(["C", "F"]).optional(),
    }),
    handler: async ({ city, unit }) => {
        return `Cloudy, 62°${unit ?? "F"} in ${city}`;
    },
});

const session = await client.createSession({
    tools: [getWeather],
    onPermissionRequest: approveAll,
});
