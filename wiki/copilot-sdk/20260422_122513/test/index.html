test — Conformance Suite

One YAML-driven harness proves all four SDKs behave identically against the same CLI.

The test/ directory contains language-agnostic conformance snapshots — YAML files describing a session scenario and its expected event stream. Every SDK ships a harness adapter that reads the YAML, drives the SDK, captures events, normalises them, and diffs against the snapshot. A single failing test indicates divergence between an SDK and the contract.

📚 What is this & why does it exist?

A harness + YAML snapshot infrastructure. Each test/snapshots/<feature>/*.yaml is a scenario: inputs, tool definitions, prompt, hook responses, expected final event stream. A per-SDK harness (Node: test/harness.ts; Python: test/harness.py; Go: go/internal/e2e; .NET: dotnet/test/Harness) turns the YAML into a live session, streams events, normalises timestamps/IDs, and asserts equality.

💡 Real-world analogy

Think of a chain of identical hotels. Each lobby must serve the same cappuccino — same temperature, same foam pattern, same saucer. Corporate HQ (YAML snapshots) defines the exact recipe. Each hotel has a local barista (SDK harness) following the recipe. An inspector (the test runner) orders from every hotel and measures. If one lobby's cappuccino is 2° off (one event extra or missing), the chain knows which branch drifted without re-auditing the recipe.

🎯 Why This Module Exists

Four SDKs + one protocol = a matrix of 4 implementations × N scenarios of "do we match the CLI?". Writing 4 copies of "send prompt, check response" tests would mean tests drift. A single set of YAML scenarios consumed by four harnesses enforces that the behaviour contract is one artefact — and any discrepancy surfaces as a normalised diff in CI, not as "oh, Go doesn't emit that event." This is also the mechanism used during protocol-version bumps: add the new scenario once; all four SDKs must implement and pass, or the PR is blocked.

🚶 One Harness Run

A single Node harness invocation against permissions.yaml:

  1. Load scenario — parse YAML into a typed scenario object (prompt, tools[], hookResponses[], expectedEvents[]).
  2. Spawn SDK Client — new CopilotClient(); await client.start().
  3. Create session — register tools from scenario, wire onPermissionRequest to return the scenario's canned approvals/denials.
  4. Subscribe to events — push every received SessionEvent into an actual array.
  5. Send prompt — session.send({prompt: scenario.prompt}).
  6. Await idle — await session.onIdle().
  7. Normalise — strip volatile fields: timestamp, sessionId, messageId, trace-context IDs → placeholder strings.
  8. Diff — deepStrictEqual(actual, scenario.expectedEvents). Failures print structural diffs.
  9. Teardown — await session.disconnect(); await client.stop().
  10. Report — JUnit XML or JSON; CI annotates the PR with failures.

⚡ Normalisation Algorithm

Each harness applies a fixed set of replacements to the event stream before diffing:

  • sessionId → <SESSION_ID>
  • messageId → <MESSAGE_ID_N> (indexed to preserve cross-references within the stream)
  • traceId, spanId → redacted
  • timestamp → omitted
  • Numeric durations → omitted (timing varies)
  • Tool call IDs → <TOOL_CALL_ID_N>

The normaliser is careful to preserve structural relationships (a toolCallCompleted referencing TOOL_CALL_ID_2 must refer to the same call as the earlier toolCallStarted). Violations of this invariant are themselves a test failure.

Adding a Scenario

  1. Create test/snapshots/<feature>/my_case.yaml with scenario: + expectedEvents: sections.
  2. Run Node harness in record mode: npm run test:record -- my_case. Captures and writes expected events.
  3. Run all four harnesses in check mode: npm run test:conformance. All must pass.
  4. Submit PR; reviewer sees the YAML change + any generated code updates.

📊 Performance

Each scenario spawns a CLI, runs one session, tears down. Typical wall clock: 0.5-3s per scenario per SDK. Running all four harnesses over 20 scenarios parallelised completes in under a minute. CI parallelises by SDK (not by scenario) because CLI reuse within a harness saves cold-start cost.

Normaliser snippet

function normalise(events: SessionEvent[]): SessionEvent[] {
    const idMap = new Map<string, string>();
    return events.map(e => {
        const copy = structuredClone(e);
        if ("timestamp" in copy) delete copy.timestamp;
        if ("sessionId" in copy) copy.sessionId = "<SESSION_ID>";
        if ("messageId" in copy) copy.messageId = mapId(idMap, "MSG", copy.messageId);
        if ("toolCallId" in copy) copy.toolCallId = mapId(idMap, "TOOL_CALL", copy.toolCallId);
        return copy;
    });
}

Node harness core

export async function runScenario(scenario: Scenario): Promise<Result> {
    const client = new CopilotClient();
    await client.start();
    const session = await client.createSession({
        tools: scenario.tools,
        onPermissionRequest: mkPermissionHandler(scenario.permissionResponses),
    });
    const actual: SessionEvent[] = [];
    session.on(e => actual.push(e));
    await session.send({ prompt: scenario.prompt });
    await session.onIdle();
    await client.stop();
    return diff(normalise(actual), scenario.expectedEvents);
}
