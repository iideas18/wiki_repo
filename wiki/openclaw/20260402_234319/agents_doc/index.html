Agents — LLM Orchestration Engine

Multi-Provider LLM Orchestration, Tool Execution & Agent Spawning

The agents module is the execution engine of OpenClaw. It handles the full lifecycle of an AI agent command — from model resolution and auth profile management through streaming LLM responses, tool execution loops, context compaction, and cascading model fallback. It supports 12+ LLM providers, sandboxed code execution, and autonomous child agent spawning via ACP.

📚 What is this & why does it exist?

The Agents module is the brain of OpenClaw. When a user sends a message, this module figures out which AI model to talk to, sends the request, streams back the response in real-time, and handles any tool calls the AI wants to make (running code, fetching web pages, spawning sub-agents). If the primary model fails, it automatically falls back to alternative providers.

💡 Real-world analogy

Think of the Agents module as an air traffic control tower at a busy international airport. Each incoming user message is a flight requesting a landing slot. The tower (agent-command pipeline) determines which runway (LLM provider) to assign. The streaming system is like the real-time radar feed — continuously updating position. Tool calls are like ground services (refueling, baggage handling) that happen mid-flight. If one runway shuts down (provider error), the tower immediately reroutes to an alternative runway (model fallback). The sandbox is the secure customs area where foreign cargo (untrusted code) is inspected before entry.

🚶 Step-by-Step Narrated Walkthrough

Follow a single user chat message as it flows through the entire Agents pipeline:

  1. Command Entry — The user message arrives as an AgentCommandOpts object in agent-command.ts. This includes the message text, optional images, provider/model overrides, and delivery target.
  2. Session Resolution — command/session.ts resolves or creates a session using the composite key (agent ID + channel + account + thread). The session store is loaded from disk with file-lock protection (~1ms).
  3. Model Selection — run/setup.ts calls resolveHookModelSelection() which checks agent config, then plugin hooks, then falls back to the default model. The effective context window is calculated here.
  4. Auth Profile Ordering — auth-profiles.ts loads stored API credentials, filters out expired/cooldown profiles, and sorts by recency. External CLI credentials are synced with a 15-minute TTL.
  5. Runner Initialization — pi-embedded-runner/run.ts initializes the SessionManager from @mariozechner/pi-coding-agent, prepares tool runtimes (LSP, MCP, codex), and builds the system prompt from workspace files (SOUL, AGENTS, TOOLS, IDENTITY).
  6. Payload Building — payloads.ts constructs provider-specific payloads. Anthropic gets cache-retention headers; Google gets schema sanitization via clean-for-gemini.ts; OpenRouter gets capability flags.
  7. LLM Streaming — The request is sent to the chosen provider. Streaming chunks arrive in real-time through provider-specific wrappers (e.g., openai-stream-wrappers.ts). Each chunk is assembled into the response buffer.
  8. Tool Execution Loop — If the LLM requests a tool call, attempt.ts validates arguments (with tool-call-argument-repair.ts for malformed JSON), executes the tool, and feeds the result back to the LLM. This loop continues until the LLM stops requesting tools.
  9. Context Compaction — If the conversation history exceeds the context window minus reserves (20K tokens floor), compact.ts triggers adaptive compaction: split messages by token share (40% base ratio), summarize each chunk, merge preserving identifiers. A 20% safety margin accounts for token estimation inaccuracy.
  10. Model Fallback — If the provider returns an error, model-fallback.ts categorizes it (rate-limit, context overflow, timeout, auth) and cascades to the next model in the fallback chain. Cooldown probing allows retrying recently-failed providers with short budgets.
  11. Result Assembly — The EmbeddedPiRunResult is assembled with payloads, usage metrics (input/output tokens), metadata (model used, duration, stop reason), and any pending tool sends.
  12. Delivery — command/delivery.ts routes the output to the target channel (webchat, WhatsApp, Slack thread, etc.). Session state and transcript are persisted to disk.
