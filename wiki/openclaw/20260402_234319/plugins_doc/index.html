💡 What is this?

The plugins module is the extensibility backbone of OpenClaw. It manages how plugins are discovered, loaded, configured, and wired into the assistant lifecycle. Every channel adapter, LLM provider, memory engine, and tool extension is a plugin. The system uses a manifest-first approach: plugin metadata (openclaw.plugin.json) is parsed and validated before any plugin code runs, enabling fast config validation and auto-enable logic without importing heavy runtime dependencies.

🔎 Analogy — how does this work?
Think of the plugin system as a modular electrical panel in a building. Each plugin is a circuit breaker with a standardized interface. The manifest is the label on each breaker — it tells the panel what the breaker controls without flipping it on. The registry is the panel itself, routing power (API calls) to the right circuits. The hook pipeline is the wiring bus — events flow through it and each active breaker can intercept, transform, or block the current.

    Architecture

    The plugin system is organized into four major subsystems: Discovery scans plugin roots and parses manifests into a cache; Loading evaluates enable/disable config state and uses jiti to lazily import plugin code; Registration builds the plugin API surface and populates the central registry with hooks, tools, and channels; and the MCP Bridge extracts MCP server configuration from bundles for external tool serving.

    Plugin Lifecycle

    The lifecycle of a plugin spans from discovery through registration to runtime hook execution. The application kicks off discovery by scanning configured plugin roots. Each discovered manifest is loaded into a registry of static metadata. The runtime then resolves enable states, lazily imports plugin modules via jiti, and calls each plugin's register() function with a typed API surface. Hooks registered during this phase are later invoked by the hook runner with priority-based ordering.

    Hook Execution Pipeline

    Hooks are the primary extension mechanism in the plugin system. When the application invokes runHook(name, event), the hook runner collects all registered handlers for that hook name, sorts them by priority (highest first, with pluginId as a tiebreaker for equal priorities), and executes them sequentially. Each handler receives the current accumulated result and can transform or extend it. Results are merged via mergeResults(). A handler can signal early exit through shouldStop(), which terminates the pipeline and logs the terminal decision. This allows plugins to override default behavior or short-circuit processing when needed.

    Code Examples

    Plugin Registration

    A plugin exports a default object with a register() method. The API surface passed to register() provides typed methods for hooking into the lifecycle, registering tools, and declaring capabilities.

    // Example: Registering a plugin with hooks and tools
import type { OpenClawPluginDefinition } from "./types.js";

export default {
  register(api) {
    // Register a lifecycle hook
    api.registerHook("before_agent_start", {
      priority: 100,
      handler: async (event) => {
        api.logger.info("Agent starting for", event.channelId);
        return { extraSystemPrompt: "You are helpful." };
      },
    });

    // Register a custom tool
    api.registerTool({
      name: "my-plugin-lookup",
      description: "Looks up data from my service",
      parameters: { query: { type: "string" } },
      execute: async ({ query }) => {
        return { result: await fetchFromService(query) };
      },
    });
  },
} satisfies OpenClawPluginDefinition;

    Plugin Manifest

    Every plugin must include an openclaw.plugin.json manifest that declares its identity, config schema, and capabilities. The manifest is validated statically before any plugin code is imported.

    // openclaw.plugin.json — Plugin manifest
{
  "id": "my-custom-plugin",
  "name": "My Custom Plugin",
  "version": "1.0.0",
  "enabledByDefault": false,
  "configSchema": {
    "apiEndpoint": { "type": "string", "default": "https://api.example.com" }
  },
  "providers": ["my-provider"],
  "providerAuthEnvVars": {
    "my-provider": ["MY_PROVIDER_API_KEY"]
  }
}
