Admin Operations

Focus Deep-Dive

Config mutation, scoped resets, and system-state commands

Admin operations are the privileged commands that modify OpenClaw’s persistent configuration, credentials, and installed services. Every mutation — from changing a model default to a full factory reset — flows through the mutateConfigFile transactional pipeline, which guarantees atomic reads, draft-based edits, and hash-checked writes so that concurrent CLI sessions never silently overwrite each other’s changes.

📚 What is this & why does it matter?

Admin operations form the control plane of OpenClaw. While regular slash commands read state and produce output, admin commands write state — they change the config file on disk, stop or start system services, and tear down workspace artifacts. Understanding this module is essential for debugging “config not saved” issues, building new administrative commands, or auditing what reset --scope full actually deletes.

💡 Real-world analogy

Think of a bank vault with a double-entry ledger. Every teller (CLI session) that wants to modify account balances must first read the current ledger page, make changes on a draft copy, and then compare a checksum before committing. If another teller changed the ledger in the meantime, the commit is rejected and the teller must re-read. mutateConfigFile is that ledger protocol — it prevents lost updates even when multiple terminals run configure simultaneously.

Overview

Primary role

Provide transactional config mutation and scoped teardown commands that safely modify OpenClaw system state.

Main inputs

RuntimeEnv context, user-supplied options (ResetOptions, UninstallOptions), and the current OpenClawConfig on disk.

Key decisions

Which reset scope to apply? Which uninstall targets to remove? Should the operation run in dry-run mode? Is a hash conflict detected?

Outputs / side effects

ConfigReplaceResult with the new config hash, service stop/start signals, and filesystem deletions for reset and uninstall scopes.

How It Works

Admin operations follow three distinct patterns depending on the command: transactional config mutation for configure and agent config, scoped reset for the reset command, and multi-scope uninstall for teardown. All three patterns share the same dry-run and confirmation guardrails.

Config Mutation Lifecycle

The mutateConfigFile function implements an optimistic-concurrency protocol. It reads the current config file into a snapshot, passes a mutable draft to the caller’s mutate callback, and then performs a compare-and-swap write using the snapshot’s hash. If another process modified the file between read and write, the operation fails with a hash-conflict error rather than silently overwriting.

flowchart TD
  START["mutateConfigFile() called"]
  READ["Read config file from disk"]
  SNAP["Create ConfigFileSnapshot + hash"]
  DRAFT["Clone snapshot into mutable draft"]
  MUTATE["Execute caller's mutate(draft, context)"]
  COMPARE{"baseHash === currentHash?"}
  WRITE["Atomically write draft to disk"]
  RESULT["Return ConfigReplaceResult + result T"]
  CONFLICT["Throw hash-conflict error"]
  DRYRUN{"dryRun enabled?"}
  PREVIEW["Return preview without writing"]

  START --> READ
  READ --> SNAP
  SNAP --> DRAFT
  DRAFT --> MUTATE
  MUTATE --> DRYRUN
  DRYRUN -->|Yes| PREVIEW
  DRYRUN -->|No| COMPARE
  COMPARE -->|Match| WRITE

The flowchart above shows the full config mutation pipeline. The critical path runs from top to bottom: read → snapshot → draft → mutate → compare → write. The dry-run branch exits early after mutation without touching disk, and the hash-conflict branch raises an error that the caller can retry.

Configure Command

The configureCommand and configureCommandWithSections functions launch an interactive wizard that collects user input, then calls mutateConfigFile internally to persist changes. The sections parameter allows callers to restrict the wizard to specific config areas (e.g., only model settings).

// src/commands/configure.commands.ts — configure entry points
export async function configureCommand(
  runtime: RuntimeEnv = defaultRuntime
) {
  await runConfigureWizard({ command: "configure" }, runtime);
}

export async function configureCommandWithSections(
  sections: WizardSection[],
  runtime: RuntimeEnv = defaultRuntime
) {
  await runConfigureWizard(
    { command: "configure", sections },
    runtime
  );
}

Scoped Reset Flow

The resetCommand applies a progressively wider teardown depending on the chosen ResetScope. The "config" scope only removes the config file. The "config+creds+sessions" scope additionally clears stored credentials and active session tokens. The "full" scope performs a factory reset that also removes workspace artifacts, agent directories, and cached data.

Multi-Scope Uninstall

The uninstall command uses a scope-set pattern rather than a single enum. The buildScopeSelection helper reads individual boolean flags (--service, --state, --workspace, --app) and the --all shorthand to produce a Set<UninstallScope>. Each scope triggers a specific teardown action, and scopes execute in dependency order: service is stopped before state is removed, and workspace is cleaned before app binaries are deleted.

// src/commands/uninstall.ts — scope selection and teardown
type UninstallScope = "service" | "state" | "workspace" | "app";

export type UninstallOptions = {
  service?: boolean;
  state?: boolean;
  workspace?: boolean;
  app?: boolean;
  all?: boolean;
  yes?: boolean;
  nonInteractive?: boolean;
  dryRun?: boolean;
};

function buildScopeSelection(
  opts: UninstallOptions
): { scopes: Set<UninstallScope>; hadExplicit: boolean; }

async function stopAndUninstallService(
  runtime: RuntimeEnv
): Promise<boolean>
⚠ Dependency ordering matters: The uninstall pipeline always processes scopes in the order service → state → workspace → app. Attempting to remove state while the service is still running would cause file-lock errors on Windows. The stopAndUninstallService helper handles graceful shutdown before any filesystem deletions begin.

Code Walkthrough — applyAgentConfig

This walkthrough traces how agent configuration parameters are merged into the global OpenClawConfig object. The function uses a selective-merge strategy: only fields that are explicitly provided in the params object are overwritten; omitted fields preserve their existing values.

Receive the current config and parameters

The function takes the full OpenClawConfig as its first argument and a params object with the target agentId plus optional override fields. The config is treated as immutable input — a new config object is returned.

// src/commands/agents.config.ts — entry point
export function applyAgentConfig(
  cfg: OpenClawConfig,
  params: {
    agentId: string;
    name?: string;
    workspace?: string;
    agentDir?: string;
    model?: string;
  }
): OpenClawConfig

Look up or create the agent entry

The function searches cfg.agents for an entry matching params.agentId. If no entry exists, a new agent record is initialized with default values. This ensures that applyAgentConfig can be called for both existing agents and first-time setup.

Selective field merge

Each optional parameter is checked for presence (not just truthiness — an empty string is a valid override). Only present fields are written to the agent record. This prevents accidental field clearing when only one property needs to change.

Return new config

A new OpenClawConfig object is returned with the updated agents array. The original cfg is never mutated, keeping the function pure and compatible with the mutateConfigFile draft pattern where the caller controls when the draft is committed.

Setup Command

The setupCommand orchestrates first-run initialization. It creates workspace directories, writes a default config file (via mutateConfigFile), and optionally launches the configure wizard. It is safe to call on an already-initialized workspace — existing files are not overwritten.

// src/commands/setup.ts — setup entry point
export async function setupCommand(
  opts?: { workspace?: string },
  runtime: RuntimeEnv = defaultRuntime
)
✓ Idempotent design: setupCommand checks for the existence of each artifact before creating it. Running setup on an already-configured workspace is a safe no-op — it will only create missing files and directories.
