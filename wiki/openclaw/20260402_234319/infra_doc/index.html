Infrastructure — Core Runtime Services

Core Runtime Services

The Infrastructure module provides the foundational runtime layer for OpenClaw: data store abstractions (SQLite and atomic JSON persistence), an in-memory caching layer with TTL-based eviction, a cron-style heartbeat scheduler, process supervision across Linux/macOS/Windows, a resilient outbound delivery pipeline, and system-level utilities including SSRF-safe networking and sandboxed filesystem operations.

Architecture

The infrastructure layer sits beneath every other OpenClaw module. Configuration flows down from config/, while channels, agents, and commands depend on infra for I/O, scheduling, delivery, and process control. The three sub-modules (store, caching, scheduling) encapsulate the data persistence, in-memory state, and time-based execution concerns respectively.

Data Flow

A typical request flows through the infrastructure layer from configuration load through state persistence, message normalization, delivery queuing, and finally transport. The pipeline ensures atomic writes, retry on transient failures, and audit logging at each stage.

How Infrastructure Connects to Config & Commands

Infrastructure owns runtime I/O and scheduling. Config owns schema validation and materialization. Commands own user-facing workflows. The boundary between them is defined by typed interfaces: infra exposes loadJsonFile(), writeJsonAtomic(), acquireGatewayLock(), and scheduleGatewaySigusr1Restart(). Config calls into infra for file persistence; commands call into infra for process control and delivery.

🚶 Step-by-Step Narrated Walkthrough

Follow a single outbound message delivery as it flows through the entire Infrastructure pipeline:

  1. Config Resolution — loadConfig() reads the YAML/JSON5 config file via atomic JSON I/O, applies environment substitution, and materializes the OpenClawConfig object.
  2. Session Lookup — The session store loads the conversation entry from disk using readJsonFile<SessionEntry>() with file locking to prevent concurrent writes.
  3. Approval Check — If the message triggers a command execution, exec-approvals.ts checks the allowlist patterns. If no match, it opens a JSONL socket to request user approval (30-minute timeout).
  4. Heartbeat Gate — The heartbeat runner checks active hours, evaluates the reason kind, and decides whether to send or skip based on channel visibility settings and interval configuration.
  5. Payload Normalization — outbound/payloads.ts converts the ReplyPayload into a NormalizedOutboundPayload, chunking text by markdown paragraphs if needed.
  6. Channel Resolution — outbound/channel-resolution.ts resolves the channel plugin adapter, validating capabilities (media support, threads, reactions).
  7. Queue Enqueue — enqueueDelivery() writes a JSON file to ${stateDir}/delivery-queue/ using atomic writes with PID-based temp files.
  8. Delivery Attempt — The delivery runner reads pending items, attempts send via the channel adapter, and on success calls ackDelivery() to remove the queue file.
  9. Retry on Failure — Transient errors trigger exponential backoff (5s → 25s → 120s → 600s). Permanent errors (bot blocked, chat not found) move the item to failed/.
  10. Cost Tracking — session-cost-usage.ts records token usage and calculates per-provider costs for the session transcript.
  11. Process Health — The gateway lock file is refreshed, system presence is broadcast via mDNS, and the update runner checks for new releases on the configured channel.

Sub-Modules

store/

Data store abstractions and persistence layer. Atomic JSON I/O, SQLite runtime integration, device auth storage, delivery queue persistence, and safe file operations with symlink protection.

  • Atomic writes with UUID-based temp files
  • State migration detection for legacy paths
  • Sandboxed filesystem with O_NOFOLLOW

caching/

In-memory caching layer with TTL-based eviction, Symbol-based singletons for global state, fixed-window rate limiting, and deduplication utilities for heartbeat and system event payloads.

  • System presence cache (200 entries, 5-min TTL)
  • Session-scoped event queues (max 20)
  • Fixed-window rate limiter with backoff

scheduling/

Cron-style heartbeat scheduling, process supervision across three OS platforms, SIGUSR1-based graceful restarts with cooldown enforcement, and delivery queue recovery with exponential backoff.

  • Active-hours time gating for heartbeats
  • Supervisor-aware process respawn
  • Exponential backoff (5s → 600s) for retries

Atomic JSON Write Pattern

export async function writeJsonAtomic(
  filePath: string,
  value: unknown,
  options?: { mode?: number }
): Promise<void> {
  const tmpPath = `${filePath}.${crypto.randomUUID()}.tmp`;
  const data = JSON.stringify(value, null, 2);
  await fs.writeFile(tmpPath, data, { mode: options?.mode ?? 0o600 });
  await fs.rename(tmpPath, filePath);
}

Heartbeat Summary Resolution

export type HeartbeatSummary = {
  intervalMs: number;
  reason: HeartbeatReasonKind;
  visibility: HeartbeatVisibility;
  enabled: boolean;
};

export function resolveHeartbeatSummaryForAgent(
  agentId: string
): HeartbeatSummary {
  const enabled = isHeartbeatEnabledForAgent(agentId);
  const intervalMs = resolveHeartbeatIntervalMs(agentId, config);
  const reason = resolveHeartbeatReason(agentId);
  const visibility = resolveHeartbeatVisibility(agentId);
  return { intervalMs, reason, visibility, enabled };
}
