Data Models

Focus Deep-Dive

Core persistence type system for OpenClaw’s infrastructure layer

Every value that OpenClaw writes to disk or holds in memory conforms to one of these types. Understanding them is the fastest way to navigate the codebase.

📚 What is this & why does it matter?

Data models define the shape of everything persisted to disk or held in memory across the store layer. Getting the types right prevents runtime errors, makes the codebase self-documenting, and ensures that every reader of a JSON file or SQLite row knows exactly what fields to expect and what invariants hold.

💡 Real-world analogy

Think of data models like architectural blueprints for a building. Every room (data field) has a purpose, every door (interface) connects rooms in specific ways, and every load-bearing wall (required field) must remain in place. Change a blueprint incorrectly and walls don’t align—rename a field without updating consumers and the app crashes at runtime.

Overview

Primary role

Define the canonical TypeScript interfaces and types for every persistent artifact in the store layer.

Main inputs

Raw JSON from disk, SQLite rows, environment variables, and in-memory state from upstream modules.

Key decisions

Versioned schemas (version: 1) enable forward-compatible migrations. Optional fields use ? to distinguish missing from empty.

Outputs / side effects

Typed objects consumed by query builders, migration scripts, delivery queues, and session managers throughout the infra layer.

How It Works

Every model in the store layer follows the same lifecycle: define a TypeScript interface, export it, and consume it in exactly one reader function and one writer function. This ensures a single source of truth for every field name and type.

Device Auth Store

The DeviceAuthStore interface wraps all device-level credentials into a single versioned record. The tokens map uses Record<string, unknown> to allow heterogeneous token formats across providers.

/** Versioned device credential schema */
interface DeviceAuthStore {
  version: 1;
  deviceId: string;
  tokens: Record<string, unknown>;
}

/** Individual token entry with CRUD helpers */
interface DeviceAuthEntry {
  tokenKey: string;
  tokenValue: unknown;
}

function loadDeviceAuthToken(
  store: DeviceAuthStore,
  key: string
): DeviceAuthEntry | undefined {
  const value = store.tokens[key];
  if (value === undefined) return undefined;
  return { tokenKey: key, tokenValue: value };
}

function storeDeviceAuthToken(
  store: DeviceAuthStore,
  key: string,
  value: unknown
): void {
  store.tokens[key] = value;
}

function clearDeviceAuthToken(
  store: DeviceAuthStore,
  key: string
): boolean {
  if (!(key in store.tokens)) return false;
  delete store.tokens[key];
  return true;
}
Key detail: The version: 1 literal type ensures that code handling a DeviceAuthStore object will not compile if handed a future schema version without an explicit migration step.

Delivery Queue Models

The delivery system uses a two-layer type hierarchy. QueuedDeliveryPayload captures the intent (what to deliver, where, and how), while QueuedDelivery extends it with operational metadata used by the retry engine.

interface QueuedDeliveryPayload {
  channel: string;
  to: string;
  accountId?: string;
  payloads: unknown[];
  threadId?: string;
  replyToId?: string;
  bestEffort?: boolean;
  gifPlayback?: boolean;
  forceDocument?: boolean;
  silent?: boolean;
  mirror?: boolean;
}

interface QueuedDelivery extends QueuedDeliveryPayload {
  id: string;
  enqueuedAt: number;
  retryCount: number;
  lastAttemptAt?: number;
  lastError?: string;
}
Retry semantics: When retryCount exceeds the configured maximum, the delivery is moved to a dead-letter directory rather than deleted, preserving the payload for manual inspection.

Session Entry

Each active or historical session is represented by a SessionEntry record. The store layer persists these to a JSON5-formatted session store file, keyed by sessionId.

interface SessionEntry {
  sessionId: string;
  updatedAt: number;
  sessionFile?: string;
  channel?: string;
  chatType?: string;
  execHost?: string;
  modelOverride?: string;
  inputTokens?: number;
  outputTokens?: number;
  spawnedBy?: string;
  spawnDepth?: number;
  subagentRole?: string;
}

Execution Approvals

The approvals subsystem tracks pending and resolved execution requests. ExecApprovalsFile is the top-level container persisted to disk, while request and resolution records are indexed by id.

Validation Pipeline

flowchart TD
    A["Raw JSON from disk"] --> B["JSON.parse / JSON5.parse"]
    B --> C{"version field present?"}
    C -- Yes --> D["Match version to schema"]
    C -- No --> E["Reject: invalid format"]
    D --> F{"Schema matches current?"}
    F -- Yes --> G["Zod validation pass"]
    F -- No --> H["Run migration pipeline"]
    H --> G
    G --> I{"All required fields valid?"}
    I -- Yes --> J["Return typed object"]
    I -- No --> K["Return validation error"]
    E --> K

The validation pipeline runs every time a model is loaded from disk. Raw JSON is parsed, version-checked, optionally migrated, then validated through a Zod schema. Only fully validated objects are returned to callers; everything else surfaces as a structured error.

Design benefit: Because validation is centralized in the load path, no downstream consumer ever needs to check for missing or malformed fields—the type system guarantees correctness after the load boundary.

The load function reads the approvals file, validates its version, and returns a typed result or null:

async function loadApprovalsFile(
  filePath: string
): Promise<ExecApprovalsFile | null> {
  const raw = await readJsonFile<unknown>(filePath);
  if (!raw || typeof raw !== "object") return null;
  const obj = raw as Record<string, unknown>;
  if (obj.version !== 1) return null;
  return obj as ExecApprovalsFile;
}
Guard clause: The version !== 1 check ensures that if a future version introduces breaking changes, the current code fails fast rather than silently misinterpreting fields.
