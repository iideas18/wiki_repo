Model Picker

Focus Deep-Dive

Discovering, filtering, and selecting AI models across providers

When a user runs /model set gpt-4 or /model scan, the model picker subsystem is responsible for loading the full model registry, resolving configured entries (defaults, fallbacks, image models), presenting filterable rows, and persisting the user's selection back into the configuration. It bridges the gap between raw provider catalogs and the single "active model" that the agent runtime consumes.

📚 What is this & why does it matter?

The model picker is the user-facing layer that turns a sprawling multi-provider model catalog into a manageable selection experience. Every /model subcommand — set, set-image, list, scan — relies on the registry loader and configured-entries resolver to know which models exist, which are available, and which the user has already chosen. Understanding this module is essential for debugging "model not found" errors, adding new provider integrations, or tracing how a fallback chain is evaluated at runtime.

💡 Real-world analogy

Think of a streaming service's "Choose your plan" screen. Behind the scenes the service queries every available plan from multiple billing providers, marks which ones are available in your region, highlights your current selection, and lets you switch with a single click. The model picker does the same thing — except the "plans" are AI models from OpenAI, Anthropic, local Ollama instances, and more. It aggregates, filters, tags, and presents them so the user can pick one without knowing the underlying provider plumbing.

Contents

Overview

Primary role

Load the model registry from all configured providers, resolve tagged entries (default, fallback, image), and expose set/scan commands for model selection.

Main inputs

User-supplied model key strings (e.g. gpt-4, claude-3-opus), the OpenClawConfig object, and provider auth credentials from AuthProfileStore.

Key decisions

Is the requested model key valid? Is the provider reachable and the model available? Should suppressed built-in models be hidden from the listing?

Outputs / side effects

Writes the selected model key into the persisted config via updateConfig(). Returns ModelRow[] arrays for display and versions.json-compatible availability maps.

Key insight: The model picker never calls provider APIs directly. It delegates to discoverModels() which abstracts every provider behind a uniform Model<Api> interface. This keeps the picker purely about selection, not about protocol differences between providers.

Core Types

The model picker revolves around two data structures: ConfiguredEntry which represents a model reference extracted from the user's config, and ModelRow which is the display-ready row shown to the user in listings and scan results.

ConfiguredEntry

Each entry in the user's configuration — default model, fallback chain, image model — is normalized into a ConfiguredEntry. The tags set indicates why this entry exists (e.g. "default", "fallback#1", "image").

How It Works

The model picker pipeline has three distinct phases: registry loading, configured entry resolution, and model selection/scanning. Each phase builds on the previous one's output.

Phase 1 — Registry Loading

The loadModelRegistry() function bootstraps the full model catalog from all configured providers. It discovers the agent directory, reads auth credentials, calls each provider's model enumeration API, and filters out suppressed built-in models.

// src/commands/models/list.registry.ts
export async function loadModelRegistry(
  cfg: OpenClawConfig,
  opts?: { sourceConfig?: OpenClawConfig },
) {
  const agentDir = resolveOpenClawAgentDir();
  const authStorage = discoverAuthStorage(agentDir);
  const registry = discoverModels(authStorage, agentDir);
  const models = registry
    .getAll()
    .filter((model) =>
      !shouldSuppressBuiltInModel({
        provider: model.provider,
        id: model.id,
      }),
    );
  // ... availability checking against auth credentials
  return { registry, models, availableKeys, availabilityErrorMessage };
}
Performance note: discoverModels() caches provider responses for the lifetime of the process. Subsequent calls to loadModelRegistry() within the same session are nearly free because the discovery layer returns cached catalogs.

Phase 2 — Configured Entry Resolution

Once the registry is loaded, resolveConfiguredEntries() walks the user's OpenClawConfig to extract every model reference and assign semantic tags. The function processes entries in a fixed order: default model first, then fallback chain, then image model, then image fallback chain, and finally any explicitly configured model entries.

// src/commands/models/list.configured.ts
export function resolveConfiguredEntries(cfg: OpenClawConfig) {
  // resolves default, fallbacks, image model, configured models
  // Tags: "default", "fallback#N", "image", "img-fallback#N", "configured"
  return { entries };
}
Ordering matters: If the same model key appears as both "default" and "configured", the tags are merged into a single ConfiguredEntry rather than creating a duplicate. This ensures each model key appears at most once in the resolved list, with all applicable tags combined.

Phase 3 — Model Selection Commands

The modelsSetCommand and modelsSetImageCommand functions handle the final step: persisting the user's choice into the config file. Both follow the same pattern — call updateConfig() with a mutation function, log the result, and confirm to the user.

// src/commands/models/set.ts
export async function modelsSetCommand(
  modelRaw: string,
  runtime: RuntimeEnv,
) {
  const updated = await updateConfig((cfg) => {
    return applyDefaultModelPrimaryUpdate({
      cfg,
      modelRaw,
      field: "model",
    });
  });
  logConfigUpdated(runtime);
  runtime.log(
    `Default model: ${
      resolveAgentModelPrimaryValue(updated.agents?.defaults?.model)
        ?? modelRaw
    }`,
  );
}
// src/commands/models/set-image.ts
export async function modelsSetImageCommand(
  modelRaw: string,
  runtime: RuntimeEnv,
) {
  const updated = await updateConfig((cfg) => {
    return applyDefaultModelPrimaryUpdate({
      cfg,
      modelRaw,
      field: "imageModel",
    });
  });
  logConfigUpdated(runtime);
  runtime.log(
    `Image model: ${
      resolveAgentModelPrimaryValue(updated.agents?.defaults?.imageModel)
        ?? modelRaw
    }`,
  );
}

The pipeline is intentionally linear for the set commands — there is no branching or retry logic. If the model key is not found in the registry, the command fails immediately with an error message. The scan command, by contrast, adds a probing loop before the selection step.

Notice that resolveAgentModelPrimaryValue is called after the config write. This is intentional — it reads the updated config to resolve any alias or provider-qualified name back to a human-readable form. If resolution fails (returns null), the raw user input is echoed instead.

Code Walkthrough: toModelRow

The toModelRow function is the bridge between the internal Model<Api> objects and the user-facing ModelRow display type. Here is how each piece of data is resolved, step by step.

Accept parameters and destructure

The function receives a parameter bag that includes the registry model (which may be undefined if the config references a model that no longer exists), the canonical key, tags, aliases, the set of available keys from probing, and optional config/auth references for provider-level fallback.

// src/commands/models/list.registry.ts
export function toModelRow(params: {
  model?: Model<Api>;
  key: string;
  tags: string[];
  aliases?: string[];
  availableKeys?: Set<string>;
  cfg?: OpenClawConfig;
  authStore?: AuthProfileStore;
  allowProviderAvailabilityFallback?: boolean;
}): ModelRow

Handle missing models

If params.model is undefined, the model exists in config but not in any provider's catalog. The function returns a ModelRow with missing: true and all capability fields set to null. This allows the UI to render a warning row without crashing.

Resolve availability

For existing models, availability is determined by checking params.availableKeys. If the key is present, available: true. If the set exists but the key is absent, available: false. If no availability set was provided (probing was skipped), available: null. When allowProviderAvailabilityFallback is set and the model-level check is null, the function falls back to checking whether any model from the same provider is available.

Build the display row

The final ModelRow is assembled from the model's metadata (name, input modalities, context window, local flag) combined with the resolved availability and the flattened tags array. This is returned to the caller for rendering.
