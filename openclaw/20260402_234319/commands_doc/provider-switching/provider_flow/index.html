Provider Flow

Focus Deep-Dive

How OpenClaw resolves, probes, and selects provider authentication at runtime

When a user invokes a model command or an agent needs to make an LLM call, OpenClaw must decide which provider to use and how to authenticate. The provider flow pipeline resolves configuration, builds a list of probe targets from profiles, environment variables, and models.json, executes concurrent auth probes against each candidate, and returns a ranked summary. This module is the backbone of multi-provider credential management.

📚 What is this & why does it matter?

Provider flow is the authentication resolution pipeline that sits between user-facing model commands and the actual LLM API calls. Every time OpenClaw needs to verify a credential, rotate between providers, or report which auth sources are active, the provider flow module orchestrates the process. Understanding this pipeline is essential for debugging auth failures, configuring multi-provider setups, and extending the credential system with new provider types.

💡 Real-world analogy

Imagine an airport security checkpoint with multiple lanes — biometric, boarding pass, and priority access. Each traveler (API request) is checked against available lanes (providers) based on their ticket type (auth source). The system probes each lane for availability and wait time, then routes the traveler to the best open lane. If biometric is down, it falls back to boarding pass. The provider flow is that checkpoint controller — it probes every lane in parallel, records latency and status, and returns the fastest healthy option.

Overview

Primary role

Resolve provider credentials from multiple sources (profiles, env vars, models.json) and probe each candidate to determine auth readiness.

Main inputs

OpenClawConfig, a list of provider names, model candidates, and AuthProbeOptions controlling timeout and concurrency.

Key decisions

Which auth sources to include, how to order probes, which candidates pass validation, and how to handle rate-limited or expired credentials.

Outputs / side effects

An AuthProbeSummary containing per-target results with status codes, latency measurements, and reason codes for failures. No mutations to config.

Core Types

The provider flow module revolves around two key type families: probe results that capture the outcome of individual auth checks, and provider overviews that summarize the effective credential state for display commands.

AuthProbeResult & AuthProbeStatus

Each probe target produces an AuthProbeResult with a status enum indicating whether the credential is valid, rate-limited, expired, or otherwise unusable. The reasonCode field provides machine-readable detail for failures.

How It Works

The provider flow pipeline operates in four distinct phases: context resolution, target building, concurrent probing, and order management. Each phase is implemented as a separate async function, enabling callers to compose only the phases they need.

Phase 1 — Auth Context Resolution

Before any probing can occur, the pipeline must resolve the current configuration into a structured auth context. The resolveModelsAuthContext function loads and validates the config, resolves the default agent, and discovers all available plugin providers.

// src/commands/models/auth.ts
async function resolveModelsAuthContext(): Promise<ResolvedModelsAuthContext> {
  const config = await loadValidConfigOrThrow();
  const defaultAgentId = resolveDefaultAgentId(config);
  const agentDir = resolveAgentDir(config, defaultAgentId);
  const workspaceDir =
    resolveAgentWorkspaceDir(config, defaultAgentId) ??
    resolveDefaultAgentWorkspaceDir();
  const providers = resolvePluginProviders({
    config,
    workspaceDir,
    // ... additional options
  });
  return { config, agentDir, workspaceDir, providers };
}
Key insight: The auth context is resolved once and passed to all downstream functions. This ensures that the config snapshot is consistent across the entire probe cycle — no TOCTOU races between reading profiles and executing probes.

Phase 2 — Probe Target Building

The buildProbeTargets function takes the resolved providers and model candidates and produces two outputs: a list of AuthProbeTarget objects for live probing and a list of AuthProbeResult objects for targets that were excluded early.

// src/commands/models/auth.ts
export async function buildProbeTargets(params: {
  cfg: OpenClawConfig;
  providers: string[];
  modelCandidates: string[];
  options: AuthProbeOptions;
}): Promise<{
  targets: AuthProbeTarget[];
  results: AuthProbeResult[];
}>
Early-exit results: Targets with missing_credential, expired, invalid_expires, unresolved_ref, or ineligible_profile reason codes are returned in the results array without ever hitting the network. This is a critical performance optimization for setups with many configured but inactive providers.

Enumerate credential sources. For each provider in the providers array, the function collects credentials from three sources: auth profiles (OAuth tokens, API keys, bearer tokens), environment variables (OPENAI_API_KEY, etc.), and models.json entries. Each source produces one or more candidate targets.

Cross-product with model candidates. Each credential source is paired with each model candidate to produce the full target matrix. If a provider declares supported models, only the intersection is kept.

Apply early-exit filters. Targets with missing, expired, or invalid credentials are immediately converted to AuthProbeResult entries with the appropriate reasonCode and removed from the live-probe list.

Apply auth order filter. If the user has set an auth order for this provider (via modelsAuthOrderSetCommand), targets not in the order list are excluded with excluded_by_auth_order. Remaining targets are reordered to match the user-specified sequence.

Return split results. The function returns { targets, results } where targets are ready for live probing and results contain all early-exit entries.

Phase 3 — Concurrent Auth Probing

The runAuthProbes function takes the targets from Phase 2 and executes lightweight HTTP requests against each provider endpoint in parallel. It reports progress via an optional callback and returns the complete AuthProbeSummary.

// src/commands/models/auth.ts
export async function runAuthProbes(params: {
  cfg: OpenClawConfig;
  providers: string[];
  modelCandidates: string[];
  options: AuthProbeOptions;
  onProgress?: (update: {
    completed: number;
    total: number;
    label?: string;
  }) => void;
}): Promise<AuthProbeSummary>

The sequence diagram shows how runAuthProbes orchestrates the full pipeline. It first calls buildProbeTargets to get the live targets and early-exit results. The live targets are probed concurrently (respecting the concurrency limit in AuthProbeOptions). Each probe returns an HTTP status code and latency measurement. The progress callback fires after each probe completes. Finally, early-exit results and live probe results are merged into a single AuthProbeSummary.

Phase 4 — Auth Order Management

Users can control which credentials are used for a given provider via three order management commands. These commands read and write a per-provider auth order that is respected by buildProbeTargets.
