Search Setup

Focus Deep-Dive

Configuring and selecting web search providers through the setup wizard

When a user runs the search setup flow or types /docs search, the search setup module discovers all available search providers — both bundled and runtime-contributed — presents a selection prompt, handles API key credential input, and writes the chosen provider into OpenClawConfig. This module bridges the gap between plugin-contributed search providers and the user-facing configuration wizard.

📚 What is this & why does it matter?

Search setup is the configuration gateway for OpenClaw's web search capability. Every search provider — whether it's a bundled provider like Tavily or Brave, or a runtime plugin — must be discovered, selected, and credentialed through this flow before the agent can perform web searches. Understanding this module is essential for adding new search providers, debugging "no search provider configured" errors, or tracing how API keys are stored in the config.

💡 Real-world analogy

Think of setting up a new streaming service on your smart TV. First, the TV scans for all available apps (provider discovery). Then you pick one from the list (selection prompt). Next, you enter your login credentials (API key input). Finally, the TV saves your choice as the default (config persistence). The search setup flow is exactly this process — but for web search providers in an AI assistant.

Overview

Primary role

Discover available search providers, present a selection UI, collect credentials, and persist the chosen provider into OpenClawConfig.

Main inputs

Current OpenClawConfig, RuntimeEnv for environment variable checks, WizardPrompter for interactive prompts, and optional SetupSearchOptions.

Key decisions

Which providers are available? Does the user already have a key? Should the key come from env or manual input? Which provider is selected?

Outputs / side effects

An updated OpenClawConfig with the selected provider, enabled flag set to true, and the credential applied. No direct I/O side effects.

Core Types

The search setup module defines several types that bridge the generic flow system with search-specific configuration. SearchProvider is a deeply-nested type extraction from the config schema, while SearchProviderSetupContribution extends the generic FlowContribution with search-specific metadata.

// src/flows/search-setup.ts — Core type definitions
export type SearchProvider = NonNullable<
  NonNullable<
    NonNullable<
      NonNullable<OpenClawConfig["tools"]>["web"]
    >["search"]
  >["provider"]
>;

type SearchConfig = NonNullable<
  NonNullable<
    NonNullable<OpenClawConfig["tools"]>["web"]
  >["search"]
>;

type MutableSearchConfig = SearchConfig & Record<string, unknown>;

The SearchProvider type uses a chain of NonNullable unwrapping to drill through the optional config nesting and extract the literal union of valid provider names. MutableSearchConfig extends the readonly config with an index signature so that provider-specific credential setters can write arbitrary keys.

  kind: "search";
  surface: "setup";

  option: SearchProviderSetupOption;
  source: "bundled" | "runtime";

How It Works

Search setup operates in four distinct phases: provider discovery, selection flow, credential application, and docs search integration. Each phase is intentionally decoupled so that provider discovery can be reused by other setup flows.

Phase 1 — Provider Discovery

The resolveSearchProviderOptions function is the public entry point for discovering available providers. It delegates to resolveSearchProviderSetupContributions, which merges bundled providers shipped with OpenClaw and runtime providers registered by plugins, then sorts the merged list alphabetically by label.

Phase 2 — Selection Flow

The runSearchSetupFlow orchestrates the full interactive wizard. It resolves available providers, renders a selection prompt via WizardPrompter, checks for existing credentials, and applies the result.

// src/flows/search-setup.ts — Main setup flow
export async function runSearchSetupFlow(
  config: OpenClawConfig,
  runtime: RuntimeEnv,
  prompter: WizardPrompter,
  opts?: SetupSearchOptions,
): Promise<OpenClawConfig> {
  // 1. Resolve available providers
  const providers = resolveSearchProviderOptions(config);

  // 2. Show provider selection prompt
  const selected = await prompter.select({
    message: "Choose a search provider",
    options: providers.map(p => ({ label: p.label, value: p.id })),
  });

  // 3. Handle credential input
  //    - Check hasExistingKey() first
  //    - Then hasKeyInEnv() for env-injected keys
  //    - Fall back to interactive prompt

  // 4. Apply selection + key to config
  return applySearchKey(config, selected, key);
}

Phase 3 — Credential Application

The applySearchKey function is the core of credential persistence. It performs an immutable config update using object spreads, handles the two-phase credential write pattern, and applies provider-specific selection config.

Resolve the provider entry — Look up the PluginWebSearchProviderEntry by provider name. If the entry is not found (e.g., a plugin was unloaded between selection and application), return the config unchanged as a safety guard.

// src/flows/search-setup.ts — applySearchKey
export function applySearchKey(
  config: OpenClawConfig,
  provider: SearchProvider,
  key: SecretInput,
): OpenClawConfig {
  const providerEntry = resolveSearchProviderEntry(config, provider);
  if (!providerEntry) return config;

Build the new search config — Spread the existing search config (if any), set the provider field to the selected provider, and enable search by setting enabled: true.

  const search: MutableSearchConfig = {
    ...config.tools?.web?.search,
    provider,
    enabled: true,
  };

Phase-1 credential write — If the provider does not have a setConfiguredCredentialValue method, call the standard setCredentialValue to write the key into the mutable search config object before it is frozen into the next config.

  if (!providerEntry.setConfiguredCredentialValue) {
    providerEntry.setCredentialValue(search, key);
  }

Assemble the next config — Perform an immutable deep spread to produce the new OpenClawConfig with the updated tools.web.search section. Then apply any provider-specific selection config (e.g., default model, region settings).

  const nextBase: OpenClawConfig = {
    ...config,
    tools: {
      ...config.tools,
      web: { ...config.tools?.web, search },
    },
  };
  const next = applySearchProviderSelectionConfig(
    nextBase, providerEntry,
  );

Phase-2 credential write — If the provider supports the two-phase pattern (setConfiguredCredentialValue exists), call it now with the fully-assembled config. This allows providers that need the complete config context (e.g., to derive a storage path) to write their credential correctly.

  providerEntry.setConfiguredCredentialValue?.(next, key);
  return next;
}
⚠ Two-phase credential pattern: The dual setCredentialValue / setConfiguredCredentialValue split exists because some providers need the final config object (with provider-specific selection applied) to determine where to store the credential. If your provider only needs the search config section, implement setCredentialValue alone. Only implement setConfiguredCredentialValue if you need the full OpenClawConfig context.

Phase 4 — Docs Search Integration

The docsSearchCommand in src/commands/docs.ts uses the configured search provider to perform documentation searches via the MCP tool interface. It joins query parts, invokes the mcporter tool with the configured search tool, and applies a timeout.

// src/commands/docs.ts — docsSearchCommand
export async function docsSearchCommand(
  queryParts: string[],
  runtime: RuntimeEnv,
) {
  const query = queryParts.join(" ").trim();
  const res = await runTool(
    "mcporter",
