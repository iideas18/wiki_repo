Diagnostics Commands

Focus Deep-Dive

Health checks, status scanning, and automated repair flows

The diagnostics subsystem provides three complementary views into system health: the health command for real-time gateway probes, the status command for deep runtime and session scanning, and the doctor flow for interactive config repair. Together they form the primary observability surface for operators and the first line of automated self-healing.

📚 What is this & why does it matter?

Diagnostics commands are the nervous system of an OpenClaw deployment. When a channel stops responding, when sessions accumulate stale state, or when a gateway probe times out, these commands are the first tools an operator reaches for. They surface structured health data as both human-readable summaries and machine-parseable JSON, enabling both manual triage and automated monitoring pipelines.

💡 Real-world analogy

Think of a hospital triage system. The health command is the vital-signs monitor — quick pulse, temperature, blood pressure. The status command is the full diagnostic panel — blood work, imaging, detailed charts. The doctor command is the attending physician who reads the panels and prescribes treatment. Each level provides progressively deeper insight and intervention capability.

Contents

Overview

Primary role

Probe gateway health, scan runtime status, and interactively repair misconfigured deployments via structured diagnostic pipelines.

Main inputs

CLI flags (--json, --verbose, --deep, --usage, --timeout-ms), gateway RPC responses, and local config files.

Key decisions

Should we probe channels? Is the heartbeat stale? Are sessions orphaned? Does the config need migration? Should we offer an update first?

Outputs / side effects

HealthSummary or StatusReport objects rendered as tables or JSON. The doctor flow may mutate config files and restart services.

Three diagnostic tiers: health is fast and read-only (gateway round-trip). status adds local runtime and session scanning. doctor is the only tier that writes — it can repair config, update allowlists, and restart processes.

How It Works

The diagnostics subsystem has three independent but composable command paths: the health command for gateway-level probes, the status command for local runtime scanning, and the doctor flow for interactive repair. Each is designed to be invoked independently or chained in automated pipelines.

Health Command — Gateway Probing

The healthCommand function issues a single RPC call to the gateway's health method. When the --verbose flag is set, it passes { probe: true } to trigger live channel probes rather than returning cached status. The result is a complete HealthSummary snapshot.

// src/commands/health.ts — healthCommand
export async function healthCommand(
  opts: { json?: boolean; timeoutMs?: number; verbose?: boolean; config?: OpenClawConfig },
  runtime: RuntimeEnv,
) {
  const cfg = opts.config ?? runtime.config;
  const summary = await callGateway<HealthSummary>({
    method: "health",
    params: opts.verbose ? { probe: true } : undefined,
    timeoutMs: opts.timeoutMs,
    config: cfg,
  });

  if (opts.json) {
    runtime.stdout.write(JSON.stringify(summary, null, 2));
    return;
  }

  // Render human-readable channel table
  renderChannelTable(summary.channels, summary.channelOrder, summary.channelLabels, runtime);
  renderAgentTable(summary.agents, summary.defaultAgentId, runtime);
  renderSessionSummary(summary.sessions, runtime);
}

The companion getHealthSnapshot function provides a programmatic API for other subsystems (e.g. the doctor flow) that need a HealthSummary without CLI rendering:

// src/commands/health.ts — getHealthSnapshot
export async function getHealthSnapshot(
  params?: { timeoutMs?: number; probe?: boolean },
): Promise<HealthSummary> {
  return callGateway<HealthSummary>({
    method: "health",
    params: params?.probe ? { probe: true } : undefined,
    timeoutMs: params?.timeoutMs,
  });
}

Status Command — Runtime Scanning

The statusCommand extends health data with local runtime introspection. It scans session directories, checks process states, and optionally gathers usage statistics. The --deep flag activates the full scan pipeline including status.scan.runtime.ts and status.scan.fast-json.ts.

// src/commands/status.command.ts — statusCommand
export async function statusCommand(
  opts: {
    json?: boolean;
    deep?: boolean;
    usage?: boolean;
    timeoutMs?: number;
    verbose?: boolean;
    all?: boolean;
  },
  runtime: RuntimeEnv,
) {
  const health = await getHealthSnapshot({
    timeoutMs: opts.timeoutMs,
    probe: opts.verbose,
  });

  const scanResult = opts.deep
    ? await deepScan(runtime)
    : await fastScan(runtime);

  const summary = buildStatusSummary(health, scanResult, {
    includeUsage: opts.usage,
    includeAll: opts.all,
  });

  if (opts.json) {
    runtime.stdout.write(JSON.stringify(summary, null, 2));
    return;
  }

  renderStatusReport(summary, runtime);
}
Performance note: Deep scan reads every session file from disk via status.scan.fast-json.ts, which uses streaming JSON parsing to avoid loading entire session blobs into memory. On deployments with 10,000+ sessions, prefer --json output piped to jq for filtering.

Doctor Flow — Interactive Repair

The doctor flow is the most complex diagnostic path. It combines health probing, config validation, and interactive repair into a single guided workflow. The flow is orchestrated by createDoctorPrompter which presents issues and repair options through a terminal UI.

The doctor flow runs six sequential diagnostic stages. First, it checks whether the binary itself is outdated. Then it migrates any legacy config schemas. The health snapshot is taken with full probing enabled. Installation issues (missing binaries, incorrect permissions) and startup optimization hints (unnecessary env vars, slow plugin loads) are noted. Finally, allowlist policies are validated against the current channel configuration.

Idempotent repairs: Every repair action in the doctor flow is idempotent. Running doctor twice with the same config produces the same result. Repairs are applied through atomic file writes with rollback on failure.

Code Walkthrough

Gateway health RPC

The health command calls callGateway with method "health". The gateway aggregates channel probe results, agent heartbeats, and session counts into a single HealthSummary response. The timeoutMs parameter bounds the total round-trip including all channel probes.

Channel iteration

The summary's channelOrder array determines rendering order. Each channel's ChannelHealthSummary may contain nested accounts for multi-account providers (e.g. multiple Telegram bot tokens). The configured and linked booleans distinguish between channels that are defined in config versus channels that have active authenticated connections.

Agent heartbeat evaluation

Each AgentHealthSummary contains a heartbeat field with the last heartbeat timestamp. The health renderer compares this against heartbeatSeconds from the top-level summary to determine if an agent is stale. Agents whose last heartbeat exceeds 2 × heartbeatSeconds are flagged as unhealthy.

Session age analysis

The sessions.recent array contains the most recently updated sessions with their age in milliseconds. The status command uses this to identify orphaned sessions — those with age exceeding the configured session TTL. The count field gives the total number of active sessions without loading them all.

Doctor repair dispatch

When the doctor flow identifies issues, createDoctorPrompter presents them as a numbered list. Each issue has an associated repair function. Repairs are executed in dependency order: config repairs before service restarts, allowlist repairs before channel re-probes. The maybeRepairUiProtocolFreshness function handles the special case of stale UI protocol versions.

Doctor Shared Modules

The src/commands/doctor/shared/ directory contains 25+ utility modules that the doctor flow delegates to for specific repair tasks. These are intentionally decoupled so they can be unit-tested in isolation.

ModuleResponsibility
allowlist-policy-repair.tsDetects and repairs mismatched allowlist policies against current channel configuration
exec-safe-bins.tsValidates that all referenced binaries in exec commands exist and have correct permissions
mutable-allowlist.tsProvides a mutable in-memory allowlist that the repair flow can modify before persisting
empty-allowlist-policy.tsGenerates a clean empty allowlist policy as a baseline when no policy file exists
Gateway status subsystem: The src/commands/gateway-status/ directory contains four modules — discovery.ts (gateway endpoint resolution), helpers.ts (response normalization), output.ts (rendering), and probe-run.ts (individual probe execution) — that handle the low-level gateway communication for both health and status commands.
