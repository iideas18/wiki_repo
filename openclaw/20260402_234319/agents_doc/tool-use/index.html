Agents/Tool Use/ — Function Calling & Tool Infrastructure

60+ agent tools and the infrastructure for LLM function calling

The tool-use sub-module implements OpenClaw’s complete library of agent tools and the infrastructure that enables LLMs to call them. It handles tool call normalization, argument validation and repair, parameter type checking, action gating, error propagation, result truncation, and context-window guards — turning raw LLM function-call requests into safe, validated tool executions.

Each of the 60+ tools follows a consistent contract: validate inputs via readStringParam() and TypeBox schemas, check authorization via action gates, execute the operation, and return a structured result within configured size limits.

📚 What is this & why does it exist?

The tool-use sub-module is the bridge between what an LLM wants to do and what actually happens. When an LLM decides it needs to fetch a web page, spawn a sub-agent, generate an image, or run a cron job, this module validates the request, checks permissions, repairs any malformed arguments, executes the tool, and returns the result in a format the LLM can understand. Without it, function calling would be unreliable and insecure.

It covers every stage from the moment the LLM emits a tool_call JSON object to the moment the result is injected back into the conversation context — including the surprisingly common case where the LLM produces syntactically broken JSON that needs automatic repair.

💡 Real-world analogy

Think of a Swiss Army knife with 60+ blades. Each blade is a different tool (web fetch, image generation, cron scheduling, etc.), but you can’t just yank any blade out — there’s a safety mechanism. The tool-use module is the spring-loaded locking system: it checks which blade you asked for, validates that your grip is correct (parameter validation), ensures you’re authorized to use that blade (action gating), and if you try to open the blade at a weird angle (malformed JSON), it auto-corrects your grip before the blade deploys. If something goes wrong, it safely folds the blade back and reports what happened.

Architecture

The tool execution pipeline is a linear chain with early-exit error branches. Every tool call from the LLM passes through normalization, argument repair, parameter validation, and action gating before reaching the actual tool handler. Results flow back through truncation and context guards before being returned to the LLM.

flowchart TD
  LLM["LLM Response"] --> NORM["Tool Call Normalization\nattempt.tool-call-normalization.ts"]
  NORM --> REPAIR["Argument Repair\nattempt.tool-call-argument-repair.ts"]
  REPAIR --> VALIDATE["Parameter Validation\nreadStringParam / TypeBox schemas"]
  VALIDATE --> GATE["Action Gate\ncreateActionGate()"]
  GATE --> DISPATCH["Tool Dispatch\nAnyAgentTool union routing"]
  DISPATCH --> EXEC["Tool Execution\nIndividual tool handlers"]
  EXEC --> TRUNC["Result Truncation\nDEFAULT_FETCH_MAX_CHARS"]
  TRUNC --> GUARD["Context Guard\nWindow boundary check"]
  GUARD --> LLM

Error Handling

The tool-use module defines a two-tier error hierarchy. ToolInputError (HTTP 400 equivalent) signals parameter validation failures — missing required fields, invalid types, or out-of-range values. ToolAuthorizationError (HTTP 403 equivalent) extends ToolInputError and signals permission violations when an agent tries to invoke an owner-restricted tool or an action blocked by the gate.

Both error types are caught by the attempt loop and returned to the LLM as structured error messages, capped at DEFAULT_ERROR_MAX_CHARS (4000) characters. This approach ensures the LLM can understand what went wrong and retry with corrected parameters, rather than receiving an opaque failure. The error hierarchy is intentionally modeled after HTTP status codes for familiarity.

Code Examples

Example: ToolInputError Usage Pattern

import { ToolInputError, ToolAuthorizationError } from "./tools/common";

function validateFetchUrl(url: string): void {
  if (!url || typeof url !== "string") {
    throw new ToolInputError("url parameter is required and must be a string");
  }
  const parsed = new URL(url);
  if (parsed.protocol !== "https:" && parsed.protocol !== "http:") {
    throw new ToolInputError(`Unsupported protocol: ${parsed.protocol}`);
  }
}

function checkToolAccess(tool: string, userId: string, ownerId: string): void {
  if (tool === "gateway" && userId !== ownerId) {
    throw new ToolAuthorizationError(OWNER_ONLY_TOOL_ERROR);
  }
}

Example: createActionGate() Factory Pattern

Action gates provide composable permission boundaries. An admin gate may allow all default tools, while a restricted user gate only permits read-only actions. Gates are checked synchronously before every tool dispatch.

import { createActionGate } from "./tools/common";

// Create a gate that allows only specific tool actions
const gate = createActionGate({
  allow: ["exec", "read", "write", "sessions_spawn"],
  deny: ["gateway", "subagents"],
});

// Gate returns true/false for each tool action
if (!gate.isAllowed("gateway")) {
  throw new ToolAuthorizationError("gateway tool is not permitted");
}

// Gates can be composed for layered permission checks
const adminGate = createActionGate({ allow: DEFAULT_TOOL_ALLOW });
const userGate = createActionGate({
  allow: ["read", "web_fetch", "web_search"],
  deny: ["exec", "write", "apply_patch"],
});

Example: Web Fetch Config Resolution

The fetch configuration resolver clamps user-supplied overrides within the allowed bounds, ensuring safety limits are always respected even when callers request extreme values.

const DEFAULT_FETCH_MAX_CHARS = 50_000;
const DEFAULT_FETCH_MAX_RESPONSE_BYTES = 2_000_000;
const DEFAULT_FETCH_MAX_REDIRECTS = 3;
const FETCH_MAX_RESPONSE_BYTES_MIN = 32_000;
const FETCH_MAX_RESPONSE_BYTES_MAX = 10_000_000;

function resolveFetchConfig(overrides?: Partial<FetchConfig>): FetchConfig {
  const maxBytes = Math.min(
    FETCH_MAX_RESPONSE_BYTES_MAX,
    Math.max(
      FETCH_MAX_RESPONSE_BYTES_MIN,
      overrides?.maxResponseBytes ?? DEFAULT_FETCH_MAX_RESPONSE_BYTES,
    ),
  );
  return {
    maxChars: overrides?.maxChars ?? DEFAULT_FETCH_MAX_CHARS,
    maxResponseBytes: maxBytes,
    maxRedirects: overrides?.maxRedirects ?? DEFAULT_FETCH_MAX_REDIRECTS,
  };
}
