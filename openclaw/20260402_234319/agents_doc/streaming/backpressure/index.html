Backpressure & Flow Control

Focus Deep-Dive

Managing context window limits and adaptive compaction triggers

As streaming conversations grow, accumulated tokens can approach the model's context window ceiling. This module detects impending overflow, triggers adaptive compaction to summarize older messages, truncates oversized tool results, and prunes stale images — all while maintaining conversation coherence.

📚 What is this & why does it matter?

Every LLM has a finite context window. When a long-running agent session accumulates enough messages and tool results, it risks exceeding that limit and crashing mid-response. Backpressure and flow control mechanisms detect when token counts approach the ceiling and proactively compact the conversation — summarizing old messages, truncating tool results, and pruning images. Without this, multi-turn agent sessions would fail unpredictably after a few dozen interactions.

💡 Real-world analogy

Think of a court reporter who must keep a running transcript for the judge. The transcript binder has a maximum number of pages. When it starts getting full, the reporter summarizes earlier testimony into condensed notes, archives the detailed pages, and continues writing. If a witness submits a 500-page evidence document, the reporter makes an abstract instead of pasting the whole thing. Old exhibit photos are removed to save space. The judge can still follow the trial because the summaries preserve the essential narrative.

How It Works

Backpressure management operates at three layers: pre-compaction mitigations, adaptive compaction, and session truncation as a last resort. Each layer activates only when the previous layer fails to bring token counts below the safe threshold.

Layer 1 — Pre-Compaction Mitigations

Before triggering full compaction, the system tries two lightweight measures that preserve full conversation detail:

Tool result truncation (tool-result-truncation.ts) scans all tool results in the history and truncates any that exceed a configurable byte limit. It preserves the first and last N characters with an [...truncated...] marker in between, ensuring the LLM still sees the beginning and end of large outputs.

Image pruning (history-image-prune.ts) removes image attachments from messages older than a configurable number of turns. Images are expensive in tokens (a single screenshot can cost 1000+ tokens) and become less relevant as the conversation progresses.

Key detail: The tool-result-context-guard.ts module wraps new incoming tool results before they enter the history, preventing a single oversized tool output from immediately triggering compaction. It enforces the truncation policy proactively, not just reactively.

Layer 2 — Adaptive Compaction

When pre-compaction mitigations are insufficient, the full compaction algorithm runs. It is implemented primarily in compact.ts and orchestrated by compaction-runtime-context.ts.

// compact.ts — core compaction algorithm
const BASE_CHUNK_RATIO = 0.4;
const MIN_CHUNK_RATIO = 0.15;
const SAFETY_MARGIN = 1.2;

async function compactHistory(
  messages: Message[],
  contextWindow: number,
  reserve: number,
  attempt: number = 0,
): Promise<Message[]> {
  const targetTokens = contextWindow - reserve;
  const ratio = Math.max(
    MIN_CHUNK_RATIO,
    BASE_CHUNK_RATIO - attempt * 0.1,
  );

  // Split: keep recent messages verbatim, compact older ones
  const { toCompact, toKeep } = splitMessagesByTokenShare(
    messages,
    ratio,
    targetTokens,
  );

  // Summarize older messages in stages
  const summaries = await summarizeInStages(toCompact, targetTokens * ratio);

  // Merge: summary + recent verbatim messages
  const compacted = [...summaries, ...toKeep];

  // Validate: did we actually reduce enough?
  const estimate = estimateTokens(compacted) * SAFETY_MARGIN;
  if (estimate > targetTokens && attempt < 3) {
    return compactHistory(messages, contextWindow, reserve, attempt + 1);
  }

  return compacted;
}
Watch out: The SAFETY_MARGIN of 1.2 means the system targets 83% of the actual limit. This is intentional — token estimation is approximate, and the margin protects against underestimates. However, it also means compaction triggers ~20% earlier than strictly necessary, trading context for reliability.

Summarization Strategy

The summarizeInStages() function breaks the to-compact portion into smaller chunks (each fitting within the LLM's context window) and summarizes them sequentially. Each stage's output becomes input for the next, progressively distilling the conversation. The function respects message boundaries — it never splits a single message across summary stages.

Layer 3 — Session Truncation

If compaction fails (e.g., the summary itself is too long, or the timeout fires), session-truncation.ts performs hard truncation: it drops the oldest messages entirely until the history fits. This is the last resort — it loses information but guarantees the session can continue.

Failure mode: Hard truncation can remove critical context (e.g., the initial user goal). To mitigate this, the system always preserves the first system message and the most recent N user messages, even during hard truncation.

The state diagram shows the complete lifecycle of a single compaction cycle. Most sessions never leave the Normal → CheckingTokens → Normal loop. Long-running sessions may cycle through PreCompaction several times before needing full compaction. The TimedOut transition guards against summarization hangs, ensuring the session never blocks indefinitely.

Design insight: The three-layer approach (pre-compaction → adaptive compaction → hard truncation) means the system degrades gracefully. Each layer is more aggressive but also more likely to succeed, so the session always makes forward progress.

The compaction check runs before every LLM call. compaction-runtime-context.ts assembles the runtime context needed for the decision:

// compaction-runtime-context.ts
interface CompactionRuntimeContext {
  messages: Message[];
  contextWindow: number;
  reserveTokens: number;
  estimatedTokens: number;
  toolResultSizes: Map<string, number>;
  imageCount: number;
}

function buildCompactionContext(
  session: Session,
  model: ModelConfig,
): CompactionRuntimeContext {
  const messages = session.getHistory();
  const estimated = estimateTokens(messages);
  return {
    messages,
    contextWindow: model.contextWindow,
    reserveTokens: model.maxOutputTokens + 512, // +512 for system prompt
    estimatedTokens: estimated,
    toolResultSizes: scanToolResultSizes(messages),
    imageCount: countImages(messages),
  };
}

The splitMessagesByTokenShare() function divides the history at a token boundary. It scans from the oldest message forward, accumulating token estimates until the target threshold is reached:

// compact.ts — splitting logic
function splitMessagesByTokenShare(
  messages: Message[],
  ratio: number,
  targetTokens: number,
): { toCompact: Message[]; toKeep: Message[] } {
  const compactBudget = Math.floor(targetTokens * ratio);
  let accumulated = 0;
  let splitIndex = 0;

  for (let i = 0; i < messages.length; i++) {
    const msgTokens = estimateTokens([messages[i]]);
    if (accumulated + msgTokens > compactBudget) {
      splitIndex = i;
      break;
    }
    accumulated += msgTokens;
    splitIndex = i + 1;
  }

  // Always keep system message in both halves
  const systemMsg = messages.find(m => m.role === "system");
  return {
    toCompact: messages.slice(0, splitIndex),
    toKeep: systemMsg
      ? [systemMsg, ...messages.slice(splitIndex).filter(m => m.role !== "system")]
      : messages.slice(splitIndex),
  };
}
Performance note: Token estimation uses a fast heuristic (words × 1.3) rather than running the actual tokenizer. This makes compaction checks near-instant but introduces ~10% estimation error, which is why SAFETY_MARGIN exists.

The safety timeout wraps the entire compaction pipeline. If summarization takes too long, it aborts and falls through to hard truncation:

// compaction-safety-timeout.ts
const COMPACTION_TIMEOUT_MS = 30_000;

async function withCompactionTimeout<T>(
  fn: () => Promise<T>,
  fallback: () => T,
): Promise<T> {
  const controller = new AbortController();
  const timer = setTimeout(
    () => controller.abort(),
    COMPACTION_TIMEOUT_MS,
  );

  try {
    const result = await fn();
    clearTimeout(timer);
    return result;
  } catch (err) {
    clearTimeout(timer);
    if (controller.signal.aborted) {
      console.warn("Compaction timed out, falling back to truncation");
      return fallback();
    }
    throw err;
  }
}
