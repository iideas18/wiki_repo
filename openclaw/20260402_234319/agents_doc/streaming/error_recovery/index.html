Error Recovery

Focus Deep-Dive

Categorizing, handling, and recovering from LLM streaming errors via model fallback

When an LLM provider returns an error mid-stream — rate limit, context overflow, auth failure, or transient network issue — this module categorizes the error, selects the next model in the fallback chain, and retries transparently. If all models are exhausted, it produces a structured FallbackSummaryError with per-attempt diagnostics.

📚 What is this & why does it matter?

LLM providers are unreliable at scale: APIs rate-limit, tokens expire, context windows are exceeded, and networks drop packets. Without error recovery, a single transient failure would kill an entire agent session. This module ensures the streaming pipeline degrades gracefully — falling back to alternate models, probing recently-failed providers when their cooldowns expire, and surfacing structured diagnostics when all options are exhausted. Understanding this flow is critical for debugging why an agent switched models mid-conversation or why a session ended with a fallback error.

💡 Real-world analogy

Imagine a dispatcher at a taxi company. When a customer calls, the dispatcher tries the nearest available cab. If that driver's radio is down (transient error), they try the next driver. If a driver is on a mandatory break (rate limit cooldown), the dispatcher notes the break end time and skips them for now — but may try again if no other cabs are available and the break should be ending soon. If every single cab in the fleet is unavailable, the dispatcher calls the customer back with a detailed explanation: "Driver A was on break until 3pm, Driver B had a flat tire, Driver C's license expired." That explanation is the FallbackSummaryError.

Overview

Primary role

Catch errors from LLM streaming, categorize them, select fallback models, and retry until success or exhaustion of the fallback chain.

Main inputs

Error objects from provider stream wrappers, the configured fallback model chain, per-provider cooldown state, and auth profile status.

Key decisions

Is this error retryable? Which model to try next? Should we probe a provider that recently failed? Has the abort signal been raised?

Outputs / side effects

Either a successful retry on an alternate model or a FallbackSummaryError carrying per-attempt details and the soonest cooldown expiry time.

How It Works

Error recovery operates as a state machine wrapping the streaming attempt loop. Each attempt either succeeds (returning the response payload) or fails (adding an entry to the fallback summary and advancing to the next model).

Phase 1 — Error Categorization

When a streaming error occurs, the system first categorizes it. Each provider wrapper translates its native error format into one of six canonical categories:

CategoryTriggerRetryableCooldown
rate_limitHTTP 429 or provider-specific rate limit responseYesUses Retry-After header or default 60s
context_overflowHTTP 400 with "context length" or "max tokens" in bodyYes (after compaction)None — triggers backpressure compaction first
timeoutNo response within LLM_IDLE_TIMEOUT_MSYesNone
auth_failureHTTP 401 or 403Only after cooldown expiryToken refresh period from auth-profiles.ts
provider_errorHTTP 500, 502, 503 from the providerYesExponential backoff starting at 1s
transientNetwork errors, connection resets, DNS failuresYesFixed 2s delay
Key detail: The context_overflow category is special: before attempting a fallback, the system first tries to compact the conversation (via the backpressure module). Only if compaction fails or the compacted history still overflows does it proceed to model fallback.

Phase 2 — Model Fallback Chain

The model-fallback.ts module maintains an ordered list of models to try. When the primary model fails, it walks the chain and attempts each one. The chain is configured per-deployment and typically follows the pattern: primary model → same-provider cheaper model → cross-provider equivalent → cross-provider cheaper model.

// model-fallback.ts — core fallback loop
interface FallbackAttempt {
  model: string;
  error: CategorizedError;
  durationMs: number;
  cooldownExpiry: Date | null;
}

async function attemptWithFallback(
  request: StreamRequest,
  fallbackChain: string[],
  signal: AbortSignal,
): Promise<StreamResponse> {
  const attempts: FallbackAttempt[] = [];

  for (const model of fallbackChain) {
    if (signal.aborted) break;

    const provider = getProviderForModel(model);
    if (provider.isInCooldown(model)) {
      if (!shouldAllowCooldownProbeForReason(provider, model)) {
        continue; // skip — cooldown not yet expired
      }
    }

    const start = Date.now();
    try {
      const response = await provider.stream(request, model, signal);
      logFailoverObservation(model, "success", attempts);
      return response;
    } catch (err) {
      const categorized = categorizeError(err, provider);
      attempts.push({
        model,
        error: categorized,
        durationMs: Date.now() - start,
        cooldownExpiry: categorized.cooldownExpiry,
      });
      provider.recordFailure(model, categorized);
      logFailoverObservation(model, "failure", attempts);
    }
  }

  throw new FallbackSummaryError(attempts);
}
Watch out: The fallback chain is iterated once — there is no retry of a model that already failed in the same cycle. If a transient error on the primary model would succeed on immediate retry, it still falls through to the next model. This is intentional: it prioritizes forward progress over optimistic retry on the same provider.

Phase 3 — Cooldown Probing

When a provider is in cooldown but the cooldown window is nearly expired (remainingMs < PROBE_THRESHOLD_MS), the system may issue a "cooldown probe" — a retry attempt that would normally be skipped. This enables faster recovery when rate limits expire mid-fallback-chain.

// shouldAllowCooldownProbeForReason()
const PROBE_THRESHOLD_MS = 5000;

function shouldAllowCooldownProbeForReason(
  provider: Provider,
  model: string,
): boolean {
  const cooldown = provider.getCooldownState(model);
  if (!cooldown) return true; // not in cooldown

  const remainingMs = cooldown.expiresAt.getTime() - Date.now();
  if (remainingMs <= 0) return true; // cooldown expired

  // Only probe if nearly expired and the reason was rate_limit or transient
  if (remainingMs < PROBE_THRESHOLD_MS) {
    return cooldown.reason === "rate_limit" || cooldown.reason === "transient";
  }

  return false;
}

Phase 4 — FallbackSummaryError

When all models in the fallback chain have been tried and failed, the system creates a FallbackSummaryError. This error carries structured data for every attempt — which model was tried, what error it returned, how long it took, and when its cooldown expires. The soonestCooldownExpiry property tells the caller when the earliest retry opportunity will be available.

Failure mode: If the abort signal fires during the fallback loop, the FallbackSummaryError will contain only partial attempt data. The aborted flag is set to true so callers know the error may not reflect the full fallback chain.

Abort Handling

The abort.ts module manages stream abort propagation. When the user cancels or the system determines the stream should stop, the abort signal is raised. However, to prevent data loss, the signal propagation includes a settle timeout (STEER_ABORT_SETTLE_TIMEOUT_MS = 5000) that allows in-flight chunks to drain before the connection is terminated.

The state diagram shows two levels: the outer error-recovery state machine and the inner streaming state. Note that the StopReasonCheck state inside streaming can transition to ErrorDetected when attempt.stop-reason-recovery.ts identifies an unexpected stop reason (e.g., content_filter, premature length stop). This means error recovery handles not just explicit errors but also abnormal completions.

Design insight: By modelling stop-reason anomalies as errors, the system reuses the fallback chain for both hard failures (HTTP 500) and soft failures (content filter triggered). This unification simplifies the error-handling surface and ensures all failure modes have a consistent recovery path.

Error categorization maps provider-specific errors to canonical categories. Each provider wrapper implements the categorizeError() method:

// error-categorizer.ts
type ErrorCategory =
  | "rate_limit"
  | "context_overflow"
  | "timeout"
  | "auth_failure"
  | "provider_error"
  | "transient";

interface CategorizedError {
  category: ErrorCategory;
  retryable: boolean;
  cooldownExpiry: Date | null;
  originalError: Error;
  providerMessage: string;
}

function categorizeError(err: unknown, provider: Provider): CategorizedError {
  if (err instanceof TimeoutError) {
    return { category: "timeout", retryable: true, cooldownExpiry: null,
             originalError: err, providerMessage: "LLM idle timeout" };
  }

  const status = (err as any)?.status ?? 0;
  if (status === 429) {
    const retryAfter = parseRetryAfterHeader(err);
    return { category: "rate_limit", retryable: true,
             cooldownExpiry: new Date(Date.now() + retryAfter),
             originalError: err as Error,
             providerMessage: `Rate limited, retry after ${retryAfter}ms` };
  }

  if (status === 401 || status === 403) {
    return { category: "auth_failure", retryable: false,
             cooldownExpiry: null, originalError: err as Error,
             providerMessage: "Authentication failed" };
  }

  if (status >= 500) {
    return { category: "provider_error", retryable: true,
             cooldownExpiry: new Date(Date.now() + 1000),
             originalError: err as Error,
             providerMessage: `Provider returned ${status}` };
  }

  if (isContextOverflowError(err)) {
    return { category: "context_overflow", retryable: true,
             cooldownExpiry: null, originalError: err as Error,
             providerMessage: "Context window exceeded" };
  }

  return { category: "transient", retryable: true,
           cooldownExpiry: new Date(Date.now() + 2000),
           originalError: err as Error,
           providerMessage: String(err) };
}

The FallbackSummaryError class aggregates all attempt data and computes the soonest cooldown expiry. This is what the caller receives when all models are exhausted:

// model-fallback.ts — FallbackSummaryError
class FallbackSummaryError extends Error {
  readonly attempts: FallbackAttempt[];
  readonly soonestCooldownExpiry: Date | null;
  readonly aborted: boolean;

  constructor(attempts: FallbackAttempt[], aborted = false) {
    const models = attempts.map(a => a.model).join(", ");
    super(`All fallback models exhausted: ${models}`);
    this.name = "FallbackSummaryError";
    this.attempts = attempts;
    this.aborted = aborted;

    // Find the earliest cooldown expiry across all attempts
    this.soonestCooldownExpiry = attempts
      .map(a => a.cooldownExpiry)
      .filter((d): d is Date => d !== null)
      .sort((a, b) => a.getTime() - b.getTime())[0] ?? null;
  }

  get retryableAt(): Date | null {
    return this.soonestCooldownExpiry;
  }
}
Key detail: The soonestCooldownExpiry enables smart retry scheduling upstream. Rather than using a fixed backoff, the caller can wait exactly until the first provider becomes available again.

Failover observations are logged for every attempt, successful or not. This provides an audit trail for debugging model switching:

// failover-observation.ts
interface FailoverObservation {
  timestamp: Date;
  model: string;
  outcome: "success" | "failure";
  errorCategory?: ErrorCategory;
  durationMs: number;
  attemptIndex: number;
  totalAttempts: number;
}

function logFailoverObservation(
  model: string,
  outcome: "success" | "failure",
  attempts: FallbackAttempt[],
): void {
  const observation: FailoverObservation = {
    timestamp: new Date(),
    model,
    outcome,
    errorCategory: outcome === "failure"
      ? attempts[attempts.length - 1]?.error.category
      : undefined,
    durationMs: outcome === "failure"
      ? attempts[attempts.length - 1]?.durationMs ?? 0
      : 0,
    attemptIndex: attempts.length - 1,
    totalAttempts: attempts.length,
  };
  telemetry.record("failover", observation);
}
