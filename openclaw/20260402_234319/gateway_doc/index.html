Gateway — Control Plane & Authentication

The Front Door of OpenClaw

Gateway is the control plane that manages every connection entering the system — from device authentication and rate limiting to boot orchestration, message routing, session lifecycle, and assistant identity resolution. It is the single entry point through which all client traffic flows before reaching agents.

What Is This & Why Does It Exist?

Every production system needs a front door — something that decides who gets in, how services start up, and where messages go. The Gateway module is that front door for OpenClaw.

💡 Real-world analogy

Think of Gateway as an airport terminal. The Auth subsystem is passport control — it checks your credentials (token, password, Tailscale identity, or device pairing) and decides whether to let you through. Rate limiting is the queue-management system that prevents the terminal from being overwhelmed. Boot is the pre-flight checklist that ensures all ground systems are operational before any planes depart. Routing is the air-traffic controller that dispatches each passenger to the correct gate (session) and ensures the right pilot (assistant identity) is assigned to each flight.

Narrated Walkthrough

Follow the journey of a single client request through the Gateway, step by step.

Step 1 — Client Initiates Connection

A CLI, Web UI, or mobile client opens a WebSocket connection, sending ConnectParams that include the client version, requested auth method, and optional device token.

Step 2 — Credential Resolution

The Gateway calls resolveGatewayCredentialsFromConfig() to determine which credentials apply. It checks environment variables, config files, and secret references in precedence order defined by GatewayCredentialPrecedence.

Step 3 — Auth Mode Resolution

resolveGatewayAuth() examines the config to determine the active auth mode: "none", "token", "password", or "trusted-proxy". If both token and password are configured, assertExplicitGatewayAuthModeWhenBothConfigured() enforces that an explicit mode is declared.

Step 4 — Rate Limit Check

Before evaluating credentials, the AuthRateLimiter checks the client IP against a sliding-window counter. The RateLimitConfig defines maxAttempts (default 10), windowMs (60 s), and lockoutMs (5 min). If the client is locked out, the request is rejected with retryAfterMs.

Step 5 — Authentication

authorizeGatewayConnect() evaluates the request against the resolved auth mode. It supports six methods: none, token, password, tailscale, device-token, and trusted-proxy. On failure, rateLimiter.recordFailure() is called.

Step 6 — Protocol Validation

All incoming frames are validated by the protocol layer (80+ JSON-schema validators). validateRequestFrame() and validateConnectParams() ensure type safety before any processing.

Step 7 — Boot Sequence

On first connection, runBootOnce() reads BOOT.md from the workspace directory and executes the bootstrap instructions. The result is a BootRunResult with status "ran", "skipped", or "failed".

Step 8 — Request Routing

Authenticated requests are dispatched through GatewayRequestHandlers — a Record<string, GatewayRequestHandler> that maps RPC method names to handler functions. Each handler receives a GatewayRequestHandlerOptions containing the request frame, client info, and full GatewayRequestContext.

Step 9 — Session Management

The session manager creates or resumes a GatewaySessionRow (32+ fields). It tracks SessionRunStatus ("running", "done", "failed", "killed", "timeout"), token usage, cost estimates, and derived titles. Lifecycle events are persisted via persistGatewaySessionLifecycleEvent().

Step 10 — Assistant Identity

resolveAssistantIdentity() determines the active assistant’s name, avatar, and emoji from config and workspace files. The default is DEFAULT_ASSISTANT_IDENTITY (agentId: "main", name: "Assistant"). Identity fields are bounded by MAX_ASSISTANT_NAME (50), MAX_ASSISTANT_AVATAR (200), and MAX_ASSISTANT_EMOJI (16).

Sub-Modules

🔒 Auth

Authentication, device pairing, rate limiting, install policies, and auth-mode configuration.

  • resolveGatewayAuth() — mode resolution
  • authorizeGatewayConnect() — connection auth
  • AuthRateLimiter — sliding-window rate limiter

🚀 Boot

Startup orchestration, capability negotiation, and health checks for gateway initialization.

  • runBootOnce() — one-shot bootstrap
  • BOOT.md execution — workspace init
  • Health monitoring integration

🔌 Routing

Message dispatch, session lifecycle management, assistant identity, and RPC request handling.

  • GatewayRequestHandlers — RPC dispatch
  • GatewaySessionRow — session lifecycle
  • resolveAssistantIdentity() — identity config
