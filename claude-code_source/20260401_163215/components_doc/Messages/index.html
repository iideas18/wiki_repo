Renders the conversation thread with virtual scrolling and streaming support

The Messages system is a sophisticated React component hierarchy that normalizes, groups, virtualizes, and renders every message in the Claude Code REPL. It handles 15+ message types, streaming tool output, collapsible groups, and incremental search across conversations of any size.

📚 What is this & why does it exist?

The Messages system takes raw API responses and turns them into the scrollable conversation you see in the terminal. It merges streaming partial updates with stored messages, groups related tool operations together, and uses virtual scrolling so even a 2,800-message conversation stays smooth. Think of it as the display engine that translates the AI's internal data into something a human can read and interact with.

💡 Real-world analogy

Imagine a live news ticker on a TV screen. Raw feeds arrive from dozens of reporters (message types), a producer groups related stories (message grouping), the ticker only shows a few lines at a time but you can scroll back (virtual scrolling), and breaking news appears letter-by-letter as it streams in (streaming deltas). The Messages system is that entire broadcast pipeline—from raw wire feeds to polished, scrollable on-screen text.

Performance Optimizations

React Compiler Integration

All message components use the React Compiler's _c(N) pattern for automated memoization. The Message dispatcher allocates 94 cache slots, while MessageRow uses 64. This eliminates manual useMemo/useCallback boilerplate while achieving equivalent or better performance. The compiler detects prop changes at a granular level and only re-executes the affected code paths.

Virtualization Strategy

VirtualMessageList renders only ~60 items at a time using the useVirtualScroll hook. This strategy is critical for conversations exceeding 200 messages, where full DOM rendering would cause noticeable frame drops.

Key optimizations include:

  • Append-only key arrays — New messages are pushed without reallocating the full array
  • WeakMap height cache — Measured heights are cached per message and invalidated only on terminal column change
  • Stable callbacks via itemKey threading — Reduced closure allocations by 16% of GC time during fast scroll
  • Incremental search index — warmSearchIndex() pre-lowers all text in a single pass for O(1) per-keystroke matching

Custom Memo Comparators

Both MessageRow and Messages use custom React.memo comparators instead of the default shallow equality. This prevents prop spreading from pinning full message arrays in the compiler's cache, which would accumulate ~1-2 MB over a 7-turn conversation session. The custom comparator checks only the specific fields that affect rendering.

Search Index Pre-Warming

The warmSearchIndex() API pre-lowers all message text into a single searchable index. This is performed once when the user opens the search UI, and subsequent keystrokes perform O(1) lookups against the pre-built index rather than re-scanning all messages. The warm call returns elapsed milliseconds for performance diagnostics.

Logo Deep Memoization

The LogoHeader component uses deep memoization to prevent cascade re-renders. In a 2,800-message session, naive re-rendering caused 150K+ writes per frame. Deep memoization of the logo component eliminated this overhead entirely.

Example: Custom Memo Comparator (MessageRow)

// Custom memo comparator avoids prop spreading that would pin
// full message arrays in React Compiler cache (~1-2 MB over 7 turns)
function areMessageRowPropsEqual(
  prev: Props,
  next: Props,
): boolean {
  return (
    prev.message === next.message &&
    prev.hasContentAfter === next.hasContentAfter &&
    prev.isUserContinuation === next.isUserContinuation &&
    prev.inProgressToolUseIDs === next.inProgressToolUseIDs &&
    prev.streamingToolUseIDs === next.streamingToolUseIDs &&
    prev.columns === next.columns &&
    prev.isLoading === next.isLoading &&
    prev.lastThinkingBlockId === next.lastThinkingBlockId
  );
}

export const MessageRow = memo(MessageRowImpl, areMessageRowPropsEqual);

Example: Forward Scanner for UI State

// Determines whether meaningful content exists after a given index
// Used to decide if collapsed groups should show "loading" state
export function hasContentAfterIndex(
  messages: RenderableMessage[],
  index: number,
  tools: Tools,
  streamingToolUseIDs: Set<string>,
): boolean {
  for (let i = index + 1; i < messages.length; i++) {
    const msg = messages[i]!;
    // Skip thinking blocks, collapsible tool results, and tool_result
    if (msg.type === 'assistant' && hasThinkingContent(msg)) continue;
    if (isCollapsibleToolUse(msg, tools)) continue;
    return true; // Found real content
  }
  return false;
}

Example: Brief Mode Filtering

// Brief mode suppresses non-essential tool output for cleaner display
export function filterForBriefTool<T extends { type: string }>(
  messages: T[],
  briefToolNames: Set<string>,
): T[] {
  return messages.filter(msg => {
    if (msg.type !== 'grouped_tool_use') return true;
    const toolMsg = msg as unknown as GroupedToolUseMessage;
    // Keep message only if at least one tool is not in brief list
    return toolMsg.toolUses.some(
      tu => !briefToolNames.has(tu.name),
    );
  });
}

// dropTextInBriefTurns removes assistant text between brief tool uses
export function dropTextInBriefTurns<T extends { type: string }>(
  messages: T[],
  briefToolNames: Set<string>,
): T[] {
  // Identifies "brief turns" and drops text-only assistant
  // messages within them, keeping the conversation concise
  return messages.filter((msg, i) => {
    if (msg.type !== 'assistant') return true;
    const prevIsBrief = i > 0 && isBriefTool(messages[i - 1]!);
    const nextIsBrief = i < messages.length - 1 && isBriefTool(messages[i + 1]!);
    return !(prevIsBrief && nextIsBrief);
  });
}
