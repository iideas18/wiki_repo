📚 What is this & why does it exist?

Claude Code is a terminal-based AI assistant that acts as an intelligent pair programmer. Rather than a simple chatbot, it is an agentic system that can read files, write code, run shell commands, search codebases, and orchestrate multi-step development workflows. This wiki documents the internal source architecture of the Claude Code application itself.

💡 Real-world analogy

Think of Claude Code like a fully-staffed software development office. The REPL is the front desk where you talk to the receptionist (prompt input). Your request goes to the Query Engine (project manager) who figures out which Tools (specialist departments—file editing, shell commands, web search) to dispatch. The Services layer is the back-office infrastructure (API connections, authentication, analytics). Commands are like speed-dial buttons for common requests. And the State system is the shared whiteboard that keeps everyone in sync.

Request Lifecycle

sequenceDiagram
  participant User
  participant REPL as screens/REPL.tsx
  participant QE as query.ts
  participant API as services/api/
  participant Tools as tools/*
  participant FS as File System

  User->>REPL: Type prompt or /command
  REPL->>QE: Submit query with context
  QE->>QE: Build system prompt + memory
  QE->>API: Stream API request
  API-->>QE: Assistant response (text + tool_use)
  loop Tool Execution Loop
    QE->>Tools: Execute tool (bash, file_edit, grep...)
    Tools->>FS: Read/write files, run commands
    FS-->>Tools: Results
    Tools-->>QE: Tool result
    QE->>API: Continue with tool results
    API-->>QE: Next response
  end
  QE-->>REPL: Final response
  REPL-->>User: Render markdown + diffs
Key insight: Claude Code follows an agentic loop: the model produces tool calls, the runtime executes them, and results feed back to the model until the task is complete. The Query Engine orchestrates this loop with token budgets, compaction, and permission checks at every step.

How the Core Engine Connects

The query engine sits at the center, orchestrating tool execution and model communication. Here's how a typical agentic loop flows across module boundaries:

sequenceDiagram
  participant REPL as REPL (screens/)
  participant State as AppState (state/)
  participant QE as QueryEngine (query.ts)
  participant API as API Client (services/api/)
  participant Tools as Tool Registry (tools.ts)
  participant Bash as BashTool
  participant FE as FileEditTool
  participant Perms as Permissions (utils/)

  REPL->>State: setMessages(userInput)
  REPL->>QE: runQuery(messages, tools)
  QE->>API: stream(systemPrompt + messages)
  API-->>QE: tool_use: bash(command)
  QE->>Perms: checkPermission(bash, command)
  Perms-->>QE: allowed (or prompt user)
  QE->>Tools: findToolByName(Bash)
  Tools->>Bash: execute(command)
  Bash-->>QE: stdout + stderr
  QE->>API: tool_result(output)
  API-->>QE: tool_use: file_edit(path, diff)
  QE->>FE: execute(path, diff)
  FE-->>QE: success
  QE->>API: tool_result(applied)
  API-->>QE: text(Done! I edited the file.)
  QE->>State: appendAssistantMessage
  QE-->>REPL: render response
Key insight: The Query Engine owns the agentic loop. Tools are stateless executors. The permission system gates every tool invocation. AppState is the single source of truth for UI rendering. The API client handles streaming, retries, and rate limiting.
