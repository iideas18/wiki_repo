utils/sandbox/ — Sandbox Isolation System

OS-level isolation for tool execution restricting filesystem, network, and command access

The sandbox module wraps the @anthropic-ai/sandbox-runtime library with Claude Code-specific settings integration. It enforces filesystem read/write restrictions, network domain allowlists, git bare-repo exploit protection, and platform-specific sandboxing via bubblewrap on Linux/WSL and sandbox-exec on macOS. Settings from 5 sources are merged into a unified SandboxRuntimeConfig.

📚 What is this & why does it exist?

The sandbox module provides OS-level containment for every shell command the AI runs. When you ask Claude Code to execute npm install, the command doesn't run with your full user permissions—it runs inside a restricted environment where it can only touch files in your project, access approved network domains, and cannot modify system-critical files. This prevents accidental (or malicious) damage even if the AI makes a mistake.

💡 Real-world analogy

Think of a chemical laboratory's fume hood. Scientists (tools) can perform experiments (commands) inside the hood, but the hood contains any dangerous fumes (filesystem writes, network access) and prevents them from reaching the rest of the lab (system). The hood has adjustable vents (configuration) that can be opened for specific chemicals (allowed domains/paths) while keeping everything else contained. Some experiments are too dangerous even for the hood (excluded commands) and must be performed in the open with explicit supervisor approval.

Architecture

The sandbox adapter sits between Claude Code's settings system and the @anthropic-ai/sandbox-runtime library. It translates permission rules and settings from 5 sources into a unified SandboxRuntimeConfig, adds hardcoded security protections, and manages the sandbox lifecycle including initialization, command wrapping, and post-execution cleanup.

Security Protections

Settings File Escape Prevention

The sandbox unconditionally denies write access to all settings files (.claude/settings.json, .claude/settings.local.json, etc.) across all 5 sources. This is the single most important security measure in the sandbox—it prevents a sandboxed command from modifying its own permissions by editing the settings file that controls the sandbox configuration. Even if a command escapes other restrictions, it cannot weaken the sandbox itself.

Git Bare-Repo Exploit Defense

An attacker could plant files like HEAD, objects/, refs/, hooks/, and config in the working directory during a sandboxed command. If git later runs outside the sandbox, it might interpret these as a bare git repository and execute hooks. The scrubBareGitRepoFiles() function deletes these planted files after every sandboxed command as a defense-in-depth measure. The function maintains a list of bare-repo paths (bareGitRepoScrubPaths) that are checked and cleaned during cleanupAfterCommand().

Worktree Write Access

When the working directory is a git worktree, the sandbox automatically adds the main repository path to the write allowlist. This enables symmetric access—changes made in a worktree can affect shared refs and objects in the main repository, which is essential for operations like git commit and git push.

Skills Directory Protection

The .claude/skills directory is always deny-listed for writes to prevent sandboxed commands from tampering with installed skills or planting malicious skill files.

Managed Domain Policy

When policySettings.sandbox.network.allowManagedDomainsOnly is true, the sandbox ask callback is wrapped to enforce that only managed (pre-approved) domains can be added. User-requested domain additions are silently blocked. This is a policy-level control for enterprise deployments that need to restrict outbound network access to approved endpoints only, preventing data exfiltration through unauthorized domains.

Sandbox Lifecycle

The sandbox follows a well-defined lifecycle from initialization through command execution to cleanup. The lifecycle ensures that settings changes are picked up dynamically and that post-execution cleanup always runs, even if the command fails.

Code Examples

Example: Path Pattern Resolution for Sandbox

// Resolves Claude Code-specific path patterns for sandbox-runtime
// Handles two special prefixes before delegating to the runtime library
export function resolvePathPatternForSandbox(
  pattern: string,
  source: SettingSource,
): string {
  // "//path" → absolute from filesystem root ("/path")
  if (pattern.startsWith('//')) {
    return pattern.slice(1);
  }

  // "/path" → relative to the settings file directory
  if (pattern.startsWith('/')) {
    const settingsDir = getSettingsDirForSource(source);
    return join(settingsDir, pattern.slice(1));
  }

  // "~/path", "./path", "path" → passed through for sandbox-runtime
  return pattern;
}

Example: Hardcoded Write Protections

// convertToSandboxRuntimeConfig() always adds these write denials:
const hardcodedDenyWrite: string[] = [];

// Protect settings files from sandbox escape
for (const source of SETTING_SOURCES) {
  hardcodedDenyWrite.push(getSettingsFilePath(source));
}

// Protect .claude/skills from tampering
hardcodedDenyWrite.push(join(cwd, '.claude', 'skills'));

// Protect against bare git repo exploits
// (attacker plants HEAD, objects/, refs/, hooks/, config)
const bareGitPaths = ['HEAD', 'objects', 'refs', 'hooks', 'config'];
for (const p of bareGitPaths) {
  hardcodedDenyWrite.push(join(cwd, p));
}

// Add worktree main repo to allowlist for symmetric access
if (worktreeMainRepoPath) {
  config.filesystem.allowWrite.push(worktreeMainRepoPath);
}

Example: Detecting Git Worktree for Sandbox

// Detects if cwd is a git worktree and returns the main repo path
// so the sandbox can add it to the write allowlist
async function detectWorktreeMainRepoPath(
  cwd: string,
): Promise<string | null> {
  const dotGitPath = join(cwd, '.git');

  try {
    const content = await readFile(dotGitPath, 'utf8');

    // Regular repos: .git is a directory (not a file)
    // Worktrees: .git is a file containing "gitdir: path"
    if (!content.startsWith('gitdir: ')) return null;

    const gitDir = content.slice('gitdir: '.length).trim();
    // Resolve relative paths against cwd
    const absoluteGitDir = resolve(cwd, gitDir);

    // Walk up from the gitdir to find the main repo
    // e.g., /repo/.git/worktrees/feature -> /repo
    const mainGitDir = join(absoluteGitDir, '..', '..');
    return resolve(mainGitDir, '..');
  } catch {
    return null; // Not a worktree or .git doesn't exist
  }
}
