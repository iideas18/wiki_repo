💡 Think of it like a building renovation plan

When a building undergoes renovation, each phase has a numbered blueprint that transforms the structure step by step — move this wall, rewire that circuit, upgrade the plumbing. Tenants don't have to move out; the work happens around them. The migrations module works the same way: each numbered migration transforms user settings from one version to the next, ensuring that existing configurations survive application updates without data loss or manual intervention.

Configuration

Each migration implements the Migration interface and is auto-discovered by the runner. The version stamping mechanism prevents re-execution of already-applied migrations:

// Migration interface from types.ts
export interface Migration {
  readonly version: number;
  readonly name: string;
  readonly description: string;

  up(settings: SettingsData): SettingsData;
  down(settings: SettingsData): SettingsData;

  validate(settings: SettingsData): boolean;
}

// Example migration: 004-auto-updates.ts
export const migration004: Migration = {
  version: 4,
  name: 'auto-updates',
  description: 'Add autoUpdates preference from legacy boolean',

  up(settings) {
    const legacy = settings.checkForUpdates ?? true;
    delete settings.checkForUpdates;
    return {
      ...settings,
      autoUpdates: {
        enabled: legacy,
        channel: 'stable',
        frequency: 'weekly',
      },
    };
  },

  down(settings) {
    const enabled = settings.autoUpdates?.enabled ?? true;
    delete settings.autoUpdates;
    return { ...settings, checkForUpdates: enabled };
  },

  validate(settings) {
    return typeof settings.autoUpdates === 'object'
      && typeof settings.autoUpdates.enabled === 'boolean';
  },
};

The runner executes migrations in strict version order. If any migration fails validation, the runner restores the backup and reports the failure without corrupting settings.
