PR Review Toolkit — Multi-Agent PR Analysis

6 Specialized Review Agents for PR Analysis

📚 What is this & why does it exist?

PR Review Toolkit deploys 6 specialized agents to analyze your pull request from different angles — comments, tests, silent failures, type design, code quality, and simplification opportunities. Each agent produces findings with confidence scores, and only results meeting the ≥80 threshold reach the developer. This eliminates noisy, low-value feedback and ensures every review comment is worth reading.

💡 Real-world analogy

Think of a hospital emergency room triage system. Six specialists (cardiologist, neurologist, radiologist, etc.) each examine the patient independently and write up their findings with a severity score. Only findings above a critical threshold get escalated to the attending physician. The PR Review Toolkit works the same way: 6 expert agents examine your code diff, each scores their findings, and only high-confidence issues make it to your review summary.

Agent Profiles

💬 comment-analyzer

Scans inline comments, TODOs, FIXMEs, HACKs, and documentation gaps. Identifies stale comments that no longer match the code, missing JSDoc/docstring annotations on public APIs, and TODO items that should be tracked as issues.

  • Model: Sonnet
  • Focus: Documentation quality
  • Confidence avg: 85-92

🧪 pr-test-analyzer

Evaluates test coverage for changed code. Detects missing edge-case tests, untested error paths, and test quality issues like assertions that always pass. Cross-references changed functions against test files.

  • Model: Sonnet
  • Focus: Test completeness
  • Confidence avg: 82-90

🕷️ silent-failure-hunter

Hunts for swallowed exceptions, empty catch blocks, missing error propagation, and functions that fail silently. Detects patterns like catch(e) {}, missing await on async calls, and unchecked return values.

  • Model: Sonnet
  • Focus: Error handling
  • Confidence avg: 88-95

🔬 type-design-analyzer

Reviews TypeScript/Python type safety, interface design, generic usage, and type narrowing patterns. Flags any types, overly broad union types, missing discriminated unions, and inconsistent type parameter naming.

  • Model: Sonnet
  • Focus: Type system quality
  • Confidence avg: 80-88

🐛 code-reviewer

General-purpose code review focusing on logic bugs, race conditions, security vulnerabilities, and performance issues. Uses the Opus model for highest accuracy on subtle bugs that require deep reasoning.

  • Model: Opus
  • Focus: Bug detection
  • Confidence avg: 85-96

✂️ code-simplifier

Identifies over-engineering, redundant abstractions, unnecessary indirection, and code that could be simplified. Suggests concrete simplifications with before/after examples.

  • Model: Sonnet
  • Focus: Complexity reduction
  • Confidence avg: 78-85

Confidence Scoring

Each agent assigns a confidence score (0–100) to every finding. The scoring considers:

FactorWeightDescription
Pattern certainty40%How clearly the code matches a known anti-pattern
Context evidence30%Supporting evidence from surrounding code and project conventions
Severity impact20%Potential impact if the finding is a real issue
False positive risk10%Likelihood this is a false positive based on code patterns
Only findings with confidence ≥ 80 are included in the final output. This eliminates ~40% of raw findings, dramatically improving signal-to-noise ratio.

/review-pr --agents=type-design-analyzer

Review Pipeline Details

Pipeline Stages

StageDurationDescription
1. Validation~2sVerify git repository state, check for uncommitted changes, identify diff scope
2. Context Loading~3sRead CLAUDE.md guidelines, extract project conventions and review standards
3. Summarization~5sGenerate change summary with file categories, impact assessment, and risk areas
4. Parallel Review~30sDispatch to 4-6 agents simultaneously, each analyzing their specialty area
5. Confidence Filter~1sAggregate findings, apply ≥80 threshold, de-duplicate overlapping findings
6. Output~2sFormat markdown report grouped by agent, sorted by confidence descending

De-duplication Strategy

When multiple agents flag the same code location, the pipeline de-duplicates using these rules:

  • Same file + same line range + overlapping description → keep highest-confidence finding
  • Same file + different lines + similar pattern → group under a single “pattern” heading
  • Different files + same pattern (e.g., missing error handling) → list all locations, one finding
