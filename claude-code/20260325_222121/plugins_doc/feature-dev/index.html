📚 What is this & why does it exist?

Feature Dev enforces a disciplined approach to building features in large codebases. Rather than diving straight into coding, it mandates understanding the existing code first (via parallel code-explorer agents), designing the architecture explicitly (via code-architect), implementing in small focused steps, and reviewing quality (via code-reviewer with Opus). Each phase produces artifacts that feed the next, preventing the “just hack it in” anti-pattern.

💡 Real-world analogy

Imagine building an addition to a house. You wouldn't start hammering immediately. First, you survey the existing structure (Phase 1-2: code-explorer scouts the codebase). Then an architect draws blueprints (Phase 3-4: code-architect designs the solution). Next, contractors build it phase by phase (Phase 5: implementation). Finally, a building inspector verifies everything is up to code (Phase 6-7: code-reviewer checks quality). Feature Dev is that building process for software.

Workflow Example

Basic Usage

The /feature-dev command accepts a natural-language feature description and guides the entire development process through 7 structured phases.

# Start a feature development workflow
/feature-dev "Add JWT authentication to the API layer"

# With more specific description
/feature-dev "Implement rate limiting middleware with Redis backend, \
  supporting per-user and per-endpoint limits"

# The command will automatically:
# 1. Parse your request into requirements
# 2. Launch 3 parallel code-explorers
# 3. Design architecture via code-architect
# 4. Create implementation plan
# 5. Write the code
# 6. Review with code-reviewer (Opus)
# 7. Polish and prepare commit

Phase Output Artifacts

Phase 2: Exploration Report

Each code-explorer instance produces a focused report:

  • Relevant file inventory with descriptions
  • Existing patterns that should be followed
  • Dependencies and import chains
  • Test patterns used in the project

Phase 3: Architecture Blueprint

The code-architect produces a structured design:

  • Component diagram with interfaces
  • Data flow between new and existing modules
  • API surface area (functions, types, exports)
  • Migration path for existing code

Phase 6: Quality Report

The code-reviewer (Opus) produces findings:

  • Logic correctness analysis
  • Edge cases and error handling gaps
  • Test coverage assessment
  • Performance and security observations

Design Patterns Enforced

The feature-dev workflow encourages several design patterns through its phased approach:

PatternPhaseHow It's Enforced
Understand Before Coding1-2Exploration must complete before any code is written
Design Before Build3-4Architecture blueprint required before implementation begins
Small Focused Changes5Implementation plan breaks work into discrete, reviewable steps
Review Before Ship6-7Opus-powered review catches issues before commit
Convention ConformityAllCLAUDE.md guidelines consulted at every phase

Error Recovery

If any phase fails or produces insufficient results:

  • Explorer failure: Re-run with adjusted search patterns and expanded scope
  • Architect rejection: Return to Phase 2 with additional exploration questions
  • Reviewer findings: Loop back to Phase 5 to address issues, then re-review
  • Build failures: Diagnose with Bash tool, fix, and re-verify before Phase 7

Configuration Reference

Agent Model Selection

Model selection follows a cost-quality optimization: Sonnet handles high-volume exploration and design tasks efficiently, while Opus is reserved for the single code-reviewer pass where reasoning depth has the highest impact on finding subtle bugs.

ParameterDefaultDescription
explorer.modelsonnetModel for code-explorer agents (cost-efficient analysis)
architect.modelsonnetModel for code-architect (design quality)
reviewer.modelopusModel for code-reviewer (highest quality review)
explorer.parallel3Number of parallel code-explorer instances
explorer.toolsRead,Grep,Glob,LS,BashTools available to explorer agents
architect.toolsRead,Grep,Glob,WriteTools available to architect agent
reviewer.toolsRead,Grep,Glob,BashTools available to reviewer agent (includes test runner)
