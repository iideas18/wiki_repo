📚 What is this & why does it exist?

Learning Output Style is a dual-mode SessionStart hook that transforms Claude Code from a code-generation tool into an interactive teaching assistant. In Learning Mode, Claude identifies decision points — moments where meaningful engineering choices must be made — and pauses to let the user write that code themselves, offering guidance rather than solutions. In Explanatory Mode, it provides ★ Insight blocks just like the Explanatory Output Style plugin. The result is a workflow that teaches by doing, not just by telling.

💡 Real-world analogy

Imagine a driving instructor who handles the boring highway stretches but hands you the wheel at every intersection, roundabout, and parallel-parking spot. They don’t just say “turn left” — they explain why this turn is tricky (blind corner, yield sign, pedestrian crossing) and let you practice it. The Learning Output Style works the same way: Claude handles boilerplate and configuration, but at every meaningful decision point — error handling strategy, algorithm choice, data structure selection — it hands the keyboard back to you with context about what matters and why.

Architecture

The plugin operates through a single SessionStart hook that injects dual-mode behavior instructions. Claude dynamically switches between implementing code directly and pausing for user participation based on whether the current task involves a decision point.

Dual Operating Modes

🎓 Learning Mode

Activated when Claude encounters a decision point — a moment requiring genuine engineering judgment.

  • Identifies the decision type (business logic, error handling, algorithm, etc.)
  • Provides context: requirements, constraints, trade-offs
  • Pauses and asks user to write the implementation
  • Reviews user’s code with constructive feedback
  • Suggests improvements without rewriting

💡 Explanatory Mode

Activated for straightforward code that doesn’t benefit from user participation.

  • Claude implements the code directly
  • Adds ★ Insight blocks with 2–3 educational points
  • Covers implementation rationale and pattern usage
  • Same behavior as the Explanatory Output Style plugin
  • Keeps momentum on non-educational tasks

Decision Point Criteria

Claude determines whether to pause for user participation by evaluating whether the current task falls into one of five decision point categories:

Decision Point TypeDescriptionExample
Business LogicDomain rules and validation that encode business requirementsPricing calculation, eligibility checks, status transitions
Error HandlingRecovery strategies, retry policies, and failure modesWhat to do when an API call fails, timeout handling
Algorithm ChoiceSelecting between algorithms with different performance trade-offsSorting strategy for partially-sorted data, search approach
Data StructuresChoosing the right data structure for access patternsMap vs. array for lookup-heavy operations, tree vs. flat list
Design PatternsArchitectural decisions affecting extensibility and couplingStrategy vs. switch, observer vs. callback, composition vs. inheritance

Auto-Implement Criteria

Claude implements these categories directly without pausing, as they don’t provide meaningful learning opportunities:

CategoryRationale
Boilerplate & scaffoldingRepetitive code with no decisions to make
Obvious implementationsSingle correct approach with no trade-offs
Configuration filesSyntax-driven, not judgment-driven
Simple CRUD operationsWell-established patterns, low learning value
Import statements & setupMechanical, not educational

Usage Examples

Learning Mode in Action

✋ Decision Point — Error Handling Strategy
You need to handle the case where the external payment API returns a 503 (Service Unavailable).

Consider: Should we retry immediately? Use exponential backoff? Fail fast and notify the user? Queue for later processing?
Context: This is a checkout flow — the user is waiting. Average 503 duration for this API is 2–5 seconds.

Please write the error handling logic for this case.

Explanatory Mode in Action

// Claude auto-implements middleware setup (no decision point)
app.use(express.json({ limit: '10mb' }));
app.use(cors({ origin: config.allowedOrigins }));
app.use(helmet());
★ Insight — Middleware Ordering
• Body parsing (express.json) comes first because downstream middleware and routes need parsed request bodies.
• helmet() sets security headers — placing it early ensures all responses get protected, even error responses from later middleware.
