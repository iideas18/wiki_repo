Oclgrind — Virtual OpenCL Device Simulator

LLVM-Based OpenCL Interpreter, Debugger & Analysis Framework

Oclgrind is a virtual OpenCL device simulator that interprets and executes OpenCL kernels on a software-emulated device built on LLVM IR. It provides a comprehensive platform for detecting memory access errors, data races, barrier divergence, and uninitialized memory usage in OpenCL programs, with an interactive kernel debugger and instruction profiling capabilities.

📚 What is this & why does it exist?

Oclgrind is a software-based OpenCL device that simulates kernel execution by interpreting LLVM IR instructions one by one. Instead of running your OpenCL code on real GPU hardware, Oclgrind executes it in a controlled virtual environment where every memory access, every barrier, and every atomic operation can be inspected and validated. This enables detection of bugs that are nearly impossible to find on actual hardware.

💡 Real-world analogy

Think of Oclgrind like a slow-motion instant replay system for a sports match. Real GPU execution is like watching the game at full speed — you see the final score but miss the fouls. Oclgrind replays every single play frame-by-frame, with multiple camera angles (plugins) watching for rule violations: a referee for memory out-of-bounds (MemCheck), another for player collisions in the same lane (RaceDetector), and a coach's assistant tracking every move (InstructionCounter). It is slower than the live game, but it catches everything.

🚶 Step-by-Step Narrated Walkthrough

Follow a single OpenCL vector addition kernel execution as it flows through Oclgrind:

  1. Host API Call — The application calls clCreateProgramWithSource(). The Runtime layer receives the OpenCL C source string and forwards it to the Core.
  2. Program Compilation — Program::build() invokes Clang to compile OpenCL C to LLVM IR. Precompiled headers for builtins are loaded from OCLGRIND_PCH_DIR. The resulting LLVM Module is stored.
  3. Kernel Creation — clCreateKernel("vecadd") extracts the named function from the Module. The Kernel object parses argument metadata (types, address spaces, sizes).
  4. Argument Binding — clSetKernelArg() binds each buffer and scalar. The Kernel stores typed argument values that will be loaded into private memory at launch.
  5. Enqueue & Dispatch — clEnqueueNDRangeKernel() pushes a command onto the AsyncQueue. The queue thread creates a KernelInvocation with global size, local size, and offset.
  6. Work-Group Spawning — KernelInvocation iterates over the NDRange grid. For each work-group, it allocates local Memory and creates a WorkGroup object containing N work-items.
  7. Work-Item Execution — Each WorkItem gets its own private Memory and begins interpreting LLVM IR instructions: load, store, add, getelementptr, etc. Every instruction triggers plugin callbacks.
  8. Memory Access Validation — On each load/store, MemCheck validates bounds, read/write permissions, and alignment. RaceDetector records the access in its shadow memory for conflict detection.
  9. Barrier Synchronization — When a work-item hits barrier(), the WorkGroup suspends it and switches to the next. Once all items reach the barrier, execution resumes. RaceDetector checks for divergent barriers.
  10. Plugin Analysis — InstructionCounter tallies each opcode. Uninitialized propagates shadow bits to detect reads of unwritten memory. InteractiveDebugger may pause at breakpoints.
  11. Work-Group Completion — After all work-items finish, WorkGroup deallocates local memory and notifies Context. Plugins receive workGroupComplete() — RaceDetector clears per-group shadow state.
  12. Kernel Completion — After all work-groups finish, KernelInvocation signals done. InstructionCounter prints histograms. The Runtime marks the event complete and the host can read results.

Cross-Module Connections

sequenceDiagram
  participant RT as Runtime (ICD)
  participant CTX as Core::Context
  participant MEM as Core::Memory

  participant KRN as Kernel CLI

  RT->>CTX: clEnqueueNDRangeKernel
  Note over RT,CTX: Runtime translates OpenCL API to Core calls
  CTX->>MEM: allocateBuffer / load / store
  Note over CTX,MEM: Memory validates all accesses
  CTX->>PLG: notifyMemoryLoad / notifyMemoryStore
  Note over CTX,PLG: Every memory op forwarded to active plugins
  PLG-->>CTX: logError (if violation detected)
  KRN->>CTX: Simulation::run (standalone path)
  Note over KRN,CTX: CLI bypasses Runtime, talks directly to Core
Key insight: The Core module is the center of everything — it owns the simulation state and dispatches events. The Runtime translates OpenCL API calls into Core operations. Plugins are passive observers that receive callbacks from Core. The Kernel CLI provides a standalone entry point that bypasses the Runtime entirely.
